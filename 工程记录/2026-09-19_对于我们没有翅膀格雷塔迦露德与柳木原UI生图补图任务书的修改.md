## 任务目的

用户 2026-09-19 提出：「我们的 UI 工作有多少资源可以用图片来代替？你写代码画的图效果远没有生图模型直接生成的好。」并要求：「整理成任务书，接下来我会挨个生成。」

**验收标准**：交付一份**可执行**的生图任务书——逐件给出用途、目标尺寸、风格约束（含实测色值锚点）、提示词要点、命名规范、验收标准与接入方式；用户据此可**逐张生成、按 ID 命名、丢进入料目录**，由 UI 组规范化接入。

### 任务书里的关键判断（**依据都是实测，不是估计**）

1. **"可被图片替代的面积其实很小"**：逐屏数过 15 屏共 **333 个元素**——`text` 110（33%）、`rect` 92（28%，全是功能性色块：遮罩/面板填充/进度条/流程图节点连线）、`image` 81（24%，其中 **35 次是同一张九宫格边框**、16 次是运行时存档缩略图）、`list` 25（展开 161 个标签）、`hit` 25。
   **真正由 UI 组"画"的只有 2 件**（标题 logo、标题背景氛围层）。所以任务书的定位是**补图，不是替代**。
2. **补图位置按收益排序**，全部选**不含文字**的位置（避开最大红线）：8 张系统屏底图 + 20 个功能图标 + 11 张章节主图 + 9 张 Fragment 碎片图 = **48 张**。
3. **色值锚点全部来自原素材实测取色**（PIL 量化统计），不是编的：
   - UI 主色 `#081828`（`sm_base.png` 占 92%）
   - 对话窗蓝紫渐变 `#585898` → `#7888B8` → `#88A8D8`（`meswin.png` 文本区）
   - 幻想侧浅蓝 `#A8B8F8`/`#C8D8F8`/`#D8E8F8`（`dlg_bg_26.png`）
   - 现实侧都市 `#D8E8F8`/`#98A8C8`/`#7888A8`（`tl1_bg2.png`）
   - 幻想侧风景 `#485858`/`#485878`/`#587898`/`#486858`（`tl1_bg1.png`）
   - 标题原画高调浅色 `#F8F8F8` 主导 + 暖色 `#F8E8C8`/`#F8F8B8` + 砖红 `#A87868`（`tl2_bg1.png`）
   - 章标题卡暗红 `#480808`（`ec5_bg.png`）
4. **目标尺寸全部对齐现有 layout 实测值**（不是拍脑袋）：系统屏底图 1280×720（说明会把现有 `backdrop + bg_art(1200×450)` 合并为单张满幅）、图标 512→64（UI 内 24×24）、章节主图 504×284（行内缩略图由主图缩小派生，不用另出）、Fragment 组图标 96×96 / 碎片 126×168（UI 内 40×40 / 42×56）。
5. **红线 6 条**（§7），核心两条：① **不得把任何文字画进图**——生图模型生成汉字不可靠，且内容随剧本/翻译变，烘焙进图就是**重蹈原版「250 件图片化日文」的覆辙**；② **不得画人物**——立绘与 CG 已有原版素材（1,485 / 1,361 件），生图人物必然与原画风不一致，破坏美术统一（AGENTS.md §六）。
6. **技术规格对齐既有裁决**：不透明图交 JPG（体积小得多）、需透明的交 PNG+alpha；**允许裁切与缩小，禁止放大**（D1）；生成参数必须记录（生图不可复现，无参数则不可回溯）。
7. **建议跳过批次 E 的「可拉伸九宫格边框」**（E5）：krkr 无图片遮罩 API、无 `stretch` 属性，边框只能九宫格拉伸；生图边框四边不等宽、纹理不连续，一拉伸就断纹，改造成本高、收益低。

## 风险、警示与未完成项

| # | 事项 |
