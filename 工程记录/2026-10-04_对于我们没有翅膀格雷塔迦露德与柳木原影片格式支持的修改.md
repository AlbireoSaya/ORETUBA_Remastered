- 缘起：用户提问「我们的引擎现在支持播放 H.264 格式的视频吗？」→ 我给出「默认不支持、原因是扩展名白名单」的核查报告后，用户裁定 **「给引擎加 .mp4 支持」**

## 任务目的

把「krkrz 1.4.0.8 能不能播 MP4/H.264」从推论变成**实测结论**，并落实用户「加 .mp4 支持」的要求。
**结论先给**：**能播，而且不需要改引擎、不需要写插件 DLL** —— 走 **Media Foundation** 路
（`VideoOverlay.mode = 3`，即 `vomMFEVR`）即可；DirectShow 路则既被扩展名白名单挡在门外、
本机也没有 H.264 解码器。**成品未做任何接线**（本作现在仍不播任何影片，见「风险」第 4 条）。

## 方法：源码定位 + 10 组合实机矩阵

**源码级定位**（`工具\krkrz\src\krkrz-1.4.0r2\`）：

| 事实 | 出处 |
| --- | --- |
| DShow 影片路按**扩展名白名单**派发：`.mpg .mpeg`→MPEG1System、`.mpv .m1v`→MPEG1Video、`.dat`→MPEG1VideoCD、`.avi`、`.mov`；`.asf/.wma/.wmv` 另走 Windows Media；**其余查已注册处理器表，查不到就抛 `Unknown video format extension.`** | `movie\win32\dsmovie.cpp:1176-1192 ParseVideoType()` |
| 注册口 `TVPRegisterDSVideoCodec(...)` 的形参是**裸 C++ 函数指针** `typedef void* (*tTVPCreateDSFilter)(void*)` ⇒ **脚本传不进去**，注册路必须写插件 DLL | `movie\win32\TVPVideoOverlay.h:23-31`；`base\win32\FuncStubs.cpp:2678` |
| 输出实现四选一：`vomOverlay(0)`／`vomLayer(1)`／`vomMixer(2)`／**`vomMFEVR(3)`＝Media Foundation + EVR**；模式由 TJS 属性 `mode` 设置 | `visual\win32\VideoOvlImpl.cpp:166-171`；属性声明 `visual\VideoOvlIntf.cpp:879-895` |
| `mode` **不能在 open 后改**（「open 前にセットしておくこと」） | `visual\win32\VideoOvlImpl.h:46` |
| 引擎自带的可播插件：`krdstheora.dll`（Theora `.ogv`）、`wuvorbis.dll`、`kropus.dll` —— **没有 H.264/MP4 插件** | `工具\krkrz\krkrz_20171225\plugin\` |

**实机矩阵**：新增诊断模块 `ui_videotest.tjs`（`videotest.txt` 门控）＋ 驱动器 `工具\run_videotest.py`，
在 `build_v18` 构建上跑 10 个组合（每组合三拍：open → play → 800ms 后读 `position`；能报出尺寸＝文件被解析，
`position` 推进＝解码/播放管线真的在跑）。测试媒体由 ffmpeg 现造（命令见文末）。

## 验证方式与结果

**矩阵实测（`build_v18`，无人值守；`An exception occured = 4` 全部来自故意试不支持的组合）**

| # | 文件 | `mode` | 结果 |
| --- | --- | --- | --- |
| 0 | `ed_ai.mpg`（MPEG-1+MP2） | 默认 0 | OPEN OK 960×544；**position 两次运行分别 0 / 357 ⇒ 不稳定** |
| 1 | `ed_ai.mp4`（H.264+AAC） | 默认 0 | **FAIL** `Unknown video format extension.` |
| 2 | `ed_ai_asis.mov`（MP4 内容只换扩展名） | 默认 0 | **FAIL** `IGraphBuilder::Render : [0x80040218] 未找到可用于流呈现的筛选器组合` |
| 3 | `ed_h264_mov.mov`（真 MOV 容器，`-c copy`） | 默认 0 | **FAIL** 同上 ⇒ **本机无 DShow 的 H.264 解码器** |
| 4 | `ed_xvid.avi`（Xvid/MPEG-4 Part2 + MP3） | 默认 0 | **可播** ✓ 960×544，position 434 / 544 |
| 5 | `ed_ai.mp4` | **3（MF）** | **可播** ✓ position 419 / 523；**延后读数 960×544** |
| 6 | `ed_xvid.avi` | 2（mixer） | **FAIL** `Failed to create device : [0x8876086A]`（需 D3D9 设备） |
| 7 | `ed_ai.mpg` | 3（MF） | OPEN OK 但 **position 恒 0**（本机 MF 无 MPEG-1 解码器） |
| 8 | `ed_xvid.avi` | 3（MF） | **可播** ✓ position 350 |
| 9 | `ed_ai.mp4` + `visible=true`，保持播放 6 秒 | 3（MF） | **可播且平滑**：position 329→1029→1736→2429→3128→3828→4529→5229→5934（≈700/拍 ⇒ **实时**） |

**配方（可直接复用）**：`var vo = new VideoOverlay(win); vo.mode = 3; vo.open(url); vo.play(); vo.visible = true;`

**分级结论（避免过度声称）**
- **已验证**：MP4/H.264+AAC 在本机经 MF 路**能 open、能被解析出正确尺寸、能实时推进播放位置**；
  `mode` 前置设置生效；同一路也能放 Xvid AVI。
- **未验证**：① **画面真的上屏**（见风险 3，两台抓屏法都读不到 D3D/EVR 内容 ⇒ 只能肉眼）；
  ② **声音**（无音频采集手段）；③ **Win7**（见风险 1）；④ 与游戏内 UI/画面栈的集成（未接线）。

## 风险、警示与未完成项

1. ★ **OS 依赖是本轮最大的未决风险**：MF 路能放 H.264/AAC **是因为本机（Win10/11）自带这些 MF 解码器**。
   工作区兼容性基线含 **Win7 SP1 x64**，而 **Win7 的 MF 很可能缺 AAC**（甚至有版本缺 H.264）⇒
   「视频能播、但没声音/放不出」完全可能在 Win7 上出现，**本轮无 Win7 环境，未实测**。
   备选（若必须保 Win7）：① 现成 `.mpg` 或 **Xvid `.avi`**（本机实测可播、且 `.avi` 本就在白名单内，
   **零引擎改动**，画质介于 MPEG-1 与 H.264 之间）；② 随包附带解码器（涉及分发与授权，须用户定）。
2. **EVR 的集成模型与我们的画面栈不同**：`vomMFEVR` 把画面**合成到窗口**上，不写引擎位图 ⇒
   与我们 1920×1080 画布 / 分层 UI / 截图验收体系都不是同一套。真要做播放屏，须先定「影片与 UI 谁在上」。
3. ★ **抓屏验收这条路对本引擎已两次证伪**：GDI `CopyFromScreen` → 全白；`PrintWindow(PW_RENDERFULLCONTENT=2)`
   → 白底 + D3D 空洞。与工程既有教训（「D3D 窗口抓屏全黑，看实机画面要用引擎自己导出的 PNG」）一致，
   而 **EVR 内容连引擎自己的 `exportPng` 也抓不到** ⇒ 影片类改动的验收**必须**由用户在实机肉眼看，
   不得声称「已截图验证」。
4. **成品未做任何接线**：`build_story.py` 对 `kind=="movie"` 只记数不取件、`ui_story.tjs` 无 `MoviePlay`、
   构建里也没有影片件 ⇒ **本作现在仍不播任何影片**。本轮交付的是**能力与配方**，不是播放功能；
   是否做播放屏、播哪儿、用什么格式，须用户另行决定（已在交付说明里列为待决）。
5. **`videotest.txt` 是新增诊断开关**：只放在**测试构建**里、`run_videotest.py` 跑完即自删；
   已写进作品 skill 的「复测方法」。成品从不含该开关（与既有 13 个开关同等纪律）。
