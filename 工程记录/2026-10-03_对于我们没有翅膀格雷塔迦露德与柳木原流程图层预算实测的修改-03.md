## 一、★ 实测结果（`build_v15`，Windows 11，`System.getTickCount()` 计时）

**几何**：真实数据 —— `UIFlowGeomNodes` **712 节点**（UI 组 `全量布局.json`），`UIFlowGeomLinks` **693 条代理连线**，
`viewport 60,190 1235x827`。绘制靶子＝离屏 Layer（宿主层 `UIAssetHost` 做父，1920×1080，不可见）。

| 档 | 节点框（5×`colorRect`/节点） | 连线（3 点折线，`GdiPlus.Appearance` pen） | 箭头（实心三角，brush） | **合计** |

| 100 节点 ｜**视口裁剪** | 0/100 → 0 ms | 70/693 → 1 ms | 6 → 0 ms | **1 ms** |

| 300 节点 ｜视口裁剪 | 12/300 → 0 ms | 70/693 → 2 ms | 6 → 0 ms | **2 ms** |
| **656 节点 ｜不裁剪** | **656/656 → 2 ms** | **693/693 → 8 ms** | **200 → 3 ms** | **13 ms** |
| **656 节点 ｜视口裁剪** | **54/656 → 2 ms** | **70/693 → 1 ms** | **6 → 1 ms** | **4 ms** |

**判读**：

1. **结论：运行期自绘全量在性能上成立。** 全量 13 ms 对流程图屏 120 ms 重画节拍 ⇒ 占用约 **11%**；
   开视口裁剪后 **4 ms ⇒ 约 3%**。**冻结书点名「层预算未验证」这一项，至此结清。**
2. **成本结构**：**连线是大头（8 ms / 693 条）**，节点框极便宜（656 节点 ×5 次填充仅 2 ms），箭头 3 ms。
3. **与 UI 组 POC 的对照**：他们测到「736 框 ＋ 735 折线 ＋ 200 箭头 ＝ 56 ms/帧」，
   我方在本工程构建上同规模只有 **13 ms**。差异原因可查：我方节点框全用 `colorRect`（原生、5 次矩形填充），
   连线是 3 点折线；**故不能直接说他们的 POC 偏悲观**，只能说「在本工程的实际数据与这套原语下，余量比预期大得多」。
4. **视口裁剪收益显著**：节点 656→54、连线 693→70，合计 13 ms → 4 ms（**降 69%**）。落地时应默认开裁剪。

## 三、★ 修掉一个我引入的真缺陷（**曾影响成品**）

- 现象：`ui_boot.tjs` 在窗口就绪时回调 `uiVerify17Attach`，而我原先**只在 `ui_verify17.tjs` 里声明** `UIFlowPerfArmed`。
  未装载该模块时（**成品的常态**），钩子会引用未声明标识符 ⇒ **每次启动多一段异常 dump**
  （krkrz 对**被 catch 的异常**仍打整段 dump —— 本项目既有认知，我却违反）。
- 实测证据：同一轮日志里 `An exception occured at ui_boot.tjs(319)[(function) uiStoryWindowInit]`。
- 修法：**旗标改由 `ui_boot.tjs` 自己声明**（那里才是它必须存在的地方），`ui_verify17.tjs` 去掉重复声明；
  于是未装载时既不会抛、也不会有 dump。
- ⚠️ **该缺陷曾随 `ISSUE-20261003-09` 的成品部署出去一次**（成品已按修复版重建部署，见「验证」）。
