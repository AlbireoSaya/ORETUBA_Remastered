## 任务目的与**根因**（本轮最有价值的一条）

派单时主代理按「元素底边对齐」下判据（`y+h == banner_frame.y+banner_frame.h`），实测**改前就已成立**（500 == 500）——
说明真正的偏差**不在数据，而在素材的透明留边**：

| 项 | 值 | 来源 |
| --- | --- | --- |
| `cfg.banner_frame` | `(1099, 261, 644, 239)`，九宫格 `l=t=r=b=24`，素材 `ui/x_ui_cfg_preview_frame.png` **96×96** | 数据 |
| 底板素材内容 bbox | **(7,7,89,89)** ⇒ **四周各 7px 全透明留边** | 实测（`Image.getchannel('A').getbbox()`） |
| 九宫格行为 | 边缘带 **1:1** 画在元素框**内侧**（`复刻\replica.js` 的 border-image 分支与 krkr `uiWidgetNine` 同口径） | 代码 |
| ⇒ **底板可见底边** | `261 + 239 − 7 = **493**`（截图实测：下框线笔画 y490-491、末行内容 y492） | 实测 |
| 头像素材 | `face/*` 内容**铺满整图**（341 件 bbox 末行全 = 345）⇒ **头像可见底边 = 元素底边** | 实测 |
| ⇒ 改前症状 | 头像可见底边 **500** > 底板可见底边 **493** ⇒ **头像从底板下框线穿出 7px** | 改前截图亮像素行 262..499 |

**结论：一切「与素材留边有关」的对齐都要按「可见边」算，不能按元素矩形算。**
