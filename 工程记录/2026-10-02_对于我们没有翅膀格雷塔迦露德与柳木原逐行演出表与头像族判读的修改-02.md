## 任务目的

修掉**只有「在别处检出」才会暴露**的两处缺陷（`-01` 的工作树里全绿、合并后在主工作树首次运行就红）：

**触发证据（合并后从主工作树端到端跑校验器）**：

```
cd "E:\ZCode Workspace\Galgame"      # 主工作树（检出 main）
python -X utf8 "工程/我们没有翅膀——格雷塔迦露德与柳木原/资源组/工具/verify_staging.py"
→ !! 演出_ot.tsv 含 CR（契约要求 LF）
```

根因：本仓库 `core.autocrlf=true` 且无 `.gitattributes`——**blob 是 LF，检出到盘面却是 CRLF**
（字节数恰好多出行数，这正是 `交接说明.md` C12 的「行尾提示」）。而 `-01` 的校验器与台账
都把「盘面必须无 CR」当作硬条件、把 `sha256` 算在**盘面字节**上，于是：
① 校验器在**任何一个 autocrlf 检出**上都必然失败（用户跑的主工作树首当其冲）；
② `_index.json` 的 `sha256` 随检出形态变化，**同一提交在两处检出给出不同值**，台账失去校验价值。

任务书的行尾要求只有「UTF-8（无 BOM）」一项，**并未要求 LF**；LF 是本仓库的 blob 约定（C12），
不是交付契约。故修法是**让校验器与台账对两种行尾都成立**，而不是把交付件改成 CRLF。

## 改动清单

| 文件 | 行为变化 |
| --- | --- |
| `资源组\工具\verify_staging.py` | `read_tsv()` 改为：**LF 与 CRLF 都接受**，解析前统一规范化为 LF；**仍拒绝裸 `CR`**（CR 后不接 LF）；返回值新增 `line_ending`，逐源输出改为 `[源] 行 N ｜ 场景 M ｜ 行尾 LF/CRLF ｜ op 分布 …`（把行尾形态**显式打印**，不再隐含） |

| `资源组\演出\_index.json` | 重出（含上述三字段与新的 sha256） |
| `资源组\交接编程组\产物清单.tsv` | 重出（`_index.json` 规模随内容变化） |

## 风险、警示与未完成项

1. **`_index.json` 的 `sha256` 口径已变**：读台账做字节级校验时，**必须先把盘面行尾规范化为 LF**（字段 `sha256_over` 已写明）；否则 CRLF 检出会算出不同的值。这是 C12 既有口径的落地，不是新约定。
2. **不引入 `.gitattributes`**：本件只让工具容忍两种行尾；是否给本仓库加 `.gitattributes`（`*.tsv text eol=lf` 之类）**属全仓约定变更，未擅自决定**，留作后续裁决。
3. **自证脚本已入库**：`资源组\工具\test_staging_line_endings.py`（**已随本 issue 提交**）——把「autocrlf 检出」这一缺陷类钉成判据：LF／CRLF 两态均可解析且行数相同、**裸 `CR` 与 BOM 必须被拒**、台账 `sha256` 等于 **LF 规范化**值且与盘面形态无关（`临时\probe\` 下的即席脚本未入库，其结论已由本测试固化）。
4. 其余边界与 `-01` 的「风险、警示与未完成项」一致（立绘退场无信号／四源无 BGM／`np` 仅首次引用位／`ot_s04_13b` 的 `SE\SE23.OGG` 对不上素材账／⑥ 实机抽查未做）。
