## 结论与依据

### 一、决定性突破：PFS 容器已在本机解密成功

**做法**（现成工具，未自造轮子）：

1. 下载上游官方预编译版 `psvpfstools v2.0` 的 `release_win64_7.zip`（426,259 B，内含 `psvpfsparser.exe` 629,760 B + `libcurl.dll`），落盘 `工具\psvpfstools\release_win64_7\`。
2. 用 `sce_sys\package\work.bin` 偏移 `0x50` 取出的 16 字节 klicensee 作密钥执行：

```
psvpfsparser.exe -i "<app>\PCSG00299" -o "<out>\PCSG00299" \
  -k 238dbe01ab89893c81431287a1dee15d -f http://cma.henkaku.xyz
```

**结果（26.5 秒完成，3.1 GB 全量解密）**：

- 终端末尾输出 **`keystone: matched retail hmac`** —— 这是引擎对 dump 内 `sce_sys/keystone` 做的 HMAC 校验，**通过了**。这是密码学级别的证据，证明密钥正确、解密无误（不是"看起来像明文"这种软判断）。
- 幻数全部恢复：`icon.png` → `89504e47`（PNG）、`CG/CHR/SCRIPT/SystemData/ETC.cpk` → `43504b20`（`CPK `）、`VOICE.AWB` → `41465332`（`AFS2`）、`eboot.bin` → `53434500`（`SCE\0`，SELF 头）。
- 熵从恒定的 8.00 降到正常值：CG.cpk 4.77、CHR.cpk 4.78、SCRIPT.cpk 5.41、BGM.AWB 6.99。
- **原 dump 未被改动**（mtime 仍为 2018-09-28，输出全部落在工作区内），符合「原始文件只读」。

→ **上一份记录里「klicensee 能否解密尚未实机验证」这一条，现已闭环。**

### 二、SCRIPT.cpk 已解开：引擎是**纯文本脚本**的 Tasktype ADV

`SCRIPT.cpk` = 499 个**未压缩**文件，解出合计 27,458,719 B。全部是 **Shift-JIS 明文**，涵盖 `.txt` 34 个（`adv.txt` 场景跳转表、`chr000–chr213.txt` 立绘表）+ 465 个无扩展名文件（`S##_##X` 本篇、`P##_##X` Prelude 篇、`M##_##`、`CGMODE` 相册表、`chract` 动作/关键帧表）。

脚本语言的真实长相（`S01_02A` 节选，原文 SJIS，此处已转写）：

```

	{
		:Tasktype	"Message"
		:Message	"　ちょっと恥ずかしいけど、まずは初めて彼女と目が合った日のことを君に話してしまおう。"
	}

		:Tasktype	"SePlay"
		:SE 687		// SE049
		:Wait	0

	[Task280]

		:Texture	533	// EF01
		:Position	640,360
```

**关键判定：这不是字节码，是可读的结构化文本 DSL。** 全部 499 个文件里，`[include file="AdvCfg.h"]`、`[define SCRIPT_NAME, …]`、`[iscript] … [endscript]` 这几行 **全部位于 `//` 注释内**，是开发者遗留的历史写法；可执行内容只有自定义的 `[Section]{ :Key value }` 结构。Tasktype 词汇表**只有 55 种**，全部枚举完毕：

**引擎身份**：**未能取得公开命名**。已交叉核对 VNDB（PC 原版与 R 版 Engine 字段均为 `Lucifen`，而 PS3/Vita 三个 release 页 Engine 字段**全为空**）、GARbro 支持格式表（只覆盖 PC 版的 LPK1/Lucifen）、GitHub 仓库检索（`PCSG00299`/`oretsuba`/`Oretachi ni Tsubasa` 均 0 条）。脚本里唯一能标识来源的是开发者署名注释（`//MAGES.松山--シーンジャンプ処理ここから。--`）。**可确证的结论是：这是 5pb./MAGES. 为 PS3/PSV 移植自建或改造的文本 ADV 引擎，与 PC 版的 Lucifen 不是同一套。**

### 四、问题 1 结论：**能汉化**，且成本比预想低得多

**（1）文本层：完全可控。**
实测全量：**65,485 条 Message、2,183,751 个字符**、24,873 条带 `:Voice` 语音引用、24 条 `SetSceneName` 章节标题。文本在 CPK 里是自由格式文本字段（`":Message "…""`），**不存在 Lucifen 那种字节长度硬约束**——译文长度可以自由变化。

**（2）最大红利：88% 的台词可以复用已完成的 R 版译文。**

把 PSV 版解出的 57,483 条去重台词，与 `工程\我们没有翅膀R\语料\R版台词.json` 做逐字比对：

| 项 | 值 |
| --- | --- |
| PSV 版去重台词 | 57,483 条 |
| 与 R 版语料**逐字完全相同** | **50,559 条** |
| PSV 侧命中率 | **88.0%** |
| PSV 版独有（需新译） | **仅 6,924 条** |

即：**要新译的只有 6,924 条**（美咲线 + Prelude 短篇 + 新增场景），其余可用原文字符串做键，直接从 R 版译文库自动填充。

**（3）附带的产品质量提升**：现有 R 版成品因 Lucifen 定长约束有 **5,368 条译文被截断**（见 `lucifen-text-length-constraint`）。PSV 版脚本无此约束，**重做或移植时可以顺带修复这些截断**。

**（4）真正的卡点只剩一个：`eboot.bin`。**
实测量化：`eboot.bin` 877,280 B，PFS 层已解，但仍是 **SELF 加密**（头 `53 43 45 00`，全文无可读字符串）。而以下两类内容**只存在于 eboot 内**：

- **名字框/说话人显示名**：脚本里 `:Name 110 // 女生徒` 只是**数字 ID**，真正要显示的字符串只出现在 `//` 注释里。我在**整棵解密树**（含全部 CPK）里用 SJIS 原始字节搜索 `女生徒`、`ガルーダ`、`パル`，命中文件**只有 `SCRIPT.cpk` 一个**（且都在注释里）→ 名字表在 eboot。
- **文字渲染路径**（SJIS 字节 → 字形的转换表 / 字体载入方式）：决定中文能否显示。CPK 里**没有任何字体文件**（124+182 张 UI 全是 PNG），说明引擎要么用 PS Vita 系统字体（`sce_module\libface.suprx` 在位），要么把字体/映射表编进了 eboot。**两种情况下，要让 PSV 原版显示中文都得动 eboot。**

**（5）UI 文字是混合的**：`sys_menu.png`（522×301）我实看过，是**预渲染的日文图片**（「システムデータを上書きします。よろしいですか？…」+ YES/NO）→ 这类可以直接改图翻译；但配置菜单的标签文字既不在脚本里、也不在 `config.png`（实看是夜景背景图）里 → 大概率也在 eboot。

**（6）eboot 能不能解？——能，但需要 Vita3K 类工具。** Vita3K 已合并的 PR #3499 明确写：菜单项会对 app 目录下的 `.self`/`.suprx`/`.skprx`**/`eboot.bin`**「**使用该 app 的 license key (klic) 解密**」并写到缓存子目录；源码 `vita3k/packages/src/sce_utils.cpp` 的 `decrypt_fself(fself, klic)` 在无 klic 时报错 `No klic provided for encrypted App`。**而我们手上正好有 klic**（就是刚用来解 PFS 的那 16 字节）。所以「解密 eboot」是有明确路径的，本次未执行（需下载 Vita3K 并安装固件，属另一次工程动作）。

**→ 汉化结论：可行，且分两条路，成本差别极大：**
- **路线 A（改造 PSV 原版）**：解 CPK 换文本 → 简单；但要让中文**显示**，必须解密并改造 eboot 的字体/编码/名字表。风险集中在 eboot，收益是"原汁原味的 PSV 版"。
- **路线 B（重做成 Windows 版）**：见下一节。**中文显示问题自动消失**（现代引擎原生支持中文），代价是重做移植的工程量。

### 五、问题 2 与「Ren'Py 现场重做」——**我上次判断错了，现予纠正**

**上次的结论是**：「不可行……等于自建一个新游戏」。**该判断基于一个当时未验证的假设——脚本是字节码。实测证明脚本是结构化明文文本，因此结论必须修正。**

**修正后的判定：使用 Ren'Py（或其他现代 VN 引擎）把这批资源重做成一个 Windows 可玩游戏，技术上可行；它是一个「重制移植」项目，规模为一人+数周，不是"不可行"，但也不是"顺手做"。**

理由与成本拆解（全部有实测数据支撑）：

1. **素材搬运：接近零成本。** 946 CG + 1333 立绘 + 306 UI，**全部是带 alpha 的明文 PNG**，Ren'Py 直接可用，无需转码、无需逆向图片格式。
2. **音频转码：可脚本化。** 799 条 ADX + 26,500 条语音。Ren'Py 官方只支持 Opus/Ogg/MP3/FLAC/WAV，不支持 HCA/ADX → 需批量转 OGG/Opus（`vgmstream` 或 `cricodecs` 都能批量做）。一次性脚本活。
3. **视频转码：13 个文件。** Ren'Py 内置 FFmpeg 但**明确不支持 H.264 与 AAC**，需解复用 USM 后转 WebM/VP9+Vorbis。数量少，可手工+脚本。
4. **脚本转换：这是真正的主体工作，但已从"不可做"变成"可做"。** 需要写一个 emitter，把 499 个脚本文件的 Task 序列（65,485 条 Message + 55 种 Tasktype）转换成 Ren'Py 的 `label`/`jump`/`say`/`show`/`play`/`with`。因为是**结构化文本→结构化文本**，而不是字节码反编译，所以这是一件能写、能验证、能增量推进的工程。
5. **资源 ID 映射：不用猜，注释里全都有，且已实测对得上。**
   - `:Texture 533 // EF01` ↔ `CG.cpk` 内确有 `ef01.png` ✓
   - `:Texture 165 // ST_ASU01` ↔ `CHR.cpk` 内确有 `ST_ASU01.png` ✓
   - `:SE 687 // SE049`、`:BGM 13 // bgm 14`、`:Voice 16862 // misaki_000` 同理
   → 全部 ID→文件映射表可以**从脚本注释自动生成**。
6. **名字表：也能从注释自动重建。** `:Name 110 // 女生徒`、`:Name 31 // 隼人` —— 引擎把名字表藏在 eboot 里，但**注释把它泄底了**，重做路线因此不受影响。
7. **中文显示：Ren'Py 是顺风局。** 官方文档明确：默认字体不含 CJK，需在 `gui.text_font` 换用带中文的字体；跨字体混排用 `FontGroup().add(...)`；断行用 `gui.language = "japanese-loose"`（中日文专用算法）。**这些在 PSV 路线是"要攻破 eboot 的难题"，在 Ren'Py 路线是"改两行配置"。**
8. **真正的剩余风险：55 种 Tasktype 的渲染语义。** 淡入淡出时长、立绘动作、`EffectQuake`/`Flash`/`EyeCatch`/`InOut_Act` 等特效的**表现还原度**没有公开文档可依（引擎在 eboot 里，我们没读它）。字段名自解释、取值明确，可按名字与实测截图反推，但**特效必然会有损失或走样**。这是重做路线唯一需要接受的质量折价。
9. **已有先例可参照**：社区确有同类项目——`Green-hats/Ikikoi`（把 NScripter 游戏**自动转换**成 Ren'Py 完整重制版：158 个剧情标签、约 3 万句台词、10699 条语音、7845 张图）、`JinAsukin/utage-to-renpy-android-port`（Unity+Utage → Ren'Py 的实战工具集）、`franckv/nscripter2renpy`（点对点转换器）。**没有**覆盖「CRIWARE + Tasktype ADV」的现成转换器，需自研。

**→ 问题 2 结论：**

- **直接在 Win10/11 上玩**：Vita3K 可行（官方兼容列表 PCSG00299 = Playable），且我们已能把 NoNpDrm 加密 dump 解密（本次实测成功），装上就能跑日文原版。**Win7 仍不支持**（官方 FAQ 写 `OS: Windows 8/10/11`，需 OpenGL 4.4/推荐 Vulkan）。
- **用 Ren'Py 重做成 Windows 中文版**：**可行**。工程量主要是脚本转换器 + 资源转码 + UI 重建；中文显示与名字框这两个在 PSV 路线上最扎手的点，在这条路线上都不成问题。配合 88% 的译文复用率，实际新增翻译量约 6,924 条。

### 六、两条路线的直接对比（供用户决策）

| 维度 | 路线 A：改造 PSV 原版 | 路线 B：Ren'Py 重做 Windows 版 |
| --- | --- | --- |
| 文本层难度 | 低（CPK 内明文替换） | 中（要写转换器，但结构清晰） |
| 中文显示 | **高**，卡在 eboot（字体/编码表/名字表） | **低**，改配置即可 |
| 素材 | 直接复用（原格式） | 需转码音频/视频（可脚本化） |
| 效果还原度 | 100%（原引擎） | 有折价（55 种 Tasktype 语义靠反推） |
| 运行平台 | PS Vita 真机 / Vita3K（Win8+） | Windows 7/10/11 原生 |
| 译文复用 | 88% 可复用（需匹配 CJK 字库方案） | 88% 可复用，且可修复 R 版 5,368 条截断 |
| 主要未知 | eboot 解密后字体方案是否可改 | 特效语义还原度 |

**一个重要的战略观察**：上次我说「重做不可行、建议直接汉化 PC 版」。现在数据表明，**若目标是"Windows 上玩中文的美咲线版本"，路线 B（Ren'Py 重做）反而比路线 A 更可控**——因为它把最难的两件事（字体/编码、名字表）从"逆向外加二进制补丁"降级为"配置项"，而代价只是特效还原度。反过来，如果坚持要"PSV 原味版"，则必须攻 eboot。
