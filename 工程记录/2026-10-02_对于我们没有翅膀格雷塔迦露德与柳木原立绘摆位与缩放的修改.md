## 任务目的

重写五源立绘的**横向摆位**与**尺寸**，满足用户四条要求。验收标准：改后实机帧里
① 立绘明显变小；② 1 号靠左、2 号靠右；③ 第三人起落在 1/2 之间；④ 互不重叠、不出画；⑤ 剧情回归 0 异常。

## 关键背景（为什么旧规则必然出问题）

五源立绘原用「内容区宽度百分比」定槽位：`1 人 0.40／2 人 0.25,0.75／3 人 0.18,0.50,0.82／≥4 人 0.10..0.90 均分`。
该比例是**在旧 4:3 框（宽 1200）里标定**的；D-04 全画布（宽 1920）后：
首槽中心由 480 → **192**，而立绘宽约 666 ⇒ **x=−141（左侧出画 21%）**；且 0.10 与 0.30 的中心只差 **384px < 立绘宽** ⇒ **必然重叠**。
（实测 `scene_ota_23_1b` 负 x 条目 **48 条**；目视 `画幅审计\对照_立绘出画_全画布下N≥4.jpg`。）

## 改动清单（全部在 `编程组\工具\build_story.py`）

| 改动 | 内容 |
| --- | --- |
| **新增参数** | `STAGE_CHR_SCALE = 0.80`（立绘高 ＝ 内容区高 × 此值）／`STAGE_CHR_SCALE_FLOOR = 0.35`（拥挤场景自适应降缩放的保底）／`STAGE_CHR_EDGE = 40`（两端边距）／`STAGE_CHR_GAP = 16`（最小间距） |
| **删除** | 旧比例表 `STAGE_SLOT_FRACS` 与 `stage_slot_frac()` |
| **新增 `stage_slot_layout(n, widths, cb)`** | 用户规则实现：**1 号靠左 / 2 号靠右 / 3 号起落在 1 与 2 之间从左到右均分**；按**各族实际宽度**（取该族最大宽度）反解，末尾做**左→右、右→左两遍扫描**保证互不重叠且夹在内容区内；放不下时退化为等距铺开 |
| **尺寸：底边锚定 + 缩放** | 立绘高 ＝ 内容区高 × 缩放（原为满高）；**缩放以底边为基准**（底边恒贴内容区下沿，顶随缩放下移）；`otv` 的源侧 y 偏移按同比例保留（主路径与 `chr_move` 两处同口径） |
| **按「在场集合」实时重排** | 原为**场景级固定槽**（族→槽位一次定死）。实测该模型下**68 个场景只有 2 人同屏却仍重叠**（同屏两人可能落在相邻的"中间"槽）。改为：**只要在场集合变化就重排**，变位的老成员**补发 `chr_move`**（文件序落在本次事件之前 ⇒ 引擎先移位、再让新角色入场） |
| **触发条件（三处，缺一不可）** | ① 本族**不在 state**（新出场）；② **整屏件→普通立绘**的转变（否则它带着画布中心压住别人）；③ `chr_remove` 退场后。⚠️ **不能只看 `chr_add`**——源侧也用 `chr_expr` 引入新族（实测 `ota_23_1b`/`ot_s01_02a` 的首个立绘 op 就是 `chr_expr`） |
| **只算"画得出来"的族** | `ui_staging.tjs` 的槽位上限＝`STAGE_MAX_SLOTS`(6)，`slot ≥ 6` 的族**永不显示** ⇒ 重排时排除它们（否则白占位置、把真正显示的挤重叠） |
| **场景缩放按"最大的 6 个族"算** | 而非"先出现的 6 个" ⇒ 任意 ≤6 的子集都放得下 |
| **新增自检闸门** | `[stage] 立绘布局：基准缩放×… ｜ 相邻重叠对 N（须为 0）｜ 自适应降缩放的场景 N 个 ｜ 最小有效缩放×…` |

## 风险、警示与未完成项

1. ★ **残留 7% 重叠未清零，根因是五源「无退场信号」**：C21 硬边界①明确五源拿不到立绘退场 ⇒ 本器只能把
   "本场景出现过的族"都当作在场 ⇒ 实测同屏人数累积到 **20 人**；这些场景被误判为"极拥挤"，一路降到保底 0.35 仍放不下。
   **按需求缩放为放得下需 ≈0.09，显然不可接受** ⇒ 保留现状并如实报数。
   **真正的解**：① 资源组补出五源的**退场信号**（源侧语义或逐场景判读），或 ② 用"同一渲染帧内实际出现的条数"启发式近似退场。
   **建议单独立项**。
2. **保底值 0.35 与基准 0.80 是我的选择**（用户未指定数值）：基准 0.80 使立绘比 D-04 满高小 20%，
   保底 0.35 用于 5–6 人同屏。**若要更大/更小，改一个常量即可**（`STAGE_CHR_SCALE` / `STAGE_CHR_SCALE_FLOOR`）。
3. **`chr_move` 事件数由 21 → 817**：这是"1 左 2 右"规则的固有代价——**有人进场/退场时其余立绘会横向移位**。
   若用户觉得"滑动"扎眼，可改为"只在进场时排一次、退场不重排"（代价：退场后留空位）。
4. **`--cb-full` 只为对照**：本改动在**当前 4:3 框**下同样生效（实测该态重叠 233 场景），但其完整效果
   （立绘横铺满屏）要等 **D-04 全画布落地**——D-04 仍是 UI 组的 `aeece1f`，尚未合并。
5. **未做**：正面/背面朝向、上下叠放（同侧多人）、立绘与背景的遮挡关系（z 未变，仍为 10）。
6. 回滚：`git revert` 本分支；或把常量改回满高并恢复 `stage_slot_frac`（旧实现已从代码中删除，需从 `main` 历史取回）。

## 审查结论

- **一审**：本改动以「**引擎实跑导图**（非 PIL 模拟）+ **全量闸门**（可失败：相邻重叠对数）+ **剧情回归**」三路自证；
  实机帧逐张目视（改前/改后/四人场景）。闸门确实报过非 0（中途多轮），逐轮修因（`chr_expr` 引入新族、
  整屏件→立绘转换、slot≥6 白占位、缩放按"先出现 6 个"），**证明闸门能失败、不是空跑**。
- **二审（主代理）**：核实机帧与数据侧位置一致；核闸门数字与独立复算脚本一致；剧情回归判定线；合并入 `main` 并重新部署成品。
- **遗留**：上文 1–3（退场信号缺口 / 常量取值 / 滑动观感）属已知限制，已如实登记；**建议就"退场信号"单独立项**。
