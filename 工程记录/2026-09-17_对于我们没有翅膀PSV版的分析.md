### 一、加密取证：整份 dump 是「PFS 加密的 gamedata 容器」

**现象（实测）**：

- 逐文件 64 KB 采样熵扫描：60 个文件中 **51 个熵为 7.9–8.0（密文）**，包括 `eboot.bin`、全部 `.cpk`/`.awb`/`.usm`、**全部 `.png`**（含 `sce_sys/icon0.png`、`manual\001–010.png`）、`sce_sys/trophy/NPWR05642_00/TROPHY.TRP`。
- `eboot.bin` 文件熵 **8.000**（逐 64 KB 分块均为 8.00），首字节非 ELF/SELF 幻数 → **SELF 加密**。
- `.cpk` 文件中**不存在** CRI CPK 幻数 `CPK `（`43 50 4B 20`），连偏移 0 都是随机字节。
- 所有 `.png` **不存在** PNG 幻数 `89 50 4E 47`。
- 明文文件只有：`sce_sys/param.sfo`、`clearsign`、`keystone`、`package\{head,tail,temp,stat,work}.bin`、`sce_pfs\{files.db, unicv.db, pflist}`。

**控制实验（区分「加密」与「本来就压缩」）**：

- `icon.png` 与 `icon_empty.png`（各 102,730 B）**逐字节完全相同** → 同明文得同密文。
- 但 23 个 PNG 的**明文头 16 字节必然相同**（PNG 固定签名 + IHDR 头），而它们的**密文头 16 字节各不相同**（`18db5eab…` / `682f50a5…` / `5685f223…` …）。

→ 结论：**不是**全局流密钥（否则所有 PNG 密文头会一致），而是**逐文件 / 逐扇区密钥**。这与 psvpfsparser 源码里「`dec_key` 取自 klicensee，tweak 由扇区号 + salt 派生」的模型吻合。

**决定性发现——钥匙是明文摆在 dump 里的**：

`sce_sys/package/work.bin`（512 B，熵 1.17）十六进制：

```
00000000  00 01 00 01 00 01 00 02 ef cd ab 89 67 45 23 01   ← 0x08 = 0x0123456789ABCDEF
00000010  4a 50 30 37 34 35 2d 50 43 53 47 30 30 32 39 39   J P 0 7 4 5 - P C S G 0 0 2 9 9
00000020  5f 30 30 2d 4f 52 45 54 53 55 42 41 30 30 30 30   _ 0 0 - O R E T S U B A 0 0 0 0
00000030  56 49 54 41 00 …                                    V I T A
00000050  23 8d be 01 ab 89 89 3c 81 43 12 87 a1 de e1 5d   ← 0x50 = 16 字节 klicensee
```

- `0x08`（小端 u64）= `0x0123456789ABCDEF` = **NoNpDrm 的 FAKE_AID**（TheOfficialFloW/NoNpDrm 的 `main.c` 与 libzrif `rif.h` 中的常量）。
- `0x50`（NoNpDrm 结构体里 `license.key` 的偏移）**明文**给出 16 字节密钥：**`238dbe01ab89893c81431287a1dee15d`**。

即：这份 dump 是**NoNpDrm 假授权 + PFS 加密内容**的正常形态（NoNpDrm 只伪造 license，不做解密；README 原文："Allows sharing PFS encrypted content (**unmodified non decrypted games**)"、"This software WILL NOT Work with PFS decrypted content"）。它**不是**「纯 PC 直接能看明文」的 Vitamin/FAGDec 型解密 dump。

### 二、问题 1：能否汉化？——**技术上可行，钥匙已到手；但真正的门槛在第二级，且是一整个新立项**

分三级门槛：

**门槛一 · PFS 解密 —— 已定位解法（本次建议的第一步）**

- 纯 PC 工具 `psvpfsparser`（motoharu-gosuto/psvpfstools）README 原文："this tool is a completely new standalone approach that **does not require you to have PS Vita**. All decryption is done **directly on the PC**."，命令形态 `-k <klicensee hex>` 或 `-z <zRIF>`，另需 `-f <F00D 服务>`（默认 `cma.henkaku.xyz`）。
- Vita3K 自带 fork（`external/psvpfstools`）额外实现了**离线 native F00D**（`F00DNativeKeyEncryptor.cpp` 内置 `contract_key0`，注释："originally F00D service handles different key_ids / however PFS can only use key_id 0"）→ 不必联网。
- 另一条等价路径：把 app 目录打成 zip/vpk 交给 Vita3K 安装；`vita3k/packages/src/pkg.cpp` 的 `decrypt_install_nonpdrm()` 会读 `work.bin` → `rif2zrif` → 解密并把解密结果重命名覆盖原目录 → 安装完即得到**明文 app 目录**，之后可以直接拷出来做资源提取。

**门槛二 · `SCRIPT.cpk` 内层格式 —— 未验证，是汉化可行性最大的变量**

- 解密后才能用 CRI CPK 工具（CriPakTools / YACpkTool / CriFsV2Lib / GARbro）打开，进而判定脚本字节码形态。
- 公开世界**没有任何人解包过本作 Vita 版**：VNDB 的 PS3/Vita 三个 release 页 Engine 字段**全为空**（PC 原版与 R 版都写着 `Lucifen`）；GitHub / 中文社区检索 `PCSG00299`、`我们没有翅膀 Vita 解包` 均无解包记录。
- 一条**旁证（非证据，标为推测）**：R 版的脚本是 446 个 `.tob`/`.sob`，合计 **10,499,137 B**；Vita 的 `SCRIPT.cpk` 是 **27,998,224 B**，相差 2.67 倍。Vita 版确有新增剧情，但这个倍差偏大，**倾向于**「Vita 脚本不是 R 版脚本的直接重打包」。**必须解密解包后才能定论。**
- 两种分岔的代价差别极大：
  - **若**脚本恰是 Lucifen 的 TOB0/SOB0 → 我们的 `.zcode\skills\lucifen-unpack\` 全管线（含 TOB0 消息表判据、地址重定位、LZSS、二进制补丁法）可直接复用，汉化就是「换容器」的常规活。
  - **若**是 5pb./MAGES. 侧自建或改造的脚本机（更可能）→ 需从零逆向脚本格式，属**新引擎立项**。

**门槛三 · 字体与 CJK 显示**：Vita 系统有中文字体，但引擎若自带位图字体，则需注入汉字字形（R 版就是靠 GBK 化三补丁 + 引擎级改造解决的，那套改造不可直接搬）。

**工作量对照（这是回答用户"值不值得"的关键）**：

- R 版汉化 = 58,855 槽，是我们已有全套工具、同引擎、同素材的活，仍投入了一整个 issue 周期。
- Vita 版从零起 = 引擎/脚本机逆向 + 文本提取回写 + 字体 + 重打包，**是新立项级别**。
- **最大的可复用红利**：Vita 版「以 R 版为基础」。若脚本正文与 R 版同源，理论上 R 版 58,855 槽的中文译文可以按**原文字符串匹配**做文本级迁移，只翻译新增部分（美咲线 + Prelude 短篇 + 新 OP 歌词）。**这一点同样必须等解密解包后才能验证同源度。**

### 三、问题 2：能不能在 Windows 上直接运行？——**Win10/11 能（模拟器，已收录为 Playable）；Win7 不能；"用现有引擎现场重做"不可行**

**(a) Vita3K 模拟器 —— 唯一成熟路线**

- **只有 Vita3K**：GitHub 5,723 stars、最后 push 2026-09-12（活跃）。其他「PS Vita 模拟器」要么停更（Anubis，2021）、要么已归档（kvitaemu 2017、betavita 2024），EmuCoreV 是 Vita3K 内核的安卓前端；Mednafen 官方文档**完全不含 PS Vita**。
- **官方兼容性：收录且为可玩**。官方兼容库接口（`vita3k-api.pedro.moe/list/commercial`，2026-09-16 快照）条目原文：
  `{"name": "Oritachi ni Tsubasa wa Nai", "titleId": "PCSG00299", "status": "Playable", "color": "0E8A16", "issueId": 307}`
  对应 GitHub `Vita3K/compatibility` issue #307（2020-01-10 建，2022-07-05 由 `Bootable` 改标 `Playable`）。分级定义里 Playable = "Games that can be played from start to finish with playable performance and no game breaking glitches"。
  ⚠️ **但该 issue 正文仍留着旧记录 "Hangs with a green screen"（v0.1 / build 1316 时代）**，与 2022 年之后的标签不一致，且页面自己声明"兼容列表已不反映模拟器现状、鼓励用最新版重测"。→ **需实机复测，不能只看标签。**
- **系统要求（这条直接回答"Win7 行不行"）**：官方 FAQ 原文
  > "PC CPU: x86_64/ARM 64-bit CPU  GPU: **OpenGL 4.4/Vulkan 1.0** capable graphics  RAM: Minimum of 4 GB RAM  **OS: Windows 8/10/11**, macOS 13.3 (Ventura), and Linux on a 64-bit OS"

  → **Windows 7 不在官方支持列表内**（且要 OpenGL 4.4 / 推荐 Vulkan，老 Win7 机器显卡往往也不达标）。AVX 只是推荐项，AVX2 未提及。**本机是 Windows 11（10.0.22621），满足条件。**
- **dump 格式要求**：官方支持 `.pkg / VCI / NoNpDrm / FAGDec / manually decrypted games`；对"仍处加密层的内容"视为非法输入（Vita3K PR #3597 原文："Prevents crashes or errors when games try to load no valid self or content **still layer-encrypted**"）。我们这份恰好带 `work.bin` 假授权，按 NoNpDrm 流程交给模拟器安装即可由它自行解密。
- **局限**：模拟器里跑的是**日文原版**——"能在 Windows 玩"和"能汉化"是两件事，后者要单独立项；Windows 7 用户则完全无解。

**(b) 用现有引擎 + 本作资源「现场制作」一个 Windows 版 —— 不可行**

这是把「我改一个已有游戏的数据」误当成「我用素材搭一个新游戏」。真实链路是：

解密 PFS → 解 CPK/AWB/USM → 提取 CG/立绘/语音/BGM/视频/脚本 → 资源转码为目标引擎格式 → **重建脚本**（字节码不能跨引擎执行，只能转换或整段重写）→ 重建 UI / 存档 / 设置 / 画廊 → 中文字体。

R 版之所以能被我方改造成中文 Windows 成品，是因为**原厂本来就是 Lucifen + 我们只改数据字节、不动引擎**；Vita 版是原厂**换过打包体系（LPK→CPK）与运行平台（Win→Vita）**的另一个产品，要"重做"等于自建一个新游戏。工作量与风险都显著高于直接汉化，**不建议**。

**(c) 但如果目标是"中文 + Windows + 美咲线"，有一条性价比高得多的排序**

先摆一个实测事实：**美咲线是 PS3/PSV 独占，我们的 PC R 版成品里没有。**
全量检索 R 版语料（`语料\R版台词.json` 16,289,925 B、`语料\R版串池.json` 23,163,097 B）：`美咲`出现 **0** 次（`みさき` 仅 4 次，属不同语境），而 `亜衣` 1,695 次、`香田` 612 次。
→ 也就是说：**「我们没有翅膀R」Windows 中文成品已经能用（`成品\我们没有翅膀R\`，含亜衣线），用户想从 PSV 版拿到的，实质是"美咲线 + Prelude 短篇 + 新 OP"这批独占内容。** 按性价比排序：

1. **Vita3K + 本 dump**：Win10/11 上可以立刻玩到日文原版（内容最全）。不需要汉化即可先满足"能玩"。
2. **解密 → 只提取文本 → 与 R 版译文做文本级迁移**：若同源度高，新增部分（美咲线等）翻译量可控。但仍要先跨过门槛二（解 CPK 内层格式），**这才是真正的成本所在**。
3. 找 PC 版《俺たちに翼はない～Prelude～》（2009 fandisc）替代 —— **不成立**：Prelude 只收录「ある日の林田美咲」等短篇，没有完整的美咲攻略路线。

### 四、给用户的行动建议（按顺序）

1. **先做「解密 + 探明脚本格式」这一步（一次性的小工程，不承诺汉化）**。理由：它同时决定三件事——能否汉化、能否抄近路复用 R 版译文、以及资源能不能拿去二次利用。成本可控（一个工具 + 一次运行），产出是完整的明文 app 目录。
2. **解密成功后立刻判定 `SCRIPT.cpk` 的脚本格式**：是否 Lucifen TOB0/SOB0。这一步定生死，也定工作量。
3. **同时用 Vita3K 在本机（Win11）复测 PCSG00299 是否真如标签所示 Playable**，把 issue #307 的"绿屏"旧结论排掉——这一步只影响"能不能玩"，不影响"能不能汉化"。
4. 只有当第 1、2 步给出「脚本格式可解且与 R 版同源」的结论时，才值得把 Vita 版汉化立成正式 issue。

## 风险、警示与未完成项
