# Lucifen（Easy Game System DX）解包与汉化管线

> 适用：Navel 等会社使用 **Lucifen / Easy Game System DX** 引擎的作品。
> 首次沉淀作品：『俺たちに翼はないＲ』（2011，Navel）。本篇结论均在该作**实测**确认；
> §7.1 的素材密钥求取法为『俺たちに翼はない～Prelude～』（2008）实测新增。

## 二、LPK1 归档结构（四层）

```
文件布局：[0..4)  "LPK1"
          [4..8)  u32「索引长度 ^ key1」（bit24-31 为 flags）
          [8..)   加密索引（长度由上面的字解出，可能需 <<11 变换）
         随后     数据区：各条目压缩流依次拼接
```

**索引解密后**：
```
u32 条目数 | u8 plain_len | plain[plain_len] | u8 mode(1=long/0=short)
| u32 字母表长度 | 字母表(trie) | 条目记录表[]
条目记录（flags.bit3=1 时 13 字节，否则 9 字节）：
  u8 is_crypted | u32 file_offset | u32 compr_len | u32 uncompr_len
```

**flags 位**（实测本作 `0x1e`）：bit0 = off​set<<11；bit1 = 索引模式存在；
bit2 = is_crypted；bit3 = 记录 13 字节；bit4 = whole_crypt。

### 2.1 索引层加密（自逆，加解密同用）
```python
d = 0x31746285; k = key1
for each 32-bit word w (LE):
    d = rotl32(d, 4)
    w ^= k
    k = rotr32(k, d & 31)
```
`key1` 由 **LPK 基名**（大写、去扩展名、ASCII/CP932）派生：
```python
k1 = 0x9A639DE5
for i, ch in enumerate(name_bytes):
    k1 ^= ch; k1 = rotl32(k1, 7)
# 另有 key0 = 0xA5B9AC6B 同法用 rotr32 —— key0 用于「容器层」
```

### 2.2 容器层（每条目）—— **单向置换，写回必须用逆映射**
- **解密**：先整段 nibble 正映射，再对**前 `min(len/4, 64)` 个 DWORD** 做 XOR（key 由 LPK 基名派生的 `key0` 起，`d=0x31746285` 每轮 `rotr32(d,4)`，`k = rotl32(k, d & 0xFF)`）
- **加密**：反过来——先 DWORD XOR，再 nibble **逆映射**
- nibble 正映射：`out = ((b ^ 0x50) >> 4) | (((b ^ 0xFD) & 0x0F) << 4)`
  —— 这是 256 元置换，**自逆不成立**，必须预计算逆表

### 2.3 LZSS 压缩层
```
窗口 4096 字节，**零初始化**，写游标从 0xfee 起
控制字节在前，1 字节管 8 个 token，bit0 优先：
  bit=1 → 字面量（1 字节）
  bit=0 → 回溯（2 字节）：off = b0 | ((b1 & 0xf0) << 4)
                          len = (b1 & 0x0f) + 3
复制时 off 是**窗口绝对下标**，按 (off + i) & 0xfff 逐字节读窗口
```

**写压缩器的两个要点（踩过的坑）**：
1. **每个 token 都要占一位控制位**——字面量与回溯都必须 `ctrl_bit += 1`，漏掉会写出超过 8 个 token 的组，解压必然错位。
2. **候选必须避开「本次写入区间」**——解压是逐字节「读 `(off+k)` → 写 `ncur`」，若源区间与目标区间在同一环形窗内重叠，源字节会随写入改变（RLE 式）。压缩端只选**不与本次写入区间重叠**的候选即可稳定复现，压缩率损失极小（实测 45–55%）。
3. `uncompr_len == 0` 的条目是**未压缩**：数据只做容器加密、不做 LZSS。

## 三、脚本格式

### TOB0（剧情）
```
头部：b"TOB0" | u32 size | u32 标签数 B | [u8 名长][名][0x00][u32 标签偏移] × B
code_start = 0x2e + 4*B          ← 标签数可变！不可写死 0x2e
```
- **显示文本判据（实测 100% 成立）**：头部之后是**消息表 T**，
  `T[k] + code_start` = 第 k 条消息记录的**结束地址**；该记录前 18 字节恒为
  `5b 20 0c 00 00 00 01 0b 00 00 00 01 01 00 <u32 k>`（末字段 == k）；
  **正文 = 该记录末尾之前那段无长度字段、无 NUL 的 SJIS 字节**。
- **变长回写必须重定位四类地址字段**：标签值、T 表、`02 ff 00 <addr>` 跳转、尾形地址；
  **消息索引与毫秒计时参数不重定位**（改了就错）。

### 声明串（`01 01 <u16 L>`）——说话人名 / 选项标签 / 场景描述
- 结构：`01 01` + u16 L + 内容（**末字节必须 `0x00`**）；`L = 内容字节数 + 1`。
- **引擎按 NUL 结尾读取该串** ⇒ 末字节不是 NUL 时会越读到下一条记录的 `01 01 <L>` 字节，
  在名字框渲染成 **2–3 个方块**（2026-09-15 实测：某构建器把末字节写成半角空格 0x20，
  32,512 条名字全部中招；把该字节改回 0x00 即根治，无需其他改动）。
- **等长是硬约束**：声明串与正文不同，**不要做变长重建**——长度一变即牵连结构（选择支失效/崩溃）；
  保险做法是**等长覆写**（不足处补全角空格，末字节留 NUL）。
- 名字/标签中若出现 GBK 不可编码字符（日文 `・` 等），按 §五 的回退表处理，**不得跳过整条**。

### SOB0（系统 / 本篇剧情）
- 台词内联为 `#<说话人>\<语音ID>$&<正文>$`（正文 SJIS）；按 `$` 定界解析即可。
- 本节只覆盖**正文抽取**；**命令层解码（容器 / 六表 / 项流 / 命令节点 / V / 控制串 / 参数换算）见 §十二**。

## 四、重打包策略：**二进制补丁 > 全量重建**

社区工具（`UBTL/Lucifen-Tools` 的 `lpk_repack.py`、`lpk-script-repacker.py`）**不支持 LZSS 压缩**，
对使用压缩的 LPK 会失败（`does not implement compression`）。
可行的两条路：

1. **【推荐】二进制补丁**：在原始 LPK 字节流上只替换目标条目：
   - 重新压缩该条目 → 覆盖其数据区区间
   - **其后所有条目的 `file_offset` 都要按新长度平移改写**
   - 重写该条目的 `compr_len` / `uncompr_len`（`uncompr_len=0` 的未压缩条目必须保持 0）
   - 索引重新加密写回；**头部的「索引长度 ^ key1」字也要重写**（否则 flags 丢失、引擎读坏）
2. **全量重建**：用自研压缩器重压全部条目。技术上可行（本作实测 446/446 往返逐字节一致），
   但**引擎的实际解压器比社区实现更严格**——全量重压后实机出现「スクリプト初期化ファイルのロードに失敗」。
   **建议只重压改动过的条目**，未改动条目原样保留字节。

## 五、硬约束与坑（务必遵守）

- **游戏本体路径必须纯 ASCII**。本作把存档目录绝对路径以 **Shift-JIS** 写进 `USER.CFG`；
  路径含简体字（如「我们没有翅膀R」的 们/没/翅/膀）时 `encode('cp932')` 直接失败 → 引擎无法表示。
  改路径后必须同步改写 `USER.CFG` 的路径段（u16 长度前缀 + SJIS 串 + NUL），
  两份副本都要改（存档目录内 + `%APPDATA%\<游戏名> SaveData\`）。
  - USER.CFG 缺失 → 「環境設定ファイルの読み込みに失敗」
  - USER.CFG 内路径失效 → 「セーブデータ作成フォルダが見つかりません」
- **LPK 的 key 由文件名派生**：改名 LPK（如 `SCRIPT_roundtrip.LPK`）会导致 key 不同、
  解包结果完全错乱。测试时输出文件必须仍叫 `SCRIPT.LPK`（可放不同目录）。
  —— **同理，备份 LPK 时也要记住**：回退时必须**改名回 `SCRIPT.LPK`** 再放回游戏目录。
- **译文必须可 GBK 编码；不可编码字符走回退表，绝不能跳过整条**：
  `・→·`（A1A4）、`≪→《`（A1B6）、`≫→》`（A1B7）、`♪→☆`（A1EE）、`〜→～`（A1AB）、`―→—`（A1AA）
  —— 「静默跳过」的后果是**原 SJIS 残留在文件里、在游戏内显示为生僻汉字乱码**（本作 39 条漏网即此类）。
- **GBK 显示的 EXE 侧处理**（本作实测 **165 字节常量补丁**，无需编译 DLL）：
  ① 字体字符集 `SHIFTJIS_CHARSET(0x80) → GB2312_CHARSET(0x86)` 3 处
     （2 处 `CreateFontA` push 立即数 + 1 处 `LOGFONTA.lfCharSet`）；
  ② 文本前导字节判定 `0x81-0x9F|0xE0-0xFC → 0x81-0xFE` **83 处**（4 连比较里的 `0x9F`/`0xFC`
     两个立即数改成 `0xFE`，共 162 字节）。
  补丁后：中文正确渲染，**GBK 化的日文（未翻译内容）也正常显示**。
- **文件名/路径含日文时，Windows 上可能是「SJIS 字节被误当 GBK 解码」的双重转码坏名**；
  用 `name.encode('gbk').decode('sjis')` 可还原。取磁盘真实字节用 `os.fsencode`（不要手打字符串）。

## 六、存档格式（GAMEDATA.DAT）

```
R 版：[u32 comp_size][u32 uncomp_size] + LZSS 流（无尾部）
原版：[u32 comp][u32 uncomp][10 字节附加块] + LZSS 流（流起点 0x12）
```
- 展开后：**每字节 1 条目**，`0/1 = 未解锁/已解锁`；索引 0 固定 `0x29`；
  「状态槽」自索引 331 起按 `i ≡ 1 (mod 5)` 排列。
- 解锁状态**全部在 GAMEDATA.DAT**，`APP_CFG.DAT` 无需替换。
- LZSS 解压器与 LPK 同源（同参数、同窗口模型）。

**素材提取经验（2026-09-17，亜衣线 55 场景实测）**：
- 脚本用 **ASCII 路径字符串**引用素材：`CHR\xxx.ELG`、`PIC\xxx.ELG`、`SE\xxx.OGG`。**BGM 不按名引用**（无 `BGM\*` 路径）→ 只能整包给或另做编号映射。

### 7.1.1 ⚠️ **社区密钥表可能有单字节错误——必须与 `gameinit.sob` 自述值交叉校验**（2026-09-19 实测）

**血泪案例**：`LPK-Keys.json` 中 `Ore-tachi ni Tsubasa wa Nai`（2009 原版）的 **`SE.LPK` 条目 `Key1` 写错了一个字节**：

| 归档 | 游戏自述（`gameinit.sob`） | 社区表 | |
| --- | --- | --- | --- |
| SYS / CHR / PIC / BGM / VOICE / DATA | 与社区表逐字节一致 | — | ✅ |
| **SE.LPK** | **`0x935AF6DE`** | **`0x9A5AF6DE`** | ❌ 差 1 字节 |

**症状极具迷惑性**：用错密钥解出的 582 个 `.ogg` **文件头损坏、`ffprobe` 报 `CRC mismatch!` / `Codec not found`**，
但**文件尾与其它源的同名文件逐字节一致**，且**归档索引解析完全正常**（582 条目全读出）。
实测损坏面仅 **90 字节**（76 字节落在偏移 17–268 的头部区 + 14 字节为已知尾部前缀）。

**机理**（解释了为什么只有头部坏）：`Key1` **只用于** `decrypt_content_1_first_256()`（内容区**前 256 字节**），
`Key2` 用于**索引**解密。Key2 正确 → 索引正常；Key1 错 → **仅内容区前 256 字节被解错**。
→ **凡是「索引能读、条目数对、但每个文件的开头都坏」的现象，优先怀疑 `Key1`。**

**正确做法（务必养成）**：**从作品自己的 `gameinit.sob` 取自述密钥，与社区表逐条交叉校验**。
实测偏移（原版 2009）：**`0x1594` 起、间隔 `0x88`**，每条为 `<u32 Key1><u32 Key2>`，顺序
`SYS / CHR / PIC / BGM / SE / VOICE / DATA`（**偏移因作品而异，请做健壮搜索，不要写死**）。
本项目实测 **6/7 命中**——**唯一不命中的那条就是错的**，正是它导致了 582 个音效不可播。

**交叉校验是零成本的**：只要出现「6/7」或「n-1/n」这种**差一条**的命中率，**几乎必然是该条写错了**，
而不是「该作品密钥不匹配」。**不要**因为「大部分命中」就跳过校验。

**修复方式**：**不要修改社区 `LPK-Keys.json`**（第三方文件）。在自研加载器里做**密钥覆盖表**
（本项目实现在 `工程\我们没有翅膀——格雷塔迦露德与柳木原\资源组\工具\lpk_media.py`）。

**路 A（首选，快）：密钥表就藏在 `gameinit.sob` 里。**
Prelude 实测：`解包\SCRIPT\gameinit.sob` 偏移 **0x1280** 起有 **7 条连续记录、间隔 0x88**，
结构为 `08 00 00 00 <aux1> 08 00 00 00 <aux2>`。**归档归属**由记录内 `0x018358xx` 指针链
的相邻差值确定——差值恰等于 `SYS.LPK\0`(8) / `CHR.LPK\0`(8) / `PIC.LPK\0`(8) / `BGM.LPK\0`(8) /
`SE.LPK\0`(7) / `VOICE.LPK\0`(10) / `DATA.LPK\0`(9) 的字节长度，按顺序一一对上。

```python
import re
d = open('解包/SCRIPT/gameinit.sob','rb').read()
print([hex(m.start()) for m in re.finditer(rb'\x08\x00\x00\x00(.{4})\x08\x00\x00\x00(.{4})', d, re.S)])
```

**路 B（独立交叉验证，不依赖密钥存储位置）：利用「索引明文首 4 字节恒为条目数 cnt」。**
索引密钥 `K` 满足 `u32(file, 8) ^ cnt == K`（cnt 为小整数，可枚举）。对每个候选 cnt 解出 K、
解密索引、检查解析是否自洽（条目名全为可打印 ASCII、扩展名与用途吻合、offset/size 落在数据区、
解出明文首部魔数正确：`.elg`→`ELG\x01/\x18`、`.ogg`→`OggS`、`.mpg`→`00 00 01 BA`）。
实测 SYS/CHR/PIC/BGM/SE 五个归档由路 B 独立解出的 K 与路 A 的值**逐位一致**；
DATA.LPK 因 prefix 长达 302 字节超出快筛上限漏筛，由路 A 补齐。

**注意**：`prefix` 是**归档级**字段（该归档所有条目共用的头部），读取时须前置还原。
副作用：条目声明的 `sc` 等于**含 prefix 的完整长度**，故输出 = `prefix + sc` 会让 OGG 在
EOS 页后多出 `len(prefix)` 字节（Prelude 实测 14 字节，4824/4827 个文件如此；解码器读到 EOS
即止，**无影响**），而归档末条目因 `min(off+sc, filesize)` 截断反而**没有**这 14 字节——
同一归档内两种结构并存属正常，不必"修"。

**各归档索引变体不同**：SCRIPT.LPK 可用自研 `lpk_patch`；素材归档须走社区 `lpk_extractor`
（`工程\我们没有翅膀R\工具\lpk_media.py` 是其封装，但 `GAME` 常量写死，换作须改）。

## 八、验证方法（照做即可复现）

1. **解包**：对每个 LPK 跑解包器，确认条目数与 EXE 内字符串提示量级吻合（本作 SCRIPT.LPK 446 条）
2. **压缩器**：`compress → decompress` 往返；再用**引擎自己的解包器**解你的压缩结果，逐字节比对
3. **补丁器**：全量「解码 → 重编码 → 写回 → 用引擎解包器再解」，要求**逐字节一致**
4. **实机**：把补丁后的 LPK 放进**游戏副本**（不动原件）启动，确认：
   - 无「スクリプト初期化ファイルのロードに失敗」→ 结构正确
   - 改动文本在屏幕上可见 → 文本链路打通
   - 注意此时中文可能因字符集未处理而显示为乱码——那是**字体/字符集层**的问题，不是结构问题
5. **乱码三成因（逐层排除，2026-09-15 实测总结）**：
   a. **字节层**——该串根本没被写入（构建器静默跳过）→ 原 SJIS 残留 → 生僻汉字乱码。
      判据：`现行字节 == 原版字节 且 非 ASCII`。构建器对任何跳过项都必须记账。
   b. **编码层**——译文含 GBK 不可编码字符（`・≪≫♪`）→ 先回退（见 §五）再等长化。
   c. **显示层**——引擎按 SJIS 解读 GBK → 打 EXE 字符集补丁（见 §五）。
      注意：仅当 a、b 两层都干净时，"全库残留扫描 = 0"才能作为无乱码的充分证据。

## 十、SOB0 内部结构、外挂式汉化路线与原生打包器（2026-09-17 增补）

> 来源：ISSUE-20260917-13 对《我们没有翅膀》本篇（2008）第三方简中汉化的只读侦察，全部经字节级实测 + 汉化源工程源码交叉验证。
> 记录：`工程记录\2026-09-17_对于我们没有翅膀本篇汉化资源构成的分析.md`；源工程副本：`工程\我们没有翅膀\参照\汉化源工程_ORE_TUBA_Chinese\`。

### 10.1 SOB0 内部结构（脚本 = 松散文件时同样成立）

- 头部（**精确布局见 §12.1；本行为早期粗读，已订正**）：`SOB0` + `u32 table_size` + 6 张表（各 `u32 条数 + 条数×8B`）+ `u32 strings_start` + `u32 strings_end`。
  `table_end = table_size + 8`、`header_end = 8 + 六表字节长 + 8`（实测 `s00_00.sob`：`534f4230 c8020000 15000000 …` ⇒ table_size=0x2c8、表条数 `21,6,0,4,55,0`、header_end=0x2d8）。
- **字符串并非就地内联**：脚本内有字符串指针表（汉化方源码称 `maps[4]`），引擎按 `lucifen.cpp` 的规则逐字节读串：
  `c == 0` → 跳 3 字节；`c ∈ {2,3}` → 跳 4 字节；否则读到 NUL。
- **剧情正文以 `$&` 定界**：`#<说话人>\<语音ID>$&<正文>$`（本篇全库 `$&` 出现 35,607 次 ≈ 3.56 万个文本槽）。按 `$` / `$&` 切分即可取正文，正文为 **Shift-JIS**。
- 名字与标签：`01 01 <u16 L 含 NUL> <data> 00`（§三「声明串」的规则在 SOB0 里同样成立，末字节必须 NUL）。
- 非 SOB0 的变体：本篇另有 `func_lib.sob`(SOB2)、`user_var.sob`(SOB1)、`config.dat`(CCI2)、`sob_init.dat`、`voiceinf.dat`(OGG)、`ll_app.inf`。**不要假设全库同一魔数**。

### 10.2 外挂式汉化路线：**一个 LPK 都不用改**（低成本、易回滚，优先考虑）

本篇汉化的做法（实测 + 源码双证）：

1. 把原版 `SCRIPT.LPK` 解包成松散脚本目录（**只读**），汉化方自己的 `pack.exe` 逐个生成译文脚本，写到外挂目录 `SCRIPT_CHS\`（= `SCRIPT_` + 语言码；繁体版为 `SCRIPT_CHT\`）。
2. 用 Detours 钩 `CreateFileA`：**父目录名 == `SCRIPT` 时，改开 `SCRIPT_CHS\<同名文件>`**（`patch/patch.cpp:110-112`）。
3. EXE 侧只改 `.rsrc`（RisohEditor 导入 rc 汉化 UI）+ 用 CFFExplorer 添一条伪导入 `ORE_TUBA_CHS.dll`，**`.text`/`.rdata`/`.data` 逐字节不动**（实测段级差异 0）。

**对我们的价值**：不必碰 LPK 的 LZSS/容器层，也就不受 §四「引擎解压器比社区实现严格」的约束；且**原版归档保持完整**，回滚 = 删外挂目录。代价是成品多一个 DLL 与一层文件重定向，且**未覆盖的脚本回落到原版日文**（本篇 `SCRIPT_CHS` 就漏了 15 个系统脚本）。

**外挂译文文件的结构**（自己写同类补丁时可复用）：保留原文件全部字节，**只改写字符串指针表**里需要翻译的项，令其指向**原文件长度之后**追加的 **GBK 串池**（NUL 结尾、8 字节对齐）；原日文串留在原偏移当死数据。实测本篇 397 个可解析脚本、改写指针 58,716 个，**无一指向日文**。
少数系统文件（`func_lib.sob`、`user_var.sob`、`scskip.sob`、`title.sob`、`title2.sob`、`ll_app.inf` 等）与该汉化方的 `text/packextra.py` 走的是**等长原位覆写**（日文被销毁、补 NUL），所以"外挂 = 原版串 100% 保留"**不是普适规律**（本篇全量实测 99.71%）。

### 10.3 原生打包器线索（比自研压缩器可靠，值得优先取用）

- 汉化源工程 `text/pack.py` 调的是 `.\lucifen\build\pack.exe <原版脚本> <译文> <输出>`——这是 **Lucifen 作者自带的 pack/unpack 工具**（对应 `READ_ME.TXT` 里的 `Lucifen Library & Tools Version 1.2.2`），能压缩，绕开 §四那个「社区工具不实现压缩」的坑。
- 仓库内附引擎源码 `text\lucifen\lucifen.cpp` + `CMakeLists.txt`，可自行编译；**该文件已抄录进本工作区**（见上方路径），是 LPK1/SOB0/CCI2 格式的权威实现，读结构优先查它，而不是猜。
- 后续遇 Lucifen 作品时：**先找原盘/安装介质里的 `Lucifen Library & Tools` 或该源码**，再考虑自研压缩器。

### 10.4 侦察陷阱（本次踩到，务必避免）

- **「汉化补丁备份」不一定备份原版**：本篇该目录 559 个文件与根目录**同名文件 md5 全部相同**，备份的是**汉化补丁自身**（不含任何 LPK 与原版 EXE），**不能当回滚依据**。判断"原版是否被改动"要回到时间戳 + 是否含 LPK + md5 三方互证。
- **别用 GBK 硬解来判断"是中文还是日文"**：SJIS 假名字节被 GBK 解码后**会变成合法的汉字区字符**（`あ`→`偁`、`た`→`偨`），看上去像中文串。可靠判据是：先按 cp932 解，**看有无平假名/片假名**；无假名时再按 GBK 解，看是否含中文高频功能字（的/了/是/我/你/不…）。**单独用 GBK 解码 + 目测汉字数会把整库日文误判为中文。**
- 同尺寸不同构建的 EXE 可能并存（本篇 `ORE_TUBA.EXE` 与 `免DVD补丁备份\ORE_TUBA.EXE` 同为 1,101,824 字节、差异 86.7 万字节）。**"未被汉化改动"与"等于零售原版"是两回事**，无原盘时不要下后一个结论。
- **并发会话**：本工作区可能同时有多个会话在操作同一个工作树。**动 git 前先 `git branch --show-current` 与 `git worktree list`**；需要提交时用 `git worktree add` 开独立工作树，不要移动共享工作树的 HEAD/索引（详见 `工程记录\2026-09-17_对于我们没有翅膀本篇汉化资源构成的分析.md` 的「风险、警示与未完成项」）。

## 十二、SOB0 剧本解码（命令层）：命令身份 / 控制串 / 参数换算（2026-10-06 增补）

> 来源：ISSUE-20261006-07（SOB0 首版解码器＋独立复核 R1/R2/R3）。主档 `资源组\逆向\_调研小结_第一波.md`（含复核订正）。
> 参考实现：`工程\我们没有翅膀——格雷塔迦露德与柳木原\编程组\工具\decode_sob0.py`（`--stats` 复现报告每个数字、`--check` 幂等复核）。
> §三 SOB0 段只解决**正文抽取**（`$&` 定界）；本节把解码推进到**命令层**。**TOB0 与 BGI 不适用本方法**（见 §12.5）。

### 12.1 容器与六表（精确布局，覆盖 §10.1 的粗读）

```
[0x00] magic "SOB0"/"SOB1"/"SOB2"（4B）
[0x04] u32 table_size
[0x08] 6 张表：各 = u32 条数 + 条数×8B
[table_end] u32 strings_start | u32 strings_end      ← header_end
table_end  = table_size + 8            （全量实测 482/482 成立）
header_end = 8 + 六表字节长 + 8
代码区 = [header_end, header_end + strings_start)，每 4 字节一字
串区   = [header_end + strings_start, header_end + strings_end)
```

实测 `s00_00.sob`：table_size=712(0x2c8)、表条数 `21,6,0,4,55,0`、table_end=0x2d0=table_size+8、header_end=0x2d8。

**六表值规则（全量实测）**：

| 表 | 值规则 |
| --- | --- |
| `maps[1]` | **立即数标记位**：单元 = 该字 **−1**。**恒等映射、值无独立信息**（2026-10-07 订正，见 §12.8） |
| `maps[3]` | **立即数标记位**：单元 = 该字。**恒等映射**；可作**命令身份的自带真值位**（旧述"绝对地址"**错误**，见 §12.8） |
| `maps[4]` | **代码地址 → 串偏移（还原表）**；值分两类：串区偏移（文本引用）/ 代码区偏移（跳转链） |
| `maps[2]` / `maps[5]` | 恒空 |

`word & 0xFFFFF` 是算好的 **VM 地址**；`(word & 0xFFFFF) − maps[4][addr]` 在同一文件内为常数 ⇒ **低 20 位不可跨文件直读**。

### 12.2 项流与元数表 BASE（★ 边界：不是无条件解码器）

不是扁平 opcode 流，而是**带 tag 的项流** `[tag][payload…]`，项字数 = payload 个数 + 1。

```
BASE = {00:2, 01:0, 03:1, 04:1, 05:3, 06:1, 08:3, 0C:1, 0D:0,
        13:0, 14:0, 17:2, 1E:2, 1F:2, 20:2, 28:2, 2C:3, 2E:0}   # 其余 tag 默认 1（缺省 2 字项）
```

- **记录边界对齐 99.343%**（全局锚点）；未对齐集中在**每个文件的末记录**，须**单独手工解码**。
- **刚性矛盾率（同口径，必须分开引用、禁止混报）**：**BASE 刚性 0.0323%** vs **E4 十 tag 表刚性 6.4233%**（同批 367 文件）。另有「全库刚性 1.16%/2.46%」「剧情集自适应 0.0198%」两口径——**四个口径不是同一量**。
- **不是无条件解码器**：约 6.43%（E4 十 tag 口径）项首仍落在引用字上，且**从首个矛盾点起累积漂移** ⇒ 必须带「**首个矛盾点检测 + 局部回退**」。
- **BASE 是否为正确文法，不影响事件表**：事件由独立的**命令节点探测** + `[08][arg]` 2 字实参模型产生，与 BASE 的 `08` 读法无关（`08` 元数 `payload=3`/`=1` 两种读法均自洽，**未裁**）。
- `0xFFFFFFFF` 是 **`08`/`2C` 的空操作数（null 指针）**——**不是哨兵、不是 −1 指令**；它**从不作为 tag**。
- `04` 的 arg0 恒为 32 位立即数；`1F`/`20` **各吃 2 个载荷字**（故「REF 前一个词＝tag」在这两处必然误判）。
- 个别文件代码区含**数据数组**（非纯指令流）；`maps[4] ∪ maps[0]` 是全部 `0x018` ref 的精确二分（少数文件例外）。

### 12.3 命令节点形态与 V（命令标识；**⟦订正见 §13.4：`V` = op `0x04`（CALL）的操作数 = func_lib 子程序入口⟧**）

### 12.4.1 时间参数（ms）：字节定位与「命令族」映射（★ 已解出，2026-10-07 订正）

`chr_anime` 命令节点（某批实测 `V ∈ {0x18b74（ot/otr）, 0x15bac（otp）}`，`argc == 4`）的实参序
（按解码器 `node_args`）＝ **`[flag, ms, ctrl, slot]`**，故 **时间 ＝ `args[1]`、单位毫秒**；
`PSV :Time(帧) = round(ms × 0.06)`。

**★ 通则（必须遵守）：ms 落在哪个实参位「因命令族而异」，`V` 数字「因源而异」——
必须按源各建 V →（命令族, ms 位）表，绝不可对全命令统一取 `args[1]`。**

**字节定位**：命令节点尾为 `[04][V][0C][k][03][空串REF]`（与 §12.3 同形），`argc = k ÷ 4`，
**第 p 个实参 = 节点 `[04]` 字之前第 `i-1-2p` 个字**；⇒ **ms 字 = 控制串字 + 2**（文件偏移 = 控制串偏移 + 8）。

**实测族表（★ 示例：出处是某一批本作数据，别的作品 / 别的源必须重建，不得照抄位号）**：

| 命令族 | ms 位 |
| --- | --- |
| `chr_anime` | 1 |
| `bg_zanime` | 1 |
| `bg_anime` | **4**（ot 与 otr 两源均有此族） |

**边界**：PC 侧能恢复约 **96–99%** 的时长（余下为移植端改写、PC 侧无携带者）；
**未登记的命令族一律不写时间列**——**空列 ≠ 无时长**，只表示本批未定位到该族的 ms 位。

**四路独立证据（可作方法论范例）**：① 控制串锚定；② 同文件差分（取「只改时间」的最小差分对）；
③ 金标反查；④ 跨文件差分。另有第二人以重写脚本独立复算。

⇒ **做任何「位定位」之前，先确认取样没有被过滤器偏向**（先看样本的 seq 任务数分布）。

### 12.4.2 「无唯一事件」命令的定位（★ 订正 §12.5 旧结论，2026-10-07）

### 13.1 VM 总述

Lucifen 的脚本执行层是一个**栈式字节码 VM，恰 47 个 opcode**（`0x00..0x2E`）。

| 项 | 值（本实测 build） | 证据 |
| --- | --- | --- |
| **VM 主循环（入口）** | **`VA 0x433650`**（`int __thiscall run(ctx)`） | `0x433675 eax=[esi+8]; ecx=[eax]; lea edi,[eax+4]; [esi+8]=edi; jmp [ecx*4+0x433B54]` |
| **opcode 分派表** | **`VA 0x433B54`**，**47 项**（op `0x00..0x2E`） | 全 exe **唯一**一张 47 项 indexed `jmp` 表（其余 44/52/64/66/75/35/23/19 等项者均为 handler 内部 selector switch） |
| **VM 上下文 `ctx`** | **脚本管理器 `+4`**（vtable `0x4EDF34`） | `sub_4252F0`：`lea esi,[edi+4]; mov ecx,esi; call 0x433650`（edi=manager）；管理器子 ctor `0x422200`：`lea ecx,[esi+4]; call 0x433440` |
| **唯一调用者** | `0x4252F9`（在场景调度器 `sub_4252F0` 内） | `xdis --callers 0x433650` → 仅 `0x4252F9` |
| **管理器单例** | `[app+0x19C8]`（app 指针 `[0x503248]`） | 构造 `malloc(0x404)`→`call 0x4154D0`→`[app+0x19C8]=eax`（`init 0x414130`） |
| **帧循环（3 处）** | **`0x4012EC` / `0x401348` / `0x401AF3`** 均以 `ecx=[app+0x19C8]` 调调度器 | `callers(0x4252F0) = [0x4012EC, 0x401348, 0x401AF3]` |

**`ctx` 字段布局**（由 `0x433440`(ctor) / `0x4335A0` / `0x4335B0` / `0x4335F0` / `0x433610` / `0x433630` 直读）：

| 偏移 | 名 | 语义 |
| --- | --- | --- |
| `+0x00` | vtable | `0x4EDF34` |
| `+0x04` | stack_buf | 操作数栈缓冲（`0x4335B0` malloc，`0x4000` 字 = 64 KB） |
| `+0x08` | **pc** | 执行指针（装载时 = 模块缓冲基址，`0x4335A0` 写） |
| `+0x0C` | **sp** | 操作数栈顶指针 |
| `+0x10` | **VM 返回值寄存器（RETVAL）** | **RETVAL（返回值寄存器；与 `pc`/`sp` 并列的第三个 VM 寄存器）**。**无 ctor/装载写入点**（ctor `0x433440` 不清 `+0x10`）；唯一写入点 = op `0x02`（`0x4336B7 mov [esi+0x10],ecx`，全库 **197** 次）；读点 = op `0x03`（`0x4336C3 mov ecx,[esi+0x10]`，全库 **113861** 次）。旧候选「op 0x02 的分支/续行目标寄存器」**已证伪**（op 0x02 操作数 197/197 皆立即数，非地址）。详见 `语义未决两项_说明.md` |
| `+0x14` | hook | 每步回调对象 |
| `+0x18` | hookOn | 回调开关（= `mgr+0x1C`） |

### 13.2 解释器主循环（5 条指令，逐字）

```asm
0x43366B  mov ebp,4                            ; 字长
0x433670  mov ebx,0xC                          ; 3 字
0x433675  mov eax,[esi+8]                      ; pc
0x433678  mov ecx,[eax]                        ; op = *pc
0x43367A  lea edi,[eax+4]                      ; edi = 操作数区
0x43367D  mov [esi+8],edi                      ; pc++
0x433680  jmp dword ptr [ecx*4 + 0x433B54]     ; ★ 47 路分派
```

**取节点规则**：`op = *pc++`（线性 4 字节字流，无双字对齐、无长度前缀）。

### 13.3 opcode 语义表（关键子集）＋ 参数模型

**关键 opcode**（`va` = 该 op 的 handler 地址；`*x` = 取 x 指向的字）：

| op | handler VA | 操作数字数 | 语义 |
| ---: | --- | ---: | --- |
| `0x02` | `0x4336A1` | 1 | **带值返回**：`a=pop; if(a==0) VM-return; RETVAL=*op; pc=a`（全库 197 次；旧值 49 系遇 `0x07` 即截断所得） |
| `0x03` | `0x4336C1` | 1 | `*op = RETVAL`（把 RETVAL 写入给定槽；全库 113861 次，旧值 113166 系遇 `0x07` 即截断所得） |
| `0x04` | `0x4336D2` | 1 | **CALL**：`push(pc_after_op); pc = *op` |
| `0x05` | `0x4336EC` | 3 | **CALLNATIVE**：`*op2 = op0(op1)`（`op0`=handler 指针、`op1`=实参指针、`op2`=结果存放） |
| `0x06` | `0x433716` | 1 | **JMP**：`pc = *op` |
| `0x07` | `0x433720` | 变长 | **表跳（跳转表／表驱动的多路分支）**：表**内联**于 idx 字之后（表基 = idx 字 + 1），`pc = table[idx]`，哨兵 `0xFFFFFFFF`。**index 由运行期 store 写入**（恒在「站点 −3」：`op 0x23` 21 站 / `op 0x20` 3 站），**磁盘上的 `0` 只是占位、从不作索引**；全库 **6 文件 / 24 站**（gallery 10 / func_lib 9 / main 2 / eyecatch·scskip·ssskip 各 1），**场景脚本 0 站**（已结项） |
| `0x08` | `0x43372E` | 1 | **PUSH**：`push(*op)` |
| `0x0C` | `0x433786` | 1 | **ADDSP(-k)**：`sp -= *op`（**丢弃 k 字节实参**） |
| `0x1E` | `0x433945` | 2 | **JZ**：`if (op0 == 0) pc = op1; else pc = op0 + 8`（**⟦订正（ISSUE-20261008-04 B4 R7）⟧** handler `cmp dword ptr [edi],0` **直接比较操作数字、不解引用**；旧记号 `if (*op0 == 0)` 已改；实测操作数0 全为非表立即数） |
| `0x28` | `0x433A51` | 2 | `*op1 = sp - op0`（**取栈槽地址**——原生调用实参结构的搭建） |

> 47 个 opcode 的**全表**（含 `0x00`=HALT_OK、`0x01`=RET、`0x0A..0x2E` 的算术/比较/内存 op）见
> `执行模型.md` §4.4；**操作数字数表以该表为引擎真值**（不要用数据侧反推的 `BASE`，见 §13.7/§13.8）。

**参数模型**（命令节点 `[04][V][0C][k][03][REF]` 的引擎消费）：

| 字 | op | 引擎动作 |
| --- | --- | --- |
| `[08][arg]` | `0x08` PUSH | `arg` 压入操作数栈。**⟦订正（ISSUE-20261008-04 B4 R6）⟧** **`0x08` = `push(操作数字)`**，操作数**可为立即数**；旧述「`arg` 是 maps[0/3/4] 引用字（重定位后为指针）」**过强**——实测 `arg` 为引用字者仅 **25.86%**（本作） |
| `[04][V]` | **`0x04` CALL** | `push(返回地址)`，`pc = V`（V 重定位后 = `func_lib_base + V`，即**命令实现体**） |
| `[0C][k]` | `0x0C` ADDSP | 返回后 `sp -= k` ⇒ **丢弃 k 字节实参**；**`argc = k / 4`** |
| `[03][REF]` | `0x03` | `*REF = RETVAL`（尾槽落点；`ctx+0x10` = RETVAL，即「取返回值」） |

- **实参个数** = 节点 `[04]` 前**连续的 `[08]` 项个数**；`k` = 实参总字节数 = `4 × argc`。
- op `0x05` 的三操作数 `(fn, arg, dest)`：`fn` = handler 下标（∈ `maps[1]`）、`dest` = 结果落点（∈ `maps[0]/[3]/[4]`）。
  **⟦订正（ISSUE-20261008-04 B4 R5）⟧** 旧述「`arg` **是指针**（重定位后的引用字）」**已删**：实测 `op 0x05`
  的第 2 操作数**全为非表立即数**，handler **按值 `push` 该字、不解引用**。
- **控制串**（`c`/`l<2`/`!l`/`_` 等）**不是 opcode，引擎不解释它**——它是普通字符串操作数（`maps[4]` 引用），
  「语义」全部由 handler 的 selector 与字节决定（`decode_sob0.CTRL_ROLE/CTRL_STRINGS` 是启发式，**不得作引擎真值**）。

### 13.4 ★ 关键结论：`[04][V]` 是 CALL，`V` 是 func_lib 子程序入口

- **`[04][V]` 中的 `V` = op `0x04`（CALL）的操作数**，即 **`func_lib.sob` 代码缓冲内的一个子程序入口**。
- 装载期，装载器 **`sub_424D30`**（VA `0x424D30`）逐项遍历 `maps[3]`，做 **`code[V字偏移] = V + [mgr+0xD4]`**；
  `[mgr+0xD4]` 在 `func_lib` 装载时（`0x424EEB`，`is_lib=1`）被赋为 **func_lib 代码缓冲基址**。
  ⇒ 磁盘上的 `V` 是**偏移**，装载后该字变成**运行期真实指针**（`func_lib_base + V`），`op 0x04` 直接跳过去执行。
- **引擎内没有「命令名 → 实现」的表、也没有命令名分派 switch** —— **命令名根本不在 exe 里**
  （这就是「exe 内搜 `CharacterOpen`/`BgmPlay`/`SePlay` 等命令名 0 命中」的成因；现用名字是从 PSV `:Tasktype` 借来的）。
- **不要与 opcode switch 混淆**：引擎**有**一张 47 路 **opcode** 分派表（`0x433B54`）；缺的是**命令名**层面的表。

### 13.5 六表在引擎侧的用途

装载器 `sub_424D30` 的六个重定位循环（A..E + 零检查）各自把「引用字」改写为运行期指针，去向 = 对应向量 begin：

| 表 | 重定位循环 VA | 改写式 | 去向对象 | 语义 |
| --- | --- | --- | --- | --- |
| `maps[0]` | `0x424E25` | `code[off] = [mgr+0x58][value].f0`（12 B/条） | **user_var 变量记录向量** | **变量槽引用**：`value` = 变量下标（0..N−1）→ 变量存储地址（由 SOB1 装载构建） |
| `maps[1]` | `0x424E4A` | `code[off] = [mgr+0x38][value]`（4 B/条） | **原生 handler 指针向量** | **原生函数引用**：`value` = handler 下标，由 **op `0x05`** 调用的被调函数 |
| `maps[2]` | `0x424E6C` | `code[off] = [mgr+0x48][value].f0`（12 B/条） | 具名符号向量 | 具名符号引用（仅 3 个内建：`retTgsExp`/`ScriptBootFlg`/`retAppProc`；`sub_4228F0` 注册） |
| `maps[3]` | `0x424E91` | `code[off] = value + [mgr+0xD4]` | **func_lib 缓冲** | **func_lib 代码偏移**（命令实现体入口）；**重定位位图表** |
| `maps[4]` | `0x424EB5` | `code[off] = value + ebx`（ebx = 本模块缓冲基址） | 本模块缓冲 | **本模块内串/代码偏移** |
| `maps[5]` | `0x424ED3` | 计数**必须 = 0**，否则返回 3 | — | 保留 |

- `[mgr+0x38]` 是**向量 begin**（元素 4 B），由注册器 **`sub_422730`**（`std::vector::push_back` 内联）构建；
  注册形态 `push <handler_VA>; mov ecx,esi; call 0x422730`。
- `[mgr+0xD4]` = func_lib 缓冲基址（取值器辅助函数 `0x4183B6`，读 `[ecx+0xd4]`；**不在 handler 注册表内**，M4 已证）；`[mgr+0xD8]` = 当前场景缓冲基址（取值器辅助函数 `0x4183A8`，读 `[ecx+0xd8]`）。
- **`maps[0]`（变量，0..N−1）与 `maps[1]`（handler 下标）是两套独立编号空间**（上一轮曾混为一谈，已订正）。

### 13.6 SOB0 / SOB1 / SOB2 三条装载路径

| magic | 用途 | 装载函数 | 引擎侧处理 | 证据（本 build） |
| --- | --- | --- | --- | --- |
| **SOB0** | 场景脚本 | `sub_424FA0`（按名） / `sub_424D30` | `cmp dword[eax],'SOB0'` → `sub_424D30(is_lib=0)` | `0x42502B cmp [eax],0x30424F53`；`0x4250E1 call 0x424D30` |
| **SOB2** | 共享库 `func_lib.sob` | `sub_424460`（初始化内） | `cmp dword[eax],'SOB2'` → `sub_424D30(is_lib=1)` | `0x4248B2 cmp [eax],0x32424F53`；`0x4248E6 call 0x424D30` |
| **SOB1** | 变量表 `user_var.sob` | `sub_424460`（**内联，不走 `sub_424D30`**） | 见下 | `0x424630 cmp [ebx],0x31424F53` |

- SOB0 / SOB2 **共用容器布局**：`magic(4) | u32 table_size | 6 表（各 u32 count + count×8B (key,value)）| u32 ss | u32 se | 代码区 | 串区`；
  `header_end = 8 + table_size + 8`。
- **`is_lib` 分流**（`0x424EE3`）：`is_lib=1`（func_lib）→ `[mgr+0xD4] = 本模块缓冲基址`；`is_lib=0`（场景）→ `[mgr+0xD8] = 本模块缓冲基址`。
  **只有 `is_lib=0`** 才继续 `0x424EFF call 0x4335A0`（`ctx.pc = ebx`）与 `0x424F06 call 0x4335F0`（压哨兵 0）
  ⇒ 「装载」与「可执行」是同一件事（装载完即可执行）。
- **SOB1（`user_var.sob`）不是容器**：走 `sub_424460` 内联段（`0x424630..`）——`u32 payload_len` → 3 份 `malloc` 副本
  （`[ebp+0x74]/+0x98/+0xBC`）→ 读 `u32 变量数` → 建 **N 条 12 B 记录**（`[mgr+0x58]` 向量）→ 回填「变量槽指针」。
  变量数 **N** = SOB1 头部声明的变量数（`[mgr+0x58]` 向量的 `value` 域为 `0..N−1`，与声明的条数互证 ⇒ `maps[0]` 的 `value` = **变量下标**）。
  （**变量条数 / `header_end` 随作品而异，属作品层**；本节只写机制。）

### 13.7 静态可达性结论（反汇编层 100%）

### 13.8 ★ DOS / DON'T 与坑

1. **DON'T：不要把 `BASE` 当引擎真值。** `decode_sob0.BASE` 只是**文档化启发式**（由数据侧反推），
   6 个 tag（`0x00/0x08/0x0D/0x13/0x14/0x2E`）与引擎不符；例如 `BASE[0x08]=3` 真值是 **1**（`[08][arg]` 恰 2 字）。
   引擎的长度真值**只存在于 `0x433B54` 各 handler 的代码里**（`.rdata/.data` 内**没有**「tag→长度」数据表）。
2. **DON'T：不要把 `V` 跨 build 搬用。** `V` 是**每 build 组本地**的：同一系列内高度稳定（`ot` 2008 与 `otr` 2011：剧情口径 `otr ⊆ ot`），
   跨 build 组则不相交（`ot` ↔ `otp`）。**可移植的是「命令角色/族」，不是 `V` 的数字。**
3. **DOS：`func_lib` 的命令实现体 —— 边界可判**（**⟦订正（ISSUE-20261008-04 B1/B2，2026-10-08）⟧**；
   旧述「func_lib 没有长度字段 ⇒ **节点边界不可判** / 串只能读窗口首串」**已作废**）。
   - **可判**：用**引擎真值 opcode 宽度表**（§13.3 全表；`op 0x07` **表感知**整段跨过）从 0 线性走查，
     并要求**所有控制流目标落在解出的指令起点上**，`func_lib` 整个代码区即被**唯一**切成**基本块**；
     再沿**过程内**控制流（`0x1E`/`0x06`/`0x07` 表/直落；`0x04` 不展开、`0x00/0x01/0x02` 终止）做可达闭包
     ⇒ **命令实现体 = `core` 块 ＋ 过程内可达的 `exp` 块**。
     **本作实测**：非法 op 位置 **0**、走查终点**精确落在 `ss`**、基本块 **1,519** 个、命令实现体 **120** 个
     （确定 120 / 候选 0 / 未定 0）。
   - **仍不可判的只剩一件**：**静态不可达区**（不在任何实现体内、且无静态控制流边可达）的**归属**
     —— **本作实测 17.34%**；两候选解释（**库内未被本作调用的命令实现** / **超出本模型的控制转移机制**）
     **均未证、不取一**。
   - **DON'T：不要再用「窗口」判归属。** `[V, nextV)` 区间归属**不可用**（本作实测：`V=0x1C43C` 的过程
     **恰为 `[V, nextV)`** ⇒ 旧读「V 体可跨过下一个 V」是**窗口读数假象**）；旧口径「多窗口首串一致才可采信（否则报与下一个 V 的距离）」
     **已作废**——改判**该串引用落在哪个过程内**（`core` / `exp` / 不可达区）。窗口法会**错归邻节点串**。
   - **口径教训（跨作品成立）**：**「遇变长 `op 0x07` 即截断」的走查会系统性低估计数**（`0x07` 是变长跳转表
     `[07][idx][t0..tN][0xFFFFFFFF]`）。**凡统计走查，必须先声明是「表感知」还是「截断」口径**：
     本作实测同一语料下「完整走到代码区末尾」为 **412/412（表感知）** vs **406/412（截断）**，
     多个 op 的计数随口径变化（**命中率结论不变、计数变**）。
4. **DON'T：不要再从 exe 里找命令名字符串。** 命令名不在二进制里（见 §13.4）；要命名只能逐个反汇编 handler 或靠外部金标。
5. **`OT_PREDE.EXE`（前奏诗）被 `.settec` 加壳**（`.text` 熵 `7.763` vs 正常编译的 `6.529`），**静态不可用**；
   需要「第二个构建」对照时，改用「同引擎另一作品的数据侧交叉验证」。
6. **控制串角色表（`CTRL_ROLE`/`CTRL_STRINGS`）是启发式**，只用于对齐外部金标，**不得作引擎真值引用**。
7. **★ 一种高频命令形态：`[08][arg] / [04][V] / [0C][04] / [03][REF] / [1E][slot][target]` = 「文本行推进门」**
   （**⟦新增（ISSUE-20261008-04 B2，2026-10-08）⟧**，**本作实测**）。
   - 机制：`[03][REF]` 把 `RETVAL` 写进**下一条指令的操作数槽**（REF 位移恒 **+8**），而 `op 0x1E`（JZ）的
     `op0` **按地址读**（`cmp [edi],0`，**不解引用**）⇒ **自改写的条件分支**：
     `if (V(arg) == 0) 跳到 target（下一句）else 落空 RET（挂起，等推进）`。返回非 0 = 「本句未结束」。
   - **四条可失败不变式**（本作实测全成立）：尾随 op 恒 `0x1E`(JZ)、实参 ∈{0,1}、尾 REF 位移恒 **+8**、自改写分支。
   - `ISSUE-20261007-09/10` 登记的形态族 `[04][V][0C][04][03][REF→代码区]`（尾 REF 位移恒 +8）
     **主导形态即此**（本作实测 **99.98%**）⇒ 原「带一个内联代码块的命令（语义未定）」表述**作废**。
   - ⚠️ 「与相邻的文本显示调用（`CALLN h462`）配对」这一关系**依赖前后搜索窗口宽度**
     （放宽窗口即由 0.99957 → 1.0000）⇒ **是窗口口径产物、不得当结构律**。

### 14.1 `.tob`（AfterStory 剧情字节码）记录级文法 —— **可整份解析**

- 记录头：`5b 20 <op> 00 00 00 01 <u32 L>`，**记录长 = L + 7**；body ＝ `<u8 count>` ＋ 项流。

### 14.2 立绘**位置**：原生 token DSL（引擎侧）

- 入口链（本作 exe VA）：`sp_move` 实现 `0x4033A0` → token 解析器 `0x402970` → 方位处理器 `0x402B42` → `call [obj_vtbl+0x38]`。

- **坐标空间**：内部 **640×480**，显示 ×1.25 → 800×600；**折算任意目标画布按同一比例**（1920 画布 ＝ ×3：`c→960`、`l→504`、`r→1416`、步长 `25→75`）。

### 14.3 立绘**层序**：与「槽号」相关，但**证据有限**

## 2026-10-11 源引用、直接控制流与原码ABI分层

通用Lucifen方法：控制流探针需明确 decoder 的条件跳分类，保留间接缺口与预算，按“源引用→静态路径→原码动态 ABI 证据”分层，不把静态候选当运行事实。系统 API 优先实际原 32 位实现，记录宿主版本、绑定方式及未走 loader 的限制。对象构造、类型 cast、函数接口、状态与像素应一起验证，不把单个组件当成全作结论；对不可行条件、返回 stub、状态位和通知 sink 保留边界，先验证可复现只读宿主，再逐层外推，并标注证据等级。

### Lucifen 方法：受限令牌夹具分层验证
1. 分层判定：线程 impersonation PASS 与 primary 进程创建 PASS 分开，不互相推断。
2. 正控最小化：仅对显式 grant 的专用临时目录 CREATE_NEW 16字节全零 canary(不能0字节)，比对前后原文件 SHA256。
3. 负控齐全：无 ACL 目录、已有 canary、工区外输出必须失败且不生成/不覆盖。
4. 证据先行：记录 flags、SID 授予方式、退出码；未记录的根因与 wait 值不猜、不归咎特定 DLL。
5. 结果暂存待主代理应用，不用参考 SDK 猜根因。

新目录继承的 Deny 仅 DeleteSubdirectoriesAndFiles，并非 Execute；WMI 已登记 360 安全卫士与 Defender，Defender 未找到匹配检测，故不归咎 360、不宣称 AV 误报。未修改或禁用安全产品，未改名重试逃避拦截。下一步需真实 startup 与受控写入环境，Windows 具体验证原作前置仍未满足；源码仅为受控 fixture，非生产还原层。

## 2026-10-11 参数位宽、别名与未绑定分配器

返回状态按各函数实测契约保留：BOOL、状态码、指针各有语义，勿一律 bool 化；本批 0 成功不等于 bool 失败。Unicorn 客体执行不启动原程序，但工具回调与宿主代码仍有主机能力，非 OS sandbox。写参数须辨全字与低字节；输出槽复用 caller 栈；cast 与 alias 会改变绘制目标。停在 allocator 不可填 fake 返回；静态缺口不等于全剧情已验证。勿无证推广至所有引擎或角色。
