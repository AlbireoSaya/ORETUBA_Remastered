## 四、资源引用解析规则（重构的地基）

脚本里的资源引用有一套**混合寻址**，规则如下。**这五条已逐条实测验证**，是重构时必须照抄的解析逻辑。

### R1 · 脚本文件本身
`SCRIPT.cpk` 内 499 个条目，文件名即逻辑名（`M01_01`、`adv.txt`、`chr012.txt`…）。本线需要的 31 个 + 2 个全局表见 §二。

### R2 · `:Texture N` —— ⚠️ **不是归档索引，是"场景内局部编号"，必须按注释里的名字解析**

这是最容易踩的坑。实测：**1,330 个 Texture 编号中有 602 个在不同脚本里对应不同的名字**（例如编号 `588` 在 `CGMODE` 里是 `ASU01`、在别的脚本里是 `ST_KAZ06G`）。所以编号是场景局部的，**不能按编号去索引归档**。

构建工具在把符号名替换成数字时，**把结果名留在了注释里**，这就是可靠索引：

```
:Texture	533	// EF01				→  CG.cpk\ef01.png
:Texture	165	// ST_ASU01			→  CHR.cpk\ST_ASU01.png
:Texture	0	// BG_BLACK			→  ETC.cpk\black.png
```

**做法**：抓 `:Texture N` 后面的 `// NAME` 与 `<<NAME>>` 两种形式，得到 NAME，再在 `CG.cpk` / `CHR.cpk` / `SystemData.cpk` / `ETC.cpk` / `media\img\logo\` 里按文件名（大小写不敏感、忽略扩展名）查找。

**覆盖率实测**（口径见 `工具\asset_refs.json`，可复跑）：全作共 **1,330 个不同的 `:Texture` 编号**，其中 **602 个**在不同脚本里对应不同的名字——这正是"编号是场景局部"的直接证据。全部 `(编号, 注释名)` 去重后共 **1,909 个不同的注释名**，其中 **1,897 个（99.4%）** 能在归档里按名找到实际文件。本线的 **364 个资源名 100% 命中**。

**12 个找不到的注释名**：`BG06` `BG06A` `BG06B` `BG07` `BG07A` `BG07B` `BG15D` `BG42D` `BG63` `BG69D` `NAR11` `NULL`。原因已查明：其中 6 个（`BG06*`/`BG07*`）在归档里是**拆成 8 片存储**（`BG06_0.png`…`BG06_7.png`，脚本引用基名），其余是注释里遗留的旧资源名。**这 11 个（`NULL` 除外）在美咲线的引用数均为 0**，故本交付集不受影响。

**残留未解**：`adv.txt` 的 `[Texture]{ :TextureList "texturelist.txt" }` 指向一个**全局纹理表文件 `texturelist.txt`，但该文件不在 `SCRIPT.cpk` 里**（499 个条目已全部核对，不存在）。因此"编号 → 全局纹理表项"的原始机制无法从资源侧复原 —— 但对重构无影响，因为按名字解析已经完整。

### R3 · 立绘 `:Number` 元组 —— 同样按注释名解析

```

	:Number		12,0,1,7,0	// キャラ、ポーズ、服装、表情、サイズ	//	置換しました<<st_mis01g>>

**实测：美咲线全部 1,323 处 `:Number` 行 100% 带 `<<...>>` 注释**，因此立绘解析无遗漏。

- **没有引号转义**：文本内的引号是全角 `”`，不会破坏解析；含裸 `"` 的消息实测为 0

## 八、重构建议

### 8.1 目标是"Windows 上可玩的美咲线"时，推荐路线

用 **Ren'Py**（或任何现代 VN 引擎）重建，而不是去改 PSV 原版：

| 维度 | 本线资源是否够用 |
| --- | --- |
| 剧本文本 | ✅ 全在（31 个 Shift-JIS 纯文本脚本），且结构清晰、**无长度约束** |
| 图像 | ✅ 376 张明文 PNG，**零转码**可用 |
| 音频 | ✅ 1,837 个 OGG，Ren'Py 原生支持 Vorbis |
| 影片 | ✅ 2 个 MP4（建议再转 WebM/VP9+Vorbis，因为 Ren'Py **不支持 H.264/AAC**） |
| 说话人 | ✅ `adv.txt [Name]` 362 条，可直接翻译 |
| 分支/旗标 | ✅ `[Flag]`/`[GlobalFlag]` 表在 `adv.txt`，`scn.txt` 给场景号 |
| 中文显示 | ✅ Ren'Py 换 CJK 字体 + `gui.language="japanese-loose"` 即可 |
| UI | ⚠️ 需补提（§七 第一行） |
| 演出还原度 | ⚠️ `EffectQuake`/`Flash`/`EyeCatch`/`InOut_Act` 等 20 余种效果需按字段名 + 截图反推，**会有损失** |

**工作量主体 = 写一个 `Task → .rpy` 的转换器**。因为源是结构化文本而非字节码，这是"文本对文本"的转换，可增量验证；资源侧几乎无障碍。

### 8.2 写转换器时的注意事项

1. **资源解析一律走名字，不要走编号**（§四 R2/R3 的坑）。
2. **`SceneJumpDialog`/`MessageSwitch_Tag` 的 `:Text` 不是台词**，别混进对话流。
3. **`:Message` 里的 `\n` 是强制换行**，要转成引擎的换行语义。
4. **`NextScene` / `Jump_Tag` / `FlagSwitch_Tag` / `scn.txt`** 构成跳转与分支，需一并转换，否则剧情走不下去。
5. **不要静默丢文本**：按 4,904 条 Message 逐一转换，数量必须对得上（差额即漏译或解析失败，要显式报错）。
6. Voice 名（`misaki_147`）与 `:Name` 编号是**两套**身份，分别对应语音文件与显示名。

### 8.3 若目标是"汉化 PSV 原版"

则本次资源之外还需：解密 `eboot.bin` 的 SELF 层（Vita3K 用 klicensee 可解，见前一份记录）+ 改造文字渲染路径 + 回封 CPK（`cricodecs` 支持 `--build/--replace`，但**回封可行性尚未实测**）。**这条路的主要风险不在资源，而在引擎。**

# 0) 前置：解密 PFS（密钥取自 sce_sys/package/work.bin 偏移 0x50）

# 1) 解出 SCRIPT.cpk 的 499 个脚本（→ 脚本解包/）
PYTHONPATH=工具/pylibs python 工程/我们没有翅膀PSV/工具/…   # 见 工具/ 内脚本

# 2) 收集本线资源引用（→ 美咲线清单/资源引用.tsv）
PYTHONPATH=工具/pylibs python 工程/我们没有翅膀PSV/工具/collect_misaki_assets.py \
  "工程/我们没有翅膀PSV/脚本解包" "工程/我们没有翅膀PSV/解密/PCSG00299/media" \
  "工程/我们没有翅膀PSV/美咲线清单"

# 3) 提取图像与脚本、生成音频清单
PYTHONPATH=工具/pylibs python 工程/我们没有翅膀PSV/工具/extract_misaki_assets.py \
  "工程/我们没有翅膀PSV" "工程/我们没有翅膀PSV/解密/PCSG00299/media"

# 4) 音频转码（详见 工具/美咲线过程脚本/extract_audio.py；ffmpeg 逐条 ADX/HCA → OGG）
# 5) 影片转码
ffmpeg -y -i ED_misaki.usm -c:v libopenh264 -b:v 1600k -c:a aac -b:a 192k ED_misaki.mp4
```

**注意**：`cricodecs` 的 C++ 读取器**不支持非 ASCII 路径**，必须先 `os.chdir()` 到 media 目录再用纯文件名 `C.load('CG.cpk')`。
