## 一、结论与依据

### 1.1 一句话结论

**把设计画布（primaryLayer）定为 1920×1080，脚本只写一套 1920×1080 坐标；窗口化时用 `setZoom(2,3)` 把同一画布缩到 1280×720 窗口，全屏时 `setZoom(1,1)` 原生呈现 1920×1080。**

### 1.2 为什么是「1920×1080 画布 + 2/3 缩放」而不是「1280×720 画布 + 放大」

| 理由 | 说明 |
| --- | --- |
| **2/3 是精确有理数** | 1920×1080 恰为 1280×720 的 **1.5 倍**，故 1280/1920 = **2/3**、720/1080 = **2/3**。krkrz 用**分子/分母**表示倍率正是为此（`setZoom(numer, denom)`），**无分数像素漂移**（若画布是 1280×720 而要放大到 1080p 则是 3/2，同样精确，但方向不同，见下条）。 |
| **向下缩放比向上放大安全** | 画布 1920×1080、窗口 1280×720 是**缩小**；反向（1280 画布放大到 1080p）是**放大**。缩小时信息不增加、边缘不糊化；放大时会把 720p 的像素插值成 1080p，**文字与线稿先糊**。 |
| **文字在 1080p 原生渲染** | 文字密集的 AVG 里这是实质画质收益：字体栅格化发生在 **1920×1080 画布**上，窗口化时整幅缩到 1280×720（锐），全屏时 1:1 呈现（原生 1080p 锐）。若反过来以 720p 为画布再放大到 1080p，**文字会糊**。 |
| **与既有 2× 超分素材天然匹配** | 见 §四：素材已是 2×（≥1.5×），画布提到 1.5 倍**不需要重做素材**。 |

**⚠️ 实测补充（2026-09-20，`ISSUE-20260920-18` V3 实机验证）**——上表第 3 行「文字在 1080p 原生渲染」原为**原理推论**，本轮以真实中文台词（微软雅黑）四臂对照实机量测，**推论成立且已量化**（详细数据见 §7 的 V3 行）：

| 对比臂 | 画布 / 显示 | 屏幕字号 | 边缘梯度能量（第 2/3/4 行） | 观感 |
| --- | --- | --- | --- | --- |
| **全屏：1920 原生 vs 1280 放大** | 1920 画布全屏 1:1 / 1280 画布全屏 ×1.5 | 均 36 px | **54.68 / 44.14 / 50.28** vs **46.28 / 37.11 / 42.57** | 1920 原生**梯度能量高 18–19%**，目视**明显更锐**；1280 放大版**笔画更细、更虚** |
| **窗口化：1920 下采样 vs 1280 原生** | 1920 画布 + 1280×720 窗口（2/3） / 1280 画布 + 1280×720 窗口 | 均 24 px | **74.20 / 60.40 / 66.82** vs **79.03 / 63.39 / 72.00** | **无锯齿、无断笔**，字形完整；但下采样版笔画**略细略淡（梯度能量低 5–8%）** |

- **结论**：方案「1920 画布 + 2/3 缩放优于 1280 画布 + 放大」在文字上**实测成立**（全屏路径收益显著）。
- **方案未提及的一条量化差异**：窗口化的 2/3 下采样会**轻微侵蚀笔画权重**（−5~8%），幅度不大（肉眼需并排对比才明显），但若 UI 组对字号/字重敏感，值得记录（**已登记为未决项 §十 U8**）。
- 证据：`子代理工作区\ISSUE-20260920-18\W_1080p验证\V3\`（`CMP_fullscreen_36px_line2.png`、`CMP_windowed_24px_line2.png` 及四臂 3× 裁切 PNG）。
- **方法论警示**：本项**第一次跑出来的结果是假的**（四组「文字」截图与画布导出全空白），根因见 §6.7 末「本轮返工登记」——**若当时直接出报告，会把「文字渲染正常」写成错误结论**。

> 「現バージョンの吉里吉里では、**拡大・縮小時に補間がかかるかどうかはグラフィックカードのハードウェアやドライバに影響されます。補間がかからないハードウェアやドライバの場合は、画質が荒くなります**」

同页另注：

> 「オプション次第では倍率変更ごとに使用可能なHWを調べるため、**このメソッドは拡大率を連続的に変化させて演出を行うような用途には適していません**」

→ **本方案的两条硬性推论**：① 缩放是否插值**不由我们决定**，故 §七 验证清单必须含「不插值硬件下的观感」一项；② **禁止用 `setZoom` 做连续倍率演出**（如逐帧缩放转场），需要此类演出时改用图层自身的 `setSize`/变换。

### 1.4 源码级佐证（本机 krkrz 1.4.0r2，`工具\krkrz\src\krkrz-1.4.0r2\`）

| 事实 | 源码位置 | 说明 |
| --- | --- | --- |
| 倍率**自动约分** | `environ\win32\WindowFormUnit.cpp:670-680` `AdjustNumerAndDenom()`（欧几里得算法求 GCD） | 官方「約分が自動で行われる」的实现；故 `setZoom(1920,1280)` 读回为 `zoomNumer=3 / zoomDenom=2`。**建议一律传互质数对**（本方案用 `2,3` 与 `1,1`）。 |
| 绘制目标矩形 = 层尺寸 × 实际倍率 | `environ\win32\WindowFormUnit.cpp:508-513` `SetDrawDeviceDestRect()`：`w = MulDiv(LayerWidth, ActualZoomNumer, ActualZoomDenom)` | 画布 1920×1080 × 2/3 = **1280×720**，恰好等于窗口客户区 → 无留边、无拉伸。 |
| **全屏下 `setZoom` 不改实际倍率** | `environ\win32\WindowFormUnit.cpp:694-698`：`if( !GetFullScreenMode() ) { ActualZoomDenom = denom; ActualZoomNumer = numer; }`，注释原文「**in fullscreen mode, zooming factor is controlled by the system**」 | **关键**：全屏时 `ActualZoom` 由系统按显示模式重算，脚本 `setZoom(1,1)` 只写「逻辑值」。见 §六.3。 |
| 全屏倍率由 `TVPFullScreenMode` 决定 | `environ\win32\WindowFormUnit.cpp:701-745` `RelocateFullScreenMode()` | `zoom_n/zoom_d = TVPFullScreenMode.ZoomNumer/Denom`；`FullScreenDestRect` = 客户区×倍率后在屏幕内居中。 |
| 全屏行为由**启动开关**控制 | `visual\win32\WindowImpl.cpp:206-258` `TVPInitFullScreenOptions()`；枚举 `:76-107` | `-fsres=auto\|prop\|nearest\|nochange\|expandwindow`（`fsrAuto/fsrProportional/fsrNearest/fsrNoChange/fsrExpandWindow`）、`-fszoom=yes\|inner\|outer\|no`（`fszmInner/fszmOuter/fszmNone`）、`-fsmethod=cds`（是否 `ChangeDisplaySettings`）、`-fsbpp`。**默认** `fsrNoChange` + `fszmInner`。 |
| **全屏中 `setInnerSize` 会抛异常** | `visual\win32\WindowImpl.cpp:1700-1704` `SetInnerSize` 首行 `FullScreenGuard()`；`:1153-1158` `FullScreenGuard()` 在 `Form->GetFullScreenMode()` 为真时 `TVPThrowExceptionMessage(TVPInvalidPropertyInFullScreen)` | → 必须在**进入全屏之前**设定客户区尺寸。 |
| 退出全屏时倍率被系统还原 | `environ\win32\WindowFormUnit.cpp:836-841`：`ActualZoomDenom = ZoomDenom; ActualZoomNumer = ZoomNumer; SetZoom(ZoomNumer, ZoomDenom);` | 退出全屏后回到进入前的逻辑倍率，无需脚本手动恢复。 |
| **鼠标坐标：层侧已按倍率换算** | `visual\win32\DrawDevice.cpp:51-66` `TransformToPrimaryLayerManager()`：`x = w ? (x * pl_w / w) : 0`（`pl_w` = 主层宽，`w` = `DestRect` 宽） | → 经 `Layer` / LayerManager 路径取得的鼠标坐标**已经是 1920×1080 画布坐标**（`1920 / 1280 = 1.5` 由引擎完成）。 |
| **鼠标坐标：Window 事件侧是客户区像素** | `environ\win32\WindowFormUnit.cpp:1354-1363` `GetCursorPos()` 末尾 `TranslateWindowToDrawArea(x, y)`；该函数 `:1551-1569` **只扣全屏偏移**（`x -= FullScreenDestRect.left`），**不除缩放** | → `Window.onMouseMove` 等 Window 自身事件给的是**客户区坐标**（窗口化时 0..1279×0..719），脚本若要当画布坐标用需**自行 ×1.5**。见 §六.4。 |
| `setInnerSize` 只改客户区，不动倍率 | `environ\win32\TVPWindow.cpp:784-789` `SetInnerSize()` → `SetClientSize()` | 与 `setZoom` 相互独立，两者都要设。 |

## 二、目标规格

### 2.1 规格表

| 项 | 值 |
| --- | --- |
| **设计画布（primaryLayer）** | **1920×1080**（脚本唯一坐标系；全部 UI/立绘/背景坐标按此书写） |
| **窗口化分辨率** | **1280×720**（客户区）＝ `setInnerSize(1280, 720)` + `setZoom(2, 3)` |
| **全屏分辨率** | **1920×1080**＝ `fullScreen = true`；**实际倍率由「画布尺寸 vs 显示器尺寸」决定**（见 §六.3 实测更正）。1920×1080 显示器上画布 1920×1080 → 1:1。启动参数用**默认 `-fsres=nochange`** |
| 倍率 | 窗口化 **2/3**；全屏 **1/1**（全屏倍率由系统决定，不靠脚本 `setZoom`） |
| 宽高比 | 16:9（两种分辨率同比例，**切换时画面不变形、不重新排版**） |
| 默认启动分辨率 | **1280×720 窗口化**（首次运行；设置文件缺失时的兜底） |
| 窗口边框 | 窗口化时建议 `borderStyle` 可调（自研外壳自行决定）；全屏时系统接管 |
| 最小 / 最大窗口尺寸 | 建议 `setMinSize(640, 360)` / `setMaxSize(3840, 2160)`，并**强制 16:9**（见 §六.5） |

### 2.2 切换时机

| 时机 | 动作 |
| --- | --- |
| **启动（`startup.tjs`）** | 读设置 → `primaryLayer.setSizeToImageSize()`（画布由素材/脚本决定，见 §六.2）→ 按设置选窗口化或全屏路径 |
| **切到全屏** | ①（窗口化状态下）确保**画布 = 目标全屏分辨率**（`primaryLayer.setSize(1920,1080)`，**这才是决定 1:1 的因素**，见 §六.3 实测更正）；② `fullScreen = true`；③ 等待 `onResize`（**不得同步读 `innerWidth`**，见 §6.5）；④ 写设置 |
| **切回窗口化** | `fullScreen = false`（引擎自动还原倍率与窗口尺寸，源码 `WindowFormUnit.cpp:836-841`）→ 再 `setInnerSize(1280,720)` + `setZoom(2,3)` → 写设置。**退出后 `innerWidth/innerHeight` 会有一拍陈旧值（窗口外框尺寸），不得同步读**（见 §6.5） |
| **用户拖动窗口** | `onResize` 内按 `innerWidth` 重算（见 §六.5）；**不要**用 `setZoom` 逐帧跟手（官方警告，§1.3） |
| **禁止时机** | 全屏中调用 `setInnerSize` 会抛异常（源码 `WindowImpl.cpp:1153-1158`），必须在进入全屏前设定 |

### 2.3 设置持久化

- **落点**：工程自研配置文件（krkr 侧可用 `Storages` 读写工作区内的 ini/JSON；存档系统属编程组缺口 G1，此处只定契约）。
- **⚠️ 实测读写 API（2026-09-20，V11）**：设置文件读写**必须用 `Scripts.evalStorage` / `Scripts.execStorage`**，实测两条可用：
  - `Scripts.evalStorage(name)` —— 文件内容为一条 TJS **表达式**，返回其值（如 `%[mode: "fullscreen", w: 1920, h: 1080]`）；
  - `Scripts.execStorage(name)` —— 文件内容为 TJS **语句**，在**全局上下文**执行（实测可写入预先声明的全局容器）。
  - **不可用（实测失败）**：`Array.load(fileUrlName)` 抛「无效的 object context」；`new TextStream(...)` 抛「未找到 Member "TextStream"」（krkrz 1.4.0r2 **未向 TJS 暴露** TextStream 类）。
  - 证据：`子代理工作区\ISSUE-20260920-18\W_1080p验证\V11_persist\`（`V11_evidence.txt`、`vt_display.cfg`）。
- **键**（建议名，编程组可改，但语义固定）：
  - `display_mode` ∈ `windowed` / `fullscreen`（默认 `windowed`）
  - `window_x` / `window_y`（窗口化时的窗口位置，可选）
  - `window_w` / `window_h`（窗口化时的客户区尺寸；**仅在允许自由缩放时使用**，否则恒为 1280×720）
- **读取时机**：`startup.tjs` 最开头，**在创建主窗口/设定画布之前**。
- **写入时机**：每次切换分辨率成功后立即写回；崩溃/强退时至少保留上一次成功值。
- **存档与分辨率解耦（重要）**：游戏存档一律以 **1920×1080 画布坐标**记录（立绘位置、UI 状态、截图缩略图坐标），**与当前窗口分辨率无关** → 同一存档在两种分辨率下均正确，切换分辨率**不需要重写存档**。

## 四、素材侧结论：**2 > 1.5，为 1K 重做素材不必要**

### 4.1 核心论证

画布从 1280×720 提到 1920×1080 **只是 1.5 倍**（1920/1280 = 1.5），而现有素材已经是 **2 倍**（`资源组\美术统一_超分\`，`超分清单.tsv` 的 `倍数` 列 4,415 行**全为 2**）。
**2 > 1.5** → 按比例放大的显示尺寸**天然落在素材分辨率之内**（即**下采样**，只会更锐）。

**结论：为 1K 重做素材不必要。** 现有 2× 超分集**同时满足** 1280×720 窗口化与 1920×1080 全屏两种呈现。

### 4.2 素材余量表（`超分清单.tsv` 全量实算）

| 类别 | 件数 | 原图集中位 | **2× 中位** | 2× 中位高 **≥1080** 占比 | 在 1920×1080 上的显示尺寸 | 余量 |
| --- | ---: | --- | --- | ---: | --- | --- |
| `立绘\` | **1,485** | 409×574 | **818×1148** | **75.0%** | 立绘不铺屏，按 **×1.5** 呈现（＝2× 素材 × 0.75） | — |
| `CG背景\` | **1,361** | 800×600 | **1600×1200** | **87.6%** | 4:3 → **1440×1080**（填满高度，左右各 240 黑边）；16:9 → **1920×1080** 满幅 | **11%**（4:3，下采样）／**33%**（16:9） |
| `系统UI\` | **1,569** | 280×105 | **560×210** | **17.6%** | 按 **×1.5** 呈现（UI 贴图不铺屏） | — |

| 项 | 实测 | 推导 |
| --- | --- | --- |

### 4.3 ⚠️ 必须写清的澄清：**不要把立绘 / 系统UI 垫成 1920×1080**

**结论：只有全屏背景 / CG 需要覆盖 1920×1080；立绘与系统UI 一律保持原画布尺寸，禁止垫画布。**

| 理由 | 量化 |
| --- | --- |
| 它们是**带透明通道的抠图** | 立绘 1,485 件全为 RGBA；系统UI 含大量透明底件。垫画布只是把透明区放大成大片空白像素。 |
| 垫画布**只增显存与加载时间** | 立绘 2× 中位 **818×1148 = 0.94 MP** → 垫到 1920×1080 = **2.07 MP**，像素量 **2.2 倍**（2.0736 / 0.9391 = 2.208）。显存、解码时间、打包体积同步上涨。 |
| 对画面**零收益** | 立绘按位置摆放、按尺寸绘制，垫出来的透明边**永远不会被看到**。 |
| **破坏既有 `内容bbox` 定位体系** | 交付清单的 `内容bbox(w,h)` 与 `尺寸(w,h)` 是既有定位/判透明判据（`美术交付交接件.md` §七：「`RGBA` ≠ 有透明底，判据是 `内容bbox`」）。垫画布会让 `内容bbox` 全部变成画布尺寸，**判据失效**。 |

**允许垫画布的唯一场景**：某件背景/CG 需要满屏（1920×1080）而原图比例不符、且**必须**用整张画布承载时——这属**新建素材**（UI 组重制件），**不是**对既有素材的批量垫画布。

## 五、4:3 → 16:9 的过渡方案

### 5.1 重制会根本改变 `content_box` 规则

用户已裁决「**4:3 构图改为 16:9**」（重制由 UI 组执行）。**若各源都成为 16:9，则全部源满幅填满画布，4:3 留黑边的问题消失**——`content_boxes` 的「按源代号固定盒子」规则随之失去意义。

**但重制是渐进的**：按同批交付的逐件执行表 **`资源组\美术\4比3待重制清单.tsv`（1,028 数据行）**，需重制的 4:3 全屏素材共 **1,028 件**（`CG背景` 1,004 / `系统UI` 24；按尺寸：**800×600 = 976 件**、**967×725 = 50 件**、798×600 = 1、805×607 = 1；按建议档位 T1 278 / T2 600 / T3 150）。**过渡期必然混合画幅**：已重制件为 16:9，未重制件仍为 4:3。

> **配套件**：重制任务大纲 **`资源组\UI组任务大纲_4比3转16比9重制.md`**（同 Issue `ISSUE-20260919-12`）——本方案是它的**上游口径依据**（画布基线、过渡期画幅规则）；本方案 §5.2 / §9.3 即该大纲 §1.1 引用的两处口径。

### 5.2 过渡方案（**建议编程组采用**）

**按素材实际宽高比放置，而不是按「源代号固定盒子」。**

规则（**contain：等比缩放到完全放入画布，尽量占满，居中**）：

```
给定素材实际像素尺寸 (sw, sh) 与画布 (CW, CH) = (1920, 1080)：
  scale = min(CW / sw, CH / sh)
  显示尺寸 (dw, dh) = (round(sw * scale), round(sh * scale))
  左上角 = ((CW - dw) / 2, (CH - dh) / 2)      // 垂直 + 水平都居中
```

| 素材宽高比 | 显示结果 | 留边 |
| --- | --- | --- |
| 4:3（800×600，未重制） | **1440×1080** | 左右各 **240** |
| 16:9（1280×720 / 1920×1080） | **1920×1080** | 无（满幅） |
| 16:9 近似（960×544，1.7647） | **1906×1080** | 左右各 **7**（可忽略；或按宽填 1920×1088 裁 8px，二选一，见 §十 U3） |
| 更宽（如 3840×720，5.33:1） | 1920×360 | 上下各 **360**（总纲 §八 U6 已登记第四种比例） |
| 更高（竖幅，如 1280×1920） | 720×1080 | 左右各 **600**（或改滚动，见 `美术规范.md` §六 H2） |

**这样已重制与未重制可共存**：同一场景里，重制过的背景满幅、未重制的按 4:3 居中留边，**无需为每一件手工登记盒子**，也不需要「过渡期双份布局」。

**⚠️ 实测确认（2026-09-20，V10）**——上表的两条主口径已用真素材实机量测（`子代理工作区\ISSUE-20260920-18\W_1080p验证\V10_assets\`，`V10_measurements.txt`）：

### 6.2 画布与启动序列（建议伪代码）

```tjs
// startup.tjs —— 顺序不可颠倒
// ① 读设置（在设画布之前）
var cfg = loadDisplayConfig();                    // display_mode / window_x,y / window_w,h
                                                  // 实测：必须用 Scripts.evalStorage / execStorage（§2.3）
// ② 建立画布：primaryLayer 设为 1920×1080
Window.primaryLayer.setSizeToImageSize();         // 或显式 setSize(1920,1080)
//    若 primaryLayer 由加载的第一张全屏底图决定，则确保该底图为 1920×1080；
//    否则显式 setSize，不要依赖素材尺寸。
//    ⚠ 画布尺寸 = 全屏时的实际 1:1 依据（§6.3 实测更正），必须保证为 1920×1080。
// ③ 按设置进入窗口化或全屏
if(cfg.display_mode == "fullscreen") {
    Window.setInnerSize(1920, 1080);              // 可选：仅让窗口化阶段的窗口尺寸一致；对全屏结果无影响
    Window.fullScreen = true;                     // 实际倍率由「画布 vs 显示器」决定；启动参数用默认 -fsres=nochange
} else {
    Window.setInnerSize(1280, 720);
    Window.setZoom(2, 3);                         // 画布 1920×1080 → 客户区 1280×720
}
Window.setMinSize(640, 360);                      // ⚠ 仅窗口化可用；全屏中调用会抛异常（§6.5）
Window.setMaxSize(3840, 2160);
```

**要点**：
- `setZoom` 与 `setInnerSize` **相互独立**（源码 `TVPWindow.cpp:784` 与 `WindowFormUnit.cpp:681`），两者都要调用；
- **必须传互质数对**（`2,3` / `1,1`），避免被 `AdjustNumerAndDenom` 约分后与预期不符（**实测**：`setZoom(1920,1280)` 被约成 `3/2`、`setZoom(1920,1080)` 被约成 `16/9`）；
- 脚本内所有坐标一律按 **1920×1080** 书写，**不要**在任何地方再乘 1.5；
- **全屏 1:1 的决定因素是「画布尺寸」而不是「进全屏前的客户区尺寸」**（§6.3 实测更正）；
- **全屏中不得调用 `setInnerSize` / `setMinSize` / `setMaxSize` / `borderStyle`**（均抛 `在全屏模式下无效的属性`，§6.5）。

### 6.3 全屏 1920×1080 的正确做法（**源码级注意点 + 2026-09-20 实机更正**）

> **🔴 实测更正（2026-09-20，`ISSUE-20260920-18` V6）——本条是方案唯一被实机证伪的核心断言，务必先读**
>
> **原以为**：进全屏前把客户区设成 1920×1080，全屏就会 1:1（依据官方 `fullScreen` 页「フルスクリーン時の画面解像度はクライアント領域のサイズになります」）。
> **实测是**：**全屏下 `innerWidth/innerHeight` 恒等于显示器尺寸，与进全屏前的 `setInnerSize` 无关。**
> - V6_02：进全屏前 `setInnerSize(1280,720)`，全屏后 `innerWidth/innerHeight` 仍报 **1920×1080**（= 显示器尺寸），`winsize=1920x1080`。
> - **真正决定全屏 1:1 的是「画布（primaryLayer）尺寸」**：画布 **1920×1080 → 实际倍率 1.0000**；画布 **1280×720 → 实际倍率 1.5000**（被放大，画面变软）。
>
> **⇒ 更正后的正确做法（实测配方）**：
> ```
> ① primaryLayer 画布设为 1920×1080（setImageSize(1920,1080) + setSizeToImageSize()）
> ② Window.fullScreen = true
> ③ 启动参数用默认的 -fsres=nochange（不要加 -fsres=nearest/auto/prop）
> ```
> 画布 1920×1080 时，导出画布与实机全屏截屏**逐像素完全一致（518400 采样全等，max diff = 0）**。
>
> **⇒ 因此本方案的口径改为**：**「画布（primaryLayer）尺寸 = 目标全屏分辨率」，启动参数用默认 `-fsres=nochange`**；下面「步骤 1：先设客户区」的原说法**已被实测证伪，仅作历史记录保留**（见下方原文块）。`setInnerSize` 在全屏路径上**不参与**全屏结果的判定（全屏客户区由系统/显示器决定）；保留它只是为了窗口化阶段的窗口尺寸一致，以及「因为全屏中不能再调，所以窗口化阶段先设好」。
> 证据：`子代理工作区\ISSUE-20260920-18\W_1080p验证\V6_fullscreen_matrix\`（`V6_02_1280_default.png`、`V6_matrix_measured.txt`）。

**不能只靠脚本 `setZoom(1,1)`**：全屏下 `ActualZoom` 由系统决定（源码 `WindowFormUnit.cpp:694-698` 注释「in fullscreen mode, zooming factor is controlled by the system」）。

> **做法（两步都要）**：
>

>    - **`-fsres=nochange`**（默认）：不改变显示器分辨率，按显示器当前模式全屏；
>    - **`-fszoom=inner`**（默认）：引擎按「内接」把客户区放进显示器（四周可能留黑）；

> ⚠️ **上条步骤 1 已被实测证伪**（见本小节顶部更正块）；步骤 2 的 `-fsres=nochange` 仍正确，但**「备选 `-fsres=nearest` / `auto` / `prop`」是危险的，已删除**（见下）。

**更正后的启动开关口径（实测）**：

- **`-fsres=nochange`**（默认，**唯一推荐值**）：不改变显示器分辨率，按显示器当前模式全屏；
- 备选 **`-fsres=expandwindow`**：不切分辨率，把窗口扩展到显示器（实测画布 1920×1080 下同样 1:1）；
- **❌ 删除 `-fsres=nearest` / `auto` / `prop` 作为备选**——**实测有严重副作用**：当**画布小于显示器**时，这三个值产生**等于客户区尺寸、停在 (0,0)、不覆盖屏幕**的无边框窗口，**桌面裸露**：
  - V6_13（`nearest`）/ V6_14（`auto`）/ V6_15（`prop`）：画布 1280×720 → 全屏窗口 **1280×720**（非 1920×1080）；
  - V6_16（`nearest`）：画布 960×540 → 全屏窗口 **1128×634**（尺寸来源未查明，见 §十 U10）；
  - V6_07/08/09（`prop`/`nearest`/`auto`）**看着正常，只因它们用的是 1920×1080 画布**（客户区恰好 = 屏幕），**不能据此认为这三个值可用**。
- **`-fszoom` 三值的实测语义**：
  - `inner`（默认）与 `outer`：本机 16:9 画布下结果相同（铺满）；
  - **`no`：完全不缩放、1:1 居中留黑边**。1280 画布全屏时画面原点 = **(320,180)** = ((1920−1280)/2, (1080−720)/2)，四周留黑边（V6_03）。
  - ⇒ **`-fszoom=no` 是「非 1920×1080 显示器上保持 1:1、宁可留黑边」的现成备选**，直接回应 §十 U4——**要避免非整数缩放，应改 `-fszoom`，而不是换 `-fsres`**。
- **`-fsmethod=cds`**：本机（画布 1920×1080）未观察到副作用；但其「切换显示模式」的风险（Win7）本机无法验证（见 §十 未决项）。

**实测结果矩阵（2026-09-20）**：

| 显示器 | 画布 1920×1080 + `-fsres=nochange -fszoom=inner` | 判定 |
| --- | --- | --- |
| **1920×1080** | 铺满 → **1:1 原生**（实际倍率 **1.0000**），无缩放、无插值问题 | ✅ **已实测证实**（V6_01；导出画布 vs 全屏截屏 max diff = 0） |
| 2560×1440 / 3840×2160 | 预期按内接放大 → 有缩放 | ⚠️ **未实测**（本机只有 1920×1080 一个活动模式，无法构造） |
| 1600×900 等更小 | 预期按内接缩小 → 有缩放 | ⚠️ **未实测**（同上） |

→ **若要求「非 1920×1080 显示器上也不做非整数缩放」**：**现成答案是 `-fszoom=no`**（1:1 居中 + 黑边，实测 V6_03/V6_12），仍可提请用户裁决（§十 U4）。

### 6.4 鼠标坐标换算（**关键**）

krkrz 有**两条**鼠标坐标通路，参照系不同（源码见 §1.4 最后两行）：

| 通路 | 坐标参照系 | 窗口化 1280×720 时的取值范围 | 换算 |
| --- | --- | --- | --- |
| **`Layer` / LayerManager 路径**（`Layer.getCursorPos()`、`Layer` 上的 `onMouse*` 等） | **主层（设计画布）坐标** | **0..1919 × 0..1079** | **无需换算**（引擎已按 `x * pl_w / DestRect.w` = `x * 1920/1280` 做过） |
| **`Window` 事件路径**（`Window.onMouseMove` / `onMouseDown` / `onMouseUp` / `onClick` / `onMouseWheel` 等） | **客户区（draw area）像素** | **0..1279 × 0..719** | 需**自行换算**：`canvas_x = client_x * 1920 / 1280 = client_x * 1.5`；`canvas_y = client_y * 1.5` |

**两条硬性建议**：

1. **一律走 `Layer` 侧坐标**（引擎已换算为画布坐标），命中判定 / 悬停 / 拖拽全部按 1920×1080 书写；**不要**自行乘 1.5（两条通路混用会得到相差 1.5 倍的坐标，是最容易犯的错）。
2. 若因故必须用 `Window` 事件坐标，**换算因子必须由 `Window.innerWidth` 动态求**，不得硬编码 1.5：
   `canvas_x = client_x * Window.primaryLayer.width / Window.innerWidth`
   ——这样在窗口被用户改尺寸、或全屏/窗口化切换后**自动正确**（全屏 1920 客户区时因子退化为 1）。

**全屏时的额外偏移**：`TranslateWindowToDrawArea` 会扣掉 `FullScreenDestRect` 偏移（源码 `WindowFormUnit.cpp:1551-1556`），即客户区坐标**已相对画面左上角**；`Layer` 路径仍返回画布坐标，两者同样由引擎处理，脚本无需关心黑边偏移。

**⚠️ 实测确认（2026-09-20，V4）**——上表两条通路与两条硬性建议已用真点击实机验证（`子代理工作区\ISSUE-20260920-18\W_1080p验证\V4_mouse\`）：

- **窗口化 1280×720 客户区 / 1920×1080 画布 / `setZoom(2,3)`**：`Layer = Window × 1.5` **逐点精确**（6 个采样点全部 1.5000）。
- **判别性命中测试**：画布按钮定义为 x∈[1200,1560]、y∈[800,1000]。在**客户端 (959,539)** 点击：
  - **`Layer` 路径 → (1438,808) = HIT**（正确命中；比值 1.4995/1.4991，取整误差内）；
  - **把客户端坐标直接当画布坐标 → (959,539) = miss**（错误）。
  - ⇒ **「一律走 Layer 侧坐标」不是风格建议，而是对错之分**。
- **换算公式实测成立**：`canvas_x = client_x * primaryLayer.width / innerWidth`，1280 客户区 / 1920 画布 → 因子 1920/1280 = 1.5，与实测逐点吻合。
- **全屏 1920×1080（客户区 = 画布）**：11 个采样点全部满足 `Layer == Window`（因子退化为 1），两条通路无差异；**无 1.5 倍错位**。
- 证据：`V4_windowed_1280x720_zoom2_3_clicks.txt`、`V4_fullscreen_1920x1080_clicks.txt`。

### 6.5 `onResize` 处理与窗口尺寸限制

```tjs
Window.onResize = function() {
    if(Window.fullScreen) return;                 // 全屏下不处理（倍率由系统管）
    // 若允许自由缩放：按当前客户区宽高重算倍率，保持 16:9 映射
    //   zoomNumer = 1920, zoomDenom = Window.innerWidth   （即客户区宽 = 画布宽 × denom/numer）
    //   仅在内宽为 16:9 时使用；否则先纠正客户区尺寸再设倍率
    var w = Window.innerWidth, h = Window.innerHeight;
    if(w * 9 != h * 16) {                         // 非 16:9 → 纠正（保宽，改高）
        Window.setInnerSize(w, Math.round(w * 9 / 16));
        h = Window.innerHeight;
    }
    Window.setZoom(1920, w);                      // 画布 1920 → 客户区 w
    saveDisplayConfig();                          // 写回设置
};
```

**注意**：官方警告 `setZoom` **不适合连续变化倍率**（每次变更会重新探测可用硬件，§1.3）。故：
- 拖动过程中**不要**每次 `onResize` 都调 `setZoom`；建议**拖拽结束后**（如定时器去抖 200 ms）再重算；
- 或者直接 `setMinSize(1280,720)` + `setMaxSize(1280,720)` **禁止用户改尺寸**（最稳，推荐先这么做）。

**⚠️ 实测新增的两条陷阱（2026-09-20，V5 / 顺序测试）**：

1. **切换全屏后不得同步读取 `innerWidth/innerHeight`**。实测 `fullScreen = false` 之后，`innerWidth/innerHeight` 在**至少一个事件循环内**返回的是**窗口外框尺寸**而非客户区：
   - 20 轮切换中第 1–19 轮读回 `win 1296x759`（= 1280×720 客户区 + 边框），第 20 轮才读回正确值 `1280x720`；
   - 顺序测试 `fullScreen=false` 后同样读回 `1936x1119`（= 1920×1080 客户区 + 边框）。
   - ⇒ **实现要求**：切换后**不得同步读取** `innerWidth/innerHeight` 去做布局或坐标换算（§6.4 的换算公式若拿到外框尺寸会算错）；必须在 `onResize` 或**下一拍**再读。方案 §6.6 只提到「用正在切换标志位屏蔽 `setZoom`」，**这条读值时序要求是新增的**。
   - 证据：`V5_switch\V5_20rounds.txt`。

2. **`setMinSize` / `setMaxSize` / `borderStyle` 在全屏中也抛异常**（不只是 `setInnerSize`）。顺序测试实测：
   - B4 全屏中 `setInnerSize(1280,720)` → 抛 `在全屏模式下无效的属性：%1`（`FullScreenGuard`，与 §1.4 源码结论一致）；
   - **B6 全屏中 `borderStyle = bsNone` → 抛异常**（方案原本只提了 `setInnerSize`）；
   - **B7 全屏中 `setMinSize(640,360)` → 抛异常**（方案未提示）；
   - B5 全屏中 `setZoom(2,3)` → **不抛异常**（仅写逻辑值，与 §6.3 一致）；B8 全屏中 `caption = ...` → OK。
   - ⇒ **实现要求**：`setInnerSize` / `setMinSize` / `setMaxSize` / `borderStyle` **只能在窗口化状态调用**；若在 `onResize` 中无条件调用这些属性，**必须先判 `if(!Window.fullScreen)`**。
   - **正确调用顺序（实测）**：
     ```
     进入全屏：先 setInnerSize(...)（可选，对全屏结果无影响）→ 再 fullScreen = true
     退出全屏：fullScreen = false → setInnerSize(1280,720) + setZoom(2,3)
     全屏期间禁止：setInnerSize / setMinSize / setMaxSize / borderStyle
     ```
   - 证据：报告 §3.3 顺序测试表（`V5_switch\`）。

### 6.8 `Layer.drawText` 颜色参数陷阱（**实测新增，方案原本缺失**）

**`Layer.drawText` 的颜色参数是 `0xRRGGBB`（不含 Alpha）；传 `0xAARRGGBB`（如 `0xffffffff`）会完全不画任何东西。**

- 实测：`drawText` 传 `0xffffffff` → **画面与画布导出均无任何文字**；改为 `0xffffff` → 文字正常。
- **反直觉之处**：**同一工程里 `Layer.fillRect` 却接受 `0xAARRGGBB`**（V6 矩阵用来画四角白块的 `fillRect(..., 0xffffffff)` 正常工作）。两个绘制 API 的颜色口径**不一致**。
- ⇒ **实现要求**：对话框 / UI 文字绘制**一律传 `0xRRGGBB`**。这是实现阶段 **100% 会踩**的坑（文字画不出来，却很难联想到是颜色参数）。
- 证据：`子代理工作区\ISSUE-20260920-18\W_1080p验证\misc\drawText_colour_arg_test_screen.png` 与 `drawText_colour_arg_test.log`。

### 6.9 本轮验证过程中的一次返工（**方法论警示，如实登记**）

本轮第一次跑 V3（文字清晰度）时，四组「文字」截图与导出的画布 PNG **都是空白**（只有参考网格与标记矩形）。**当时若直接出报告，就会把「文字渲染正常」写成错误结论——那是错的。** 追查后定位到两个验证 harness 缺陷：

1. `vtLoadAsset()` 在 `Window` 构造器内被调用时全局 `vtWin` 尚未赋值（原代码在构造器**返回后**才赋全局），导致 `new Layer(vtWin, vtWin.prim)` 触发 null 访问 → **V10 第一版 contain 测试其实没加载到任何素材**（第一次跑出的 contain PNG 是纯黑）；
2. **`Layer.drawText` 的颜色参数传了 `0xffffffff`（`0xAARRGGBB`），引擎完全不画**（即 §6.8 的坑）。改为 `0xffffff` 后文字正常。

**两处修正后 V3/V10 全部重跑，本方案引用的 V3/V10 结论均出自修正后的数据。** 修正前的产物（空白文字、纯黑 contain）已作废，未采信。
