## 一、分辨率与画布（**D1 已裁决，不得偏离**）

### 1.1 裁决原文（总纲 §三.5 / §八 D1）

> 画布 **1280×720**；4:3 源（本篇 / R 版 / After Story / 前奏诗，均 800×600）以**原生 1:1 居中、左右留黑边**呈现；16:9 源（涅布 1280×720）原生填满。
> **全部素材不做放大**（放大 2008 年原画会与涅布原生 720p 素材锐度不一致，违反 `AGENTS.md` §六 美术风格统一）。缩放只发生在 krkr 层的居中/留边，**不写进素材文件**。

### 2.2 按类别看（决定「能不能直接叠加」）

| 源 | `chr` 立绘 | `pic` 背景/CG | `sys` 系统 | `etc` |
| --- | --- | --- | --- | --- |
| `ot` | **RGBA 989（100%）** | RGB 756 / RGBA 7 | RGBA 477 / RGB 500 / P 122 | — |
| `otr` | **RGBA 353（100%）** | RGB 156 | — | — |
| `ota` | **RGBA 1,264（100%）** | RGB 519 | RGBA 341 / RGB 236 / P 123 | — |
| `otp` | **RGBA 591（100%）** | RGB 270 | RGBA 103 / RGB 44 / P 109 | — |
| `otv` | **RGBA 253（100%）** | RGB 102 / RGBA 17 | RGBA 177 / RGB 5 | RGB 6 / RGBA 7 / **L 111** |
| `np` | **RGBA 291（100%）** | RGBA 14 / RGB 71 / L 8 | — | — |

**结论（可直接引用）**

1. **全部 `chr` 立绘 100% 为 RGBA 且带真实 alpha**（`ot` 989 / `otr` 353 / `ota` 1,264 / `otp` 591 / **`otv` 253** / `np` 291，合计 **3,741** 张）→ **可直接按图层叠加，无需抠图**。（**W11d 更正**：原为 3,488，漏计 `otv/chr` 253。）
2. **`pic` 背景/CG 绝大多数为 RGB（不透明）**，可整幅铺底；`np/pic` 有 14 张 RGBA、8 张 L（灰度）；**`otv/pic` 119 张为 RGB 102 / RGBA 17（W11d 补录）**。
3. **`L` 灰度 119 张全部是 `otv` 的转场遮罩（111 张）＋ `np` 8 张**。krkr 的 alpha 合成需要带 alpha 的位图，**灰度 mask 需在引擎侧转成 alpha 通道**（编程组事项，非素材重制）。
4. **`P` 索引色 354 张**集中在 `ot/ota/otp` 的 `sys`（122/123/109），多为小部件与调色板化 UI 元素。krkr 对 P 模式 PNG 支持需编程组实测（`引擎工作原理.md` 未覆盖此项）。
   > **✅ 2026-09-20 确认（W19，回应 UI 组 N3）**：本表 354 张是**六源素材库合计**（`ot` 122 ＋ `ota` 123 ＋ `otp` 109），**不是统一交付集的口径**。统一交付集 `美术统一\系统UI\`（1,569 件）范围内 **P 模式实为 11 件**（实测：RGBA 715 ＋ RGB 732 ＋ **P 11** ＋ L 111 = 1,569）；`CG背景\`（1,361 件）P 模式 **0** 件。**原文保留不改**，现行口径以本注为准。
5. **不存在需要统一调色板的强制项**：各源均为 8-bit/通道，**无 16-bit、无 CMYK、无色彩配置文件**。跨源合成时按 sRGB 直通即可，**不做色彩空间转换**（避免引入色差）。

### 2.3 调色板结论

- 各源**没有随素材附带的 `.pal`/`.act` 调色板文件**（总账 48,816 条中无此类，`etc` 类仅 `otv` 124 张图）。
- **不做全局调色**：D1 的路线是「各源原生 1:1 呈现」，**不允许为统一观感而对某一源做色阶/饱和度调整**（那会同时违反「不放大」的同源理由：破坏与原生素材的一致性）。
- 若 UI 组新增 UI 素材，**取色应直接吸取既有素材像素**（推荐取样点：`ot/sys/ot_sm_base.png` 系统底、`otv/sys/otv_dlg_bg_01.png` 对话窗、`otv/sys/otv_bg_config_01.png` 配置底）——具体色值须由 UI 组用工具吸取后写入 `美术规范.md` 增补段（本模块**不解码像素**，故不提供色值，避免编造）。

## 三、缩放算法

| 场景 | 算法 | 依据 |
| --- | --- | --- |
| **默认** | **不缩放**（1:1 原样 blit） | D1 明文「全素材不放大」；且 1:1 无重采样损失 |
| 必须缩小时（仅限尺寸超出画布的素材，见 §六） | **面积平均 / 双线性（bilinear）** | 最近邻（nearest）在缩小 2036→1280 这类比例时会丢细线、产生摩尔纹；`ot` 的 `2036×37` 音乐条是细横线图，nearest 会断线 |
| 放大 | **禁止** | D1 明文；放大 2008 年原画会与 `np` 原生 720p 锐度不一致（`AGENTS.md` §六 美术风格统一） |
| UI 部件（按钮/图标/滚动条） | 按**原始像素 1:1** 摆放，不做九宫格拉伸以外的缩放 | 部件尺寸普遍很小（49×49 / 100×75 / 198×99 / 224×24），拉伸会糊 |

> **未实测项（如实登记）**：krkr 侧「非整数缩放的采样方式、是否支持指定插值」**本工作区未实测**（`引擎工作原理.md` 未覆盖，且 krkrz 已删除 `Layer.affineBlend`）。**具体 API 与可行性属编程组事项**；本规范只定算法选型原则。若 krkr 无法做高质量缩小，则 §六 的「超宽素材」改为**裁切/滚动**而非缩小。

## 四、UI 素材比例与命名规范

### 4.1 命名（**强制**，总纲 §七 I1 + §八 D2）

```
<源代号>_<原文件名小写>.<ext>
```

- **源代号**：`ot`（本篇）/ `otr`（R 版亚衣线）/ `ota`（After Story）/ `otp`（前奏诗）/ `otv`（PSV 美咲线 UI）/ `np`（涅布＊プラス）。
- **目录**：`krkr素材库\<源代号>\<kind>\`，`kind ∈ chr | pic | sys | bgm | se | voice | movie | etc`。
- **示例**：`krkr素材库\otv\sys\otv_dlg_bg_01.png`、`krkr素材库\ot\sys\ot_sm_base.png`、`krkr素材库\np\chr\np_asu_a01l.png`。
- **引用一律写全路径**（`ot/…`、`otv/…`），**禁止按 basename 隐式解析**：跨源同名 12,344 组、其中 11,081 组字节不同（`_冲突报告.md` §一）。且实测其中约 43% 只是「同一文件尾部 ≤16 字节不同」，**同样不得据此判定素材可互换**（`资源总账.md` §六.1）。

## 五、字体约束（**本工程当前缺口，如实登记**）

| 项 | 实测/事实 | 依据 |
| --- | --- | --- |
| krkr 是否自带字体 | **不自带**。靠系统字体（`Font.face` / `Font.getList()`） | `02_资源审计报告.md` §8.4；`.zcode\skills\kirikiri-unpack\SKILL.md` §8.3 |

| **中文字体内嵌 / 分发方案** | **不存在**（工程级缺口 **G2**，总纲 §三.2） | 总纲 §三.2 G2；`作品skill\SKILL.md` §一 |
| 各源原版字体 | `ot/ota/otp` 的 `SYS.LPK` 内含字体资源（`02_资源审计报告.md` §2.2 记「系统 UI 图/字体」）；**是否可提取复用未验证** | 审计 §2.2 |
| 字号 / 行距参数 | 原版参数在 `.gmp`（未解码，D11）；PSV 侧参数在 `adv.txt [Window]`（`:FontScale` / `:NameFontScale 0.8125`，**但 `adv.txt` 不在 krkr素材库内**） | 审计 §6.4 |

**给 UI 组的结论**

1. **UI 文本一律按「系统字体 + 运行时探测」设计**，不得假设某字体存在（Win7 下限机不一定有雅黑的高版本，且雅黑在 Win7 为 5.0x 版）。
2. **字号/行距按 1280×720 画布重新定**：4:3 源内容只占画布 62.5% 宽，若对话框按 1280 满幅设计、文本沿用 800×600 时代的字号，**会显得过小**。建议对话框文本区宽度按画布满幅、字号按 1280×720 基准重定（具体值由 UI 组实测截图确定）。
3. **字体缺口属编程组 G2，不是 UI 组职责**；UI 组只需**不依赖特定字体**、并避免使用超出 GBK 的罕用字（`咲` U+54B2 等 GBK 非 GB2312 字在默认字体下可能空白，审计 §5.5 风险 4）。
4. **禁止使用系统字体以外的隐式假设**（如「宋体一定有」）；krkr UI 应在启动时 `Font.getList()` 探测并回退。
