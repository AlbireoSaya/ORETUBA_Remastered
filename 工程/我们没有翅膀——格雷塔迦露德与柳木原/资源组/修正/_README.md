## 二、修正表 schema（11 列，十一张修正表 schema 一致；`field` / `locator` 取值随 `source` 分派，见 §2.1–§2.3 与 §三）

| 列 | 含义 |
| --- | --- |
| `source` | 源代号：`otp` 前奏诗 / `ota` After Story / `otr` R 版 / `otv` PSV 美咲线 / **`ot` 本篇**（W7-4 新增，`修正表_0x5C.tsv` 与 ISSUE-20260919-06 的 `修正表_说话人译名.tsv`）/ **`np`**（ISSUE-20260919-06 新增，`修正表_np说话人译名.tsv`） |
| `file` | 脚本文件名（如 `s01_03d.tob`、`02_03e.sob.jsonl`） |
| `locator` | **唯一定位串**，格式 `offset=<n>`（TOB 类）或 `seq=<n>`（SOB jsonl 类）；**otv 类为 `script=<脚本名>&lineno=<行序>`**（见 §2.1）；**ot 类为 `script=<脚本名>&seq=<行序>`**（见 §2.2）；**ota 类为 `idx=<消息 index>`**（见 §2.3） |
| `kind` | 槽类型：`title` / `dialogue` / `line` / `other` |
| `field` | 被修正的字段：**多数为 `cn`**（含 `修正表_np说话人译名.tsv`）；`修正表_0x5C.tsv` 为 **`speaker_voice`**、`修正表_说话人译名.tsv` 为 **`speaker`**（均见 §三） |
| `old_text` | 修正前文本。**语义按 `fix_type` 分叉**（ISSUE-20260930-12）：`term_unify` = **被替换词形（正则）**；其余 = 该槽**整句**（逐字符等于取文基准层，已断言）。见 §三.3 |
| `new_text` | 修正后文本。**语义按 `fix_type` 分叉**：`term_unify` = **替换值**（**不是整句**）；其余 = 该槽整句修正后文本 |
| `fix_type` | 见 §三 枚举 |
| `method` | `programmatic`（可程序化） / `manual_retranslate`（人工重译） |
| `evidence` | 判定依据（判据 + 证据文件 + 必要的截断形态说明） |
| `confidence` | `high` / `medium` / `low` |

### 2.1 `locator` 的 otv 形态（**W4b 2026-09-19 补记**）

PSV 美咲线语料 `工程\我们没有翅膀PSV\汉化\台词对照.json`（4,931 行 = 台词 4,904 + 梗概 27）
**没有 `offset` / `seq`**，其行主键是 **`脚本` + `行序`** 复合键（`行序` 为**每脚本内** 1-based 序号，
同一 `行序` 在不同脚本中重复出现，故**必须带 `script=` 才能唯一定位**）。因此：

| 列 | otv 取值 | 说明 |
| --- | --- | --- |
| `file` | `台词对照.json` | otv 的取文语料文件（等价于 otp/otr 的 `.tob`/`.sob.jsonl`） |
| `locator` | `script=<脚本名>&lineno=<行序>` | 例 `script=M01_04&lineno=216`；`script` 对应 `scene_otv.jsonl` 的 `script` 字段，`lineno` 对应 `lines[].lineno` |

**消费方定位方式**：仍按 `(source, file, locator)` 三元组定位，**不得用字符串匹配**（§四.1）；
在 `台词对照.json` 中筛 `脚本 == <脚本名>` 且 `行序 == <行序>` 即为目标槽。
**兼容性**：与 `offset=<n>` / `seq=<n>` 同属「单文件内唯一定位串」语义，只是 otv 的键是复合键、以 `&` 连接。

### 2.2 `locator` 的 ot 形态（**W7-4 2026-09-19 补记**）

本篇语料 `工程\我们没有翅膀\汉化\剧情汉化\<script>.sob.jsonl`（397 个文件）每行有 `seq` 字段，
但 **`seq` 是抽取器未过滤列表的序号，不等于行索引**（`kind=ascii` 的资源/路径行被过滤后，
同一文件内 `seq` 不连续，如 `s01_02e.sob.jsonl` 122 行而 `seq` 最大 497）。
故 ot 的行主键取 **`script=` + `seq=`** 复合键（与 otv 同构，`seq` 对应 `scene_ot.jsonl` 的 `lines[].lineno`）：

| 列 | ot 取值 | 说明 |
| --- | --- | --- |
| `file` | `<script>.sob.jsonl` | 例 `s01_02e.sob.jsonl` |
| `locator` | `script=<脚本名>&seq=<行序>` | 例 `script=s01_02e&seq=237` |

**消费方定位方式**：按 `(source, file, locator)` 三元组定位（§四.1），**不得用字符串匹配**；
在该 jsonl 中筛 `seq == <行序>` 即为目标槽（**须建 `seq → 行索引` 映射，不得直接把 `seq` 当索引**）。

> **本形态的消费落地（ISSUE-20260919-09，2026-09-19）**：`修正表_かるら.tsv`（`source=ot`，37 条，`field=cn`）
> 是**首张按本形态消费的 `cn` 覆盖表**。`build_scene_ot.py` 的实现口径：
> ① 通用路径（`file=<script>.sob` + `locator=seq=<k>`）不变；
> ② 另建 `(script, seq)` 索引（`seq` = 源 `seq` = `scene_ot.jsonl` 的 `lines[].lineno`）承接本形态，
>    两路在逐行组装时合流；③ 命中前断言 `old_text` 逐字符等于该行**取文基准层 `cn`**，不符即 fail loud；
> ④ 命中记入 `fix_refs`（`cn_origin=retranslate`），并计入 `corrections_hit`（**条目计数**，不重复计键）。
> 实测：范围内 83 条 = 生效 **37** + 门控排除 46 + 未命中 0（见 `资源组\剧本\本篇_产出报告.md`）。

### 2.3 `locator` 的 ota 形态（**W6c 2026-09-19 补记**）

After Story 语料（`工程\我们没有翅膀 After Story\语料\译文.json` / `台词.json`）的 `.tob` 头部**无标签表**
（`nlab=0`，见 `build_scene_ota.py` 模块头注释第 2 条），其记录主键是解析器写入的 **`messages[].index`**
（`工具\parse_after.py:99/105` 生成：`kind=line` 取枚举序号 `k`、`kind=title` 取 `t['index']`），
**不是字节 `offset`**。故 `ota` 的行主键取 **`idx=<消息 index>`**：

| 列 | ota 取值 | 说明 |
| --- | --- | --- |
| `file` | `<脚本名>.tob` | 例 `11_5b.tob`（After Story 的 `.tob` 文件名） |

再按 `(source, file, locator)` 三元组查表（**不得用字符串匹配**，§四.1）；命中后仍断言 `old_text` 与源语料逐字符相等。
**适用范围**：本形态目前仅见于 `修正表_B1B3.tsv` 第 **16–22 行**共 **7 条**（均 `source=ota`、`fix_type=quote_add`、
`kind=line`）；同表 `otr` 条用 `offset=`、`otp` 条用 `seq=`，**三种 locator 并存，消费方须按 `source` 分派**。

**例证**（`修正表_B1B3.tsv` 第 16 行，实测原文）：

即：`source=ota` + `file=11_5b.tob` + `locator=idx=17` 三元组唯一定位到该消息槽。

### 三.1 `speaker_split` 的语义与消费方式（**W7-4 2026-09-19**）

## 四、消费规则（W6 必须遵守）

1. **定位方式**：一律按 `(source, file, locator)` 三元组定位，**不要用字符串匹配**。
   原因：50 条 `retranslate` 中有 **15 条**的最终落盘值是**等长截断形态**（如 `#鹰志$&「是时候该学习了—— `），与 `old_text` 不完全相等。
2. **应用顺序**：先按本表覆盖 `cn`（**覆盖前先过 §四.5 来源门控**：条目 `source` 与 `cn_base` 不符者不生效、逐条留痕），
   **再**执行 D14 的译名替换（`译名替换表.tsv`），**再**组装 `scene.jsonl`。

   ⚠️ **修正层 `new_text` 不保证术语已归一，译名替换必须居其后（顺序不可颠倒）**：
   修正表的 `new_text` 只修「引号 / 错位 / 切分」等缺陷，**不负责把用词改成现行统一口径**；
   其正确性依赖「② 套修正表 → ③ 套译名替换」这一顺序。
   **实证**：`修正表_B1B3.tsv` 第 16–18 行（`11_5b.tob idx=17` / `11_5b.tob idx=45` / `11_5c.tob idx=65`）
   的 `new_text` 写的是「**羽田同学**」，正是靠其后 ③ 步译名替换（`羽田同学`→`羽田君`，见 `译名仲裁报告.md` T1）
   才在产物里变成「羽田君」。**若下游颠倒顺序（先替换后修正），修正表会把已归一的「羽田君」重新顶回「羽田同学」，
   且不再有后续步骤纠正。**
3. **冲突检测**：若同一定位出现两条修正，**中止并上报**，不得静默取其一。
4. **完整性断言**：消费后应校验「修正条目全部命中或明确排除」，未命中者逐条列出。

### 四.5 修正表来源门控（**对后续所有源模块生效的契约**，W6a2 主代理裁决）

> **规则：修正表条目只在其 `source` 与该行「取文基准层」一致时才生效。**

- **为什么**：条目 `source` 标的是「这条修正所针对的语料层」。若某行实际取文并非来自该层
  （典型：按 **D14** 共有场景**整场取本篇**），则该条修正**无对象**，不得覆盖——
  否则会用该层的重译顶掉现取文。
- **判据（逐行、可审计）**：比较「条目 `source` 对应的取文层」与「该行 `cn_base`」；
  `cn_base` 是取文基准层（未受修正表与译名替换影响），见 `资源组\剧本\schema.md` §二.1。
- **映射表（消费方必须实现，不得用特例开关）**：

  | 条目 `source` | 对应取文基准层 `cn_base` |
  | --- | --- |
  | `otr` | `otr_new`（R 版语料：本项目新译 / mig 重译） |
  | `otp` | `otp`（前奏诗；该源模块产出时其取文基准记作 `otp`） |
  | `ota` | `ota`（After Story；同上） |
  | `ot` | `ot`（本篇） |
  | `otv` | `otv`（PSV 美咲线；**W4b 2026-09-19 新增**，对应 `scene_otv.jsonl` 行 `cn_base=otv`） |
  | `np` | `np`（涅布明日香篇；**ISSUE-20260919-06 新增**，对应 `scene_np.jsonl` 行 `cn_base=np`，消费 `修正表_np说话人译名.tsv`） |

- **映射表为全集（6 项）**：`{otr→otr_new, otp→otp, ota→ota, ot→ot, otv→otv, np→np}`。
  各源构建器**声明的子集必须覆盖「本表里出现过的全部 `source`」**——只覆盖本模块自身那一项是不够的：
  装载同一张表时若映射缺项，严格实现的消费方会 **fail loud 中止**（2026-09-30 实测：`修正表_裁决20260930.tsv`
  含 `otv` 行，而 `build_scene_ot.py`/`build_scene_otp.py`/`build_scene_ota.py`/`build_scene_jsonl.py` 的映射
  当时缺 `otv`（Jsonl/otp/ota）与 `np`（ot/otp/ota）⇒ 装载即崩）。**六源映射现均补全为全集**，
  并由 `build_rulings_fixtable.py` **G7** 自动复核（「挂载本表的构建器，其映射必须覆盖本表全部 source」）。
- **唯一例外：`fix_type=term_unify` 不受本门控约束**（`term_unify` 是**词形级替换**、与取文层无关——同一术语在任何取文层都要归一，见 §三.3）。
- **被门控排除的条目必须逐条留痕**（文件 / `locator` / `原修正值` / `被排除原因` / 实际保留值），
  **不得静默丢弃**；完整性断言的口径随之变为：**范围内条目 = 生效 + 门控排除 + 未命中，三者必居其一，未命中须为 0**。
- **未登记映射的 `source`**：消费方应**报错中止**（fail loud），不得默认放行。
- **实测（W6a2，亚衣线 `s03c`）**：范围内 83 条 = 生效 **76** + 门控排除 **7**（7 条 `source=otr` 标题条目落在
  取文基准 `ot` 的共享场景上；其日文标题在本篇与 R 版逐字一致，本篇译文即正确标题）+ 未命中 **0**。
- **本规则不改任何表本体**：门控是**消费侧**的事，各修正表与 `译名替换表.tsv` 均保持原样。

## 五、根因说明（**理解这个才能正确修复**）

### B3「标题槽错位」不是标记泄漏，是译文被整条覆盖

- 22 条 `retranslate` + 21 条 A 组 + 7 条 B 组 = **50 条**，同一根因。

  其 `cn` 却是 `#鹰志$&「是时候该学习了——」$`——正是**同文件 `@1884` 那条 dialogue**
  （日文 `さて、そろそろ勉強──`）的译文。
- **剥掉标记后剩余内容 100% 是正文台词**，即：**正确的标题译文在 R 版语料中不存在** → 只能按日文标题重译。
- **闭合核验**：355 个 title 槽 = B3 22 + A 21 + B 7 + B′ 3 + 正常 302。
- **范围**：标题槽错位是 **R 版专属**——After Story 的 166 个 title 槽全库复核为 0 命中，前奏诗结构上无 `kind=title` 槽。

### B1「引号遗漏」的校验器盲区（**教训**）

- 前奏诗 6 条的原文以控制码开头（`<-4>\`、`<8>\`、`<12>\`），`工具\fix_quotes.py:34` 的判据
  `jp.startswith('「')` 恒为假 → 整批跳过；而 `verify_cn.py:24-26` 只把 `「」` 列为**译文禁用字符**，
  **从不校验「原文有 `「」` ⇒ 译文须有 `“”`」** → 既没修也没拦。
- **通用教训**：**「原文有 X ⇒ 译文必须有 Y」类校验必须双向**。只防「不该出现的字符」会漏掉「该出现却没出现」。
- ⚠️ **R 版不可用此判据**：R 版全库用日式 `「」`（约 3 万条），严格判据会**误报 3 万条**。这是全库约定差异，不是缺陷。
