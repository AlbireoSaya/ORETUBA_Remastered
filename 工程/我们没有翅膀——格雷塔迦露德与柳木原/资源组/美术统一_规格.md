## 一、为什么需要统一

六源素材目前是**各自独立**的（D2：分目录 + 来源前缀隔离）。同一张画可能同时存在于多个源：

| 源 | 图像数 | 立绘尺寸（实测） | 命名样例 |
| --- | ---: | --- | --- |
| `ot` 本篇 | 2,851 | 473×541 / 372×547 … | `ot_ai_01a.png` |
| `ota` After Story | 2,483 | 同上 | `ota_ai_01a.png` |
| `otp` 前奏诗 | 1,117 | 同上 | `otp_ai_01a.png` |
| `otr` R 版亚衣线 | 509 | 同上 | `otr_ai_01a.png` |
| `otv` PSV 美咲线 | 425 | **立绘高 630** | `otv_st_asu01a.png` |
| `np` 涅布 明日香篇 | 384 | **1280×720** | `np_asu_a01l.png` |

**实测归一化后的重叠**（去源前缀、去 `st_`、按 `<family><base><suffix>` 归并）：
- 立绘：`ot ∩ otv = 138`、Lucifen 四源共有 **158**
- CG/背景：`ot ∩ otv = 62`、`ot ∩ np = 20`、Lucifen 四源共有 75
- 系统UI：`ot ∩ otv = 106`、Lucifen 三源共有 159

**若不统一**，同一张画会有 2–4 份不同分辨率的副本，编程组按名取图时可能取到低分辨率版，且违反「美术风格统一」。

## 二、归一化命名规则（**统一产物用这个名**）

### 2.1 立绘（`chr`）

```
<family><base><suffix>.png
例：asu01a.png、ai_01a.png、kur02e.png、mis03n.png
```

`family` = 角色缩写（小写，取自原名，**不译**）；`base` = 姿势/套号（数字，**去前导零**）；`suffix` = 差分字母（表情/状态，小写，可空）。

**各源的解析规则**：

| 源 | 原名样例 | 解析 |
| --- | --- | --- |
| `ot`/`ota`/`otp`/`otr` | `ai_01a` / `asu01a` | 去源前缀 → 按 `<family>_?<base><suffix>` 拆；`family` 可为字母或字母+下划线 |
| `otv` | `st_asu01a` | **先去 `st_`**，再同上 |
| `np` | `asu_a01l` | `family=asu`；**`a01` 的 base 需与其他源比对确定**（见 §四） |

### 2.2 CG / 背景（`pic`）

```
<原名规范化>.png
例：ec28.png、bg12b.png、bg06b_3.png（分片）
```
`pic` 的原名在各源间已高度一致（Lucifen 四源共有 75 个 stem 分辨率全同），**只需去源前缀 + 小写**。

### 2.3 系统UI（`sys` / `etc`）

```
<原名规范化>.png
例：cfg1_bg.png、meswin.png、ec_bg01.png、rule000.png
```
**注意**：`otv` 的 `sys` 来自 PSV `SystemData.cpk`、`etc` 来自 `ETC.cpk`，与 Lucifen 的 `sys` 命名体系不同；**同 stem 才归并，不可强行对齐**。

**跨目录撞名 → 系统UI 侧加 `ui_` 前缀（W12，2026-09-19 增补）**：

`系统UI` 的命名空间与 `立绘`/`CG背景` 是**独立**的，但**归并后的产物名会撞车**——实测
`系统UI ∩ 立绘 = 50`、`系统UI ∩ CG背景 = 331`（并集 **381**；`立绘 ∩ CG背景 = 0`），
且**同名不同图**（例：`立绘\asu01.png` md5 `1b6d77b2…` vs `系统UI\asu01.png` md5 `6d3c98e2…`）。
按 basename 取素材会**静默取错**（超分管线已因此产生过 58 件错误产物，见 `美术统一_超分\超分说明.md` §4.1）。

**规则（唯一口径）**：`系统UI\` 下 basename 与 `立绘\` 或 `CG背景\` 相同的文件，**统一加 `ui_` 前缀**；
其余保持原名。**同一规则同步施加到 `美术统一_超分\系统UI\`**（超分产物文件名与主目录逐字节相同，只改一边会失配）。
本工程 381 个撞名文件 → `ui_<原名>.png`（如 `asu01.png → ui_asu01.png`），系统UI 其余 **1,188** 个原名不动。

- 与 `CG背景\` 侧的撞名处理（`cg_` 前缀）同构：**保留原名的一侧是「基准类别」，加前缀的一侧是「同名列」**。
- 脚本：`资源组\工具\w12_apply_ui_prefix.py`（**幂等**，`--check` 只校验；生成器重跑后必须补跑，见 `README_交付超分.md` §八）。
- **只改名、不改像素**：脚本对每个改名文件做改名前后 md5 比对，不一致即中止。

### 2.5 **统一产物名一律 ASCII**（W15，2026-09-19 增补）

**约束（唯一口径）**：`美术统一\` 与 `美术统一_超分\` 下的**全部统一产物名一律 ASCII**——
不得使用中日文等非 ASCII 字符，**含 `_底板` / `_整页` 这类中文中缀**。

**理由**：非 ASCII 文件名可能破坏 ASCII-only 管线 / 引擎字串表——旧引擎与部分打包器的字串表、
脚本路径常量、Shift-JIS / GBK 编码边界与 Windows **260 字符路径限制**都可能处理不了中文名，
重打包或运行时会出现**找不到文件 / 名字乱码 / 打包失败**（风险原记于 `美术统一\统一说明_系统UI.md` §16.2）。

**落地**：
- W11d 粒度拆分产出的 **10 个中文名**已按本约束改名：**`_底板` → `_base`**、**`_整页` → `_full`**
  （`ss_bgN_base.png` / `ss_bgN_full.png`，N=1–5），`美术统一\` 与 `美术统一_超分\` **两侧同步共 20 件**；
  对照表见 `美术统一\统一说明_系统UI.md` **§17.2**。
- 脚本：`资源组\工具\w15_ascii_rename.py`（**幂等**，`--check` 只校验不写盘，逐件 md5 前后比对，不一致即中止）。
- **生成器同样受本约束**：`unify_*.py` / `w11d_split_ssbg.py` 等若重跑，产出名须为 ASCII；
  重跑后**必须补跑本脚本**（管线顺序同 `w12_apply_ui_prefix.py`，见 `README_交付超分.md` §八）。

## 三、选源规则（**逐组独立选，保证「同一逻辑素材只有一个文件」**）

### 3.1 分组
按 §二 的**归一化键**分组。一组 = 一个逻辑素材。**组内所有候选都指向同一个统一产物**——这就自动满足「不允许同一角色在不同剧情用不同来源」的要求（因为产物只有一个文件）。

### 3.2 选优（**2026-09-19 修订：度量由「画布」改为「内容」**）

> **修订原因（主代理实测）**：`otv`（PSV）的立绘画布更大（473×630）但**四周是透明加边**，实际画面反而更小。
> 把 `otv` 内容裁出并缩放到 `ot` 尺寸比对：`asu01`/`asu01h`/`asu02`/`hiy01` 的 **MAD 仅 10–12、alpha-IoU 0.98–0.99**，
> 而本篇内部**不同**立绘的对照为 **MAD 48–79** → **确认为同一张画**，`otv` 只是缩到 94% 再套上边距。
> 内容面积比稳定在 **0.89**（系统性偏差）。
> **原规则「按画布 `w×h`」恒选 `otv`，等于每次优先选加边、丢掉真实画面**——规则本身指向了错的东西。
> **透明加边不携带任何图像信息，只是排版元数据。**

**新选优规则（按序）**：

1. **涅布优先**：若组内**通过 §3.3 宽高比门控**的候选中存在 `np` → 取 `np` 中内容面积最大者。
   （实测涅布立绘内容面积为本篇的 **1.4–2.5 倍**：`np_asu_a01x` 808×720=581,760 vs `ot_asu01` 413×558=230,454）
2. 否则取 **内容 bbox 面积（`bw × bh`）最大者** —— 即**真实画面像素最多**的那版。
3. 内容面积相同时取 **内容 `bw` 更大者**。
4. 仍相同 → 按源优先级 `ot > otr > ota > otp > otv > np` 取先者。

**清单必须同时记录**：`画布(w,h)`、`内容bbox(w,h)`、`内容面积`、`bbox偏移(x0,y0)` ——
**这样即使选中紧裁版，原端口的排版依据也不丢失**（紧裁版另有优势：bbox 直接给出立绘精确边界，便于对齐摆放）。

### 3.3 内容一致性判定（**关键**，2026-09-19 修订阈值）

组内候选**不一定**是同一张画。必须分类并记录：

| 分类 | 判据 | 处理 |
| --- | --- | --- |
| `single` | 组内只有 1 个候选 | 直接采用 |
| `same_res_same` | 同内容尺寸且 md5 相同 | 采用任一（按 §3.2） |
| `same_res_diff` | 同内容尺寸但 md5 不同 | **记入待复核**；仍按 §3.2 选一个，标 `content_conflict` |
| `diff_res_same_drawing` | 内容尺寸不同，但**内容宽高比相对差 ≤5%** | 采用 §3.2 的胜者（**同一取景的不同分辨率**） |
| **`diff_res_diff_drawing`** | 内容宽高比相对差 **>5%** | **判为不同素材，不得合并**：拆成两个独立产物（`<名>.png` 与 `<名>_alt<源>.png`），**记入待复核** |

> **宽高比门控阈值定为 5%**（原 2% 过严）：实测同一取景的组宽高比差仅 **0.4–0.9%**，
> 而真正的不同取景为 **8.8%（`kur01` 系列）、17%（`cin008`）、19%（`cin_blk2`）**；
> 2–5% 区间（如 `chi01` 系列 2.4%）多为 bbox 像素级噪声，不应据此拆组。
> **本条是唯一的「不稳定源」防护**——把不同取景合成一个素材，才会真正破坏「同一角色一套资源」。

> **⚠️ 适用范围限定（2026-09-19 用户裁决，W11f 实测后新增）**：
> **宽高比门控只适用于「立绘」（`chr`）**，**不适用于背景 / CG / 系统UI**。
> 理由：对角色立绘，同一张画的宽高比必然一致，差得多即不同素材；
> 而对背景/UI，**跨平台的宽高比差异是设计使然**——实测 `pic`/`sys` 的 198 组门控候选中
> **160 组是同一张图的 4:3 与 16:9 两版**（宽高比差恰为 **0.2500** = 1.3333 vs 1.7778），
> 本工程画布为 **1280×720（16:9）**，取 16:9 版正确 → **这些组不拆**。
> 其余「非 4:3/16:9」的组（38 组）**逐组目视裁决**。
>
> **⚠️ 规格措辞更正（2026-09-19 用户裁决，`rule*` 保持不拆）**：上句「**160 组是同一张图的 4:3 与 16:9 两版**」
> 对其中 **111 组 `rule*` 转场遮罩**表述**不准确**，应改为——
> 「**同一转场效果的两种分辨率实现，条纹/格纹间距不同；目标画幅 16:9 下取 `otv` 版**」。
> 实测：`rule030/100/110/020` 等两种分辨率**完全相同**；但 `rule000`（竖 239→180）、`rule010`（313→232）、
> `rule085`（30→23）等**条纹/格纹间距确实不同**（非同一张画等比缩放，是两种分辨率下的独立实现）。
> **结论不变：111 组保持不拆**（本工程画布 1280×720＝16:9，取 `otv` 960×544 版正确）。
> 详见 `美术统一\统一说明_系统UI.md` §九 / §十一 U1 / §十四.2。
>
> **同时**：立绘的门控拆分**必须经目视终裁**——W11e 按门控拆的 30 组中，**25 组经目视确认为
> 「同一张画的不同裁切」并已撤销拆分**（误报率 83%）。门控只是**筛出候选**，**终裁靠目视**。

## 四、涅布（`np`）的特殊处理

`np` 的命名（`asu_a01l`）与 Lucifen/PSV 体系对不上，**且其立绘为 1280×720（六源最高）**，故必须尽量归并——否则同一角色会出现「涅布版」与「Lucifen 版」两个文件，违反统一要求。

**要求**：
1. 先用**命名启发式**归并（`asu` 族 + 数字）。
2. 对未能命中的 `np` 立绘，用**内容比对**（缩放到同尺寸后算相似度；阈值由模块实测标定并说明）尝试与 Lucifen/PSV 候选配对。
3. 配对成功的 → 并入该组；**配对失败的** → 作为独立素材保留，并在待复核表说明「无法与其它源配对，已作独立素材」。
4. **不得为了凑数强行配对**。
