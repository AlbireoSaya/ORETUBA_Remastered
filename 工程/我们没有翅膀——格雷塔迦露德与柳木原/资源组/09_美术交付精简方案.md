### 4.2 WebP 不可用（**源码证据，穷举结论**）

- krkrz 1.4.0r2 **全源码树对 `webp` 0 命中**（`GraphicsLoaderIntf.cpp` 注册表无该项，无 WebP 解码器源文件、无 `libwebp` 依赖）。
- ⇒ 「**PNG → 无损 WebP，省约 30% 体积**」这一常见杠杆**在本引擎不可用**，本方案不采信任何 WebP 相关收益。
- 结论：**可用格式只落在 JPEG（有损）与 PNG（无损）/ TLG / JXR 三档上**，其中 TLG / JXR 无现成编码链路（§十二 R2）。

### 4.3 可选杠杆一览（能做 / 不能做）

## 五、压缩手段与实测收益表

> **测量方法**：PIL（`E:\ZCode Workspace\Galgame\工具\pylibs`），**每类抽样 40 件**【实测·抽样】。PSNR 为该批平均。
> **基线**：`美术统一_超分\` 的既有 PNG 字节（= 100%）。

| 手段 | 参数 | 相对原体积【实测·抽样】 | 平均 PSNR | 可否逆 | 适用 | 结论 |
| --- | --- | ---: | ---: | --- | --- | --- |
| **JPEG** | **q92** | **22.1%** | **44.3 dB** | ❌ 不可逆（母版保留可回滚） | 无 alpha 照片类（CG背景） | **采用** |
| JPEG | q88 | 18.4% | 42.7 dB | ❌ | 同上 | 不用（画质余量更小、收益增量有限） |
| JPEG | q95 | 28.8% | 46.2 dB | ❌ | 同上 | 不用（体积偏大） |
| PNG 无损重压 | zlib 最高档 / `optimize` | **立绘 90% / CG背景 RGB 88%** | ∞（无损） | ✅ | 全部 PNG | 默认关闭（改变 md5，破坏溯源） |
| 调色板化（→ P 模式） | ≤256 色 | **无效** | — | — | — | **不采用**（立绘抽样 40 件 **0 件 ≤256 色**） |
| 立绘降采样 1.5× | Lanczos | 59% | — | ❌ | 立绘 | **不采用**（裁决 3） |
| 重复件去重 | 全 4,415 件 md5 | 省 **71.7 MiB**（**95 组**，跨类别仅 3 组） | ∞（无损） | ✅ | 全库 | 默认关闭（§八.2） |

**q92 的选取依据**：44.3 dB 已高于「肉眼无损」经验阈值，且**只作用于无 alpha 的 CG背景**（软边、渐变、照片类为主，无细文字硬边）；**系统UI 与立绘均回避**（裁决 1 / 裁决 2 / §4.3）。q88 省 3.7 个百分点体积但 PSNR 降 1.6 dB，q95 体积回到 28.8%——**q92 是该曲线的拐点**。

> **q92 的落点分布（本方案的关键结构）**：`CG背景` 无 alpha 件 2,370.6 MiB 中，
> - **不在重制清单**的 **164 件 / 467.7 MiB**【实测】 → JPEG 后约 **103.4 MiB**【外推】；
> - **在 4:3→16:9 重制清单里**的 **1,003 件 / 1,902.9 MiB**【实测】 → JPEG 后约 **420.5 MiB**【外推】。
>
> ⇒ **收益大头（约 1,482 MiB）落在会被重制替换的那批上**——这正是 §九 阶段二必须 `--refresh` 收口的原因。

## 七、架构：源真值层 vs 派生交付层

### 7.1 两层定位

| 层 | 路径 | 件数 / 体积 | 性质 | 可改否 |
| --- | --- | --- | --- | --- |
| **源真值层** | `资源组\美术统一\`（**溯源基准**，1×） | 4,415 件 / 1,213.1 MiB【实测】 | 原字节复制，**不构成独立信息**（与超分侧文件名集合逐字节一致，可由六源再生） | **禁止改动** |
| **源真值层** | `资源组\美术统一_超分\`（**消费基线**，2×） | 4,415 件 / 4,355.2 MiB【实测】 | `.zcode\skills\asset-upscale\` 管线产物，UI 组 16:9 重制的**起点** | **本层只读；UI 组的重制按既有约定原位替换**（另一条线，不受本层约束） |
| **派生交付层（本方案新增）** | `资源组\美术统一_交付\` | 4,415 件 / 见 §六 C | **可再生产物**（`build_art_delivery.py` 生成），**gitignore**（与 `美术统一_超分\` 同性质） | 本层可随时重生成，**不是真值** |

### 7.2 为什么不能原地改超分集（**关键设计决定**）

| 理由 | 说明 |
| --- | --- |
| **① 超分集是 UI 组的重制起点** | `UI组任务大纲_4比3转16比9重制.md` §2.2 明文：重制的**起点 = `美术统一_超分\`**（2× 分辨率更高，比原图更适合补边/重绘的底）。 |
| **② 原位替换约定** | 同大纲 §6.1：重制产物**原位替换** `美术统一_超分\CG背景\<统一名>` / `系统UI\<统一名>`（同 `统一名`、同目录）。⇒ 该目录必须始终是「**2× PNG 母版**」的形态。 |
| **③ 若原地转 JPEG，重制起点即被污染** | 拿 JPEG（有损）当补边输入 ⇒ **有损叠加**（JPEG 块效应 + outpaint 糊化 + 再编码），且母版可回滚性丧失。 |
| **④ 破坏既有溯源体系** | 超分集承载 `超分清单.tsv` 的 **2× 几何溯源**（输入/输出画布、倍数、输入/输出 md5）与「两侧文件名集合逐字节一致」（大纲 V7）。原地改扩展名会同时打断这两条。 |

⇒ **结论：精简不能原地改超分集；精简产物另建派生交付层。** 编程组**只拿交付层**（一个目录 + 一份清单），**不再拿 1× 与 2× 两套**。

### 7.3 交付层的结构与命名口径

- **目录结构镜像超分集**：`资源组\美术统一_交付\{立绘,CG背景,系统UI}\<统一名 改扩展名>`。
- **扩展名变化口径**：**`stem` 不变、扩展名按最终格式变化**——
  - `CG背景\` 的无 alpha 件（RGB / L） → **`.jpg`**（例：`bg12b.png` → `bg12b.jpg`）；
  - **其余全部 → `.png`**（立绘全量、CG背景 RGBA、系统UI 全量）。
- **不变量（硬）**：**`母版 stem == 交付 stem`**。即交付件与超分集母版**同名不同扩展名**，`ui_` 前缀、`_alt<源>` 后缀、大小写、一律照搬。
- **编程组引用方式**：asset 串由 `ui/<原名>.png` 改为指向交付层实际文件名（`.jpg` / `.png`）；**引用一律带源前缀全路径**的既有约束（`交接说明.md` C3）不变。

### 7.4 清单契约 `交付清单.tsv`（逐件一行，4,415 行；**no-BOM UTF-8 / 制表符 / CRLF**）

实际列（**10 列**，由 `build_art_delivery.py` 的 `FIELDS` 定义）：

| 列 | 含义 |
| --- | --- |
| `类别` | `立绘` / `CG背景` / `系统UI` |
| `统一名` | 母版文件名（含原扩展名，如 `bg12b.png`） |
| `母版相对路径` | 母版在交付层坐标系下的相对路径（如 `CG背景/bg12b.png`） |
| `母版md5` | 母版文件 md5（**溯源锚点**，证明交付件由该母版派生；与 `超分清单.tsv` 的 `输出md5` 同源可比） |
| `交付相对路径` | 交付层内路径（如 `CG背景/bg12b.jpg`） |
| `交付格式` | `JPEG` / `PNG`（**唯一由「母版色彩模式」决定**：无 alpha 的 CG背景 → `JPEG`，其余 → `PNG`） |
| `交付字节` | 交付件字节数 |
| `交付md5` | 交付件 md5（PNG 复制档下与 `母版md5` 相同；转码件必然不同） |
| `是否转码` | `是` / `否`（`是` ⟺ `交付格式 == JPEG`；用于快速筛出全部有损件） |
| `是否重复组` | `是` / `否`——完全重复组标记（**只登记不删**，`--dedup` 关闭时全部照常交付；见 §八.2） |

> 清单**列名与超分集 `超分清单.tsv` 不混用**：`交付清单.tsv` 是**交付层自己的契约**，不复用 `超分清单.tsv` 的几何列（后者仍描述 2× 母版，保持不变）。

## 八、两个默认关闭的可选项及其取舍

> 两项**默认关闭**（不加参数即不生效），须在命令行**显式开启**。理由：两者的收益都以**破坏既有约定或减少可寻址对象**为代价，而收益量级（139 MiB / 71.7 MiB）**远小于裁决 1 的 1,846.7 MiB**，不值得拿契约稳定性去换。

### 8.1 `--png-recompress`（PNG 无损重压）· 默认关闭

| 项 | 内容 |
| --- | --- |
| 收益 | 省约 **139 MiB**【外推】（立绘 90% / CG背景 RGB 88%【实测·抽样】） |
| **代价（为什么默认关）** | **重编码改变文件字节 ⇒ `交付md5` 与 `母版md5` 不再相同**，且**破坏与 `超分清单.tsv` 的逐件溯源**（该表按 md5 锚定 2× 几何）。一旦开启，交付层不再能逐字节回溯到母版。 |
| 开启建议 | 仅在**明确放弃文件级溯源**（改为按 `母版路径 + stem` 溯源）时开启；开启后须在交付说明中显著标注「本层 PNG 字节已重编码，md5 溯源不可用」。 |

### 8.2 `--dedup`（重复件只留一份）· 默认关闭

| 项 | 内容 |
| --- | --- |
| 收益 | 省 **71.7 MiB**（**95 组**，跨类别重复仅 3 组）【实测】 |
| **代价（为什么默认关）** | ① **删名可能打断按名引用**（编程组 / UI 组按 `统一名` 取件，删掉的那一件若被引用即失配）；② **本工程既有惯例是「只登记不删，消费方选一」**——见 `美术统一\待归并_重复项.tsv`（25 对，**无任何文件被删除或改名**）与 `README_交付超分.md` §四补 4C。**惯例一致性优先于 71.7 MiB**。 |
| 开启建议 | 仅在**编程组明确声明按名引用白名单**后开启；开启时**只在交付层删件、母版层一字不动**，并在 `交付清单.tsv` 的 `是否重复组成员` 列标出组内保留者与退场者。 |

## 九、两阶段与重制门槛

### 9.1 阶段一（现在）：全量生成交付层

- 生成 `美术统一_交付\`（4,415 件，§六 C 口径）+ `交付清单.tsv`。
- **不触碰** `美术统一\`、`美术统一_超分\`、`超分清单.tsv`、`交付清单.tsv`（超分侧那几件）。
- 验收：§十 的 8 项检查全绿。

### 9.2 阶段二（UI 组的 16:9 重制交付后）：`--refresh` 收口

- **触发条件**：UI 组按 `UI组任务大纲_4比3转16比9重制.md` 完成 4:3→16:9 重制并**原位替换**超分集（已定：重制清单 **1,028 件 = CG背景 1,004 + 系统UI 24**）。
- **动作**：**重跑 `build_art_delivery.py --refresh`**——按新的超分集母版重建交付层与 `交付清单.tsv`。
- **为什么必须重跑**：裁决 1 的收益大头（**约 1,482 MiB**，§五）落在**会被重制替换的那 1,003 件 CG背景**上——这批件的母版字节会变，交付层**必须重新派生**，否则交付件与母版失配。

### 9.3 对 UI 组的两条要求（**跨组契约，写进重制派单**）

| # | 要求 | 理由 |
| --- | --- | --- |
| **①** | **重制产物直接按其最终格式出件**：**带 alpha → PNG；无 alpha → JPEG q92**。 | 避免「先出 PNG 再由本层二次转码」——**二次转码 = 有损叠加**（第一次 JPEG + 第二次 JPEG），且白跑一遍机时。UI 组**一次出到目标格式**，本层 `--refresh` 时对合规件**原样复制**（`是否转码 = 空`）。 |
| **②** | **重制的输入仍是 `美术统一_超分\` 的 2× PNG 母版**；**绝不可拿交付层的 JPEG 去补边**。 | 交付层是桥（`.jpg` 有损），拿它补边即**有损底 + outpaint**，接缝与画质双重劣化，且无法回滚（§7.2 ③）。重制起点**只有** `美术统一_超分\` 一个。 |

> **连带影响（如实登记）**：要求 ① 使 UI 组的重制产物若为 `.jpg`，则**超分集内该件扩展名随之变化**（`.png` → `.jpg`）——这会牵动 `超分清单.tsv`、两侧文件名集合一致性（大纲 **V7**）与 §7.3 的「stem 不变」口径。**属跨组契约变更，由主代理在阶段二前置协调**（§十二 R7）。

## 十、验收

`verify_art_delivery.py` 的 **8 项检查**（**逐条与实现一致**，本表即其 docstring 的契约；阶段一 / 阶段二收官均逐条跑）：

| # | 检查 | 判据 | 失败处置 |
| --- | --- | --- | --- |
| **1** | **件数守恒** | 交付清单行数 == 母版三类文件数；且交付目录文件集合与清单 `交付相对路径` 集合一致（无多余/缺失）。`--dedup` 生效时按去重后计；`--subset`（验收 `--limit` 小样）时放宽为「清单 ⊆ 母版 且无重复行」 | fail loud，列出差异名 |
| **2** | **逐件核对** | `交付字节` == 磁盘实际字节、`交付md5` == 磁盘实际 md5 | fail loud |
| **3** | **stem 一致性** | 交付文件名去扩展名 == 母版统一名去扩展名（§7.3 不变量） | fail loud，列出破例件 |
| **4** | **格式正确性** | CG背景 且 母版 mode ∈ {RGB,L} → 交付必须 `.jpg` 且 PIL 打开为 RGB/L；其余 → 必须 `.png` 且 mode 与母版一致；并校验 `是否转码` 列与之一致（**双向**，不信任清单） | fail loud，列出双向差异 |
| **5** | **像素尺寸一致** | 交付件 PIL size == 母版 size（转码不得改尺寸） | fail loud |
| **6** | **JPEG 画质** | 从转码件**确定性抽样**（按母版 md5 排序取前 `--sample` 件，默认 20）算 PSNR，**任一件 < 40 dB 记 FAIL**；**另对全部转码件做全量 PSNR 复算**（n=1,167）并在 `交付说明.md` 落盘 min/中位/平均——**min < 36 dB 记 FAIL（硬底线）**，36–40 dB 之间逐件列出交人工复核 | fail loud + 清单 |
| **7** | **负对照（必须做）** | 在 `临时\artdeliv_negctl\` 内构造「错误格式（PNG 塞进 .jpg 名）」「错误尺寸（真 JPEG 缩半）」两件，跑同一套检查确认对应项**确实报 FAIL** 后删除；`--no-negative-control` 可跳过（仅调试用） | 负对照不报警 ⇒ **校验器本身失效**，等同验收失败 |
| **8** | **与 `超分清单.tsv` 交叉核对** | 交付清单记录的 `母版md5` 与该表 `输出md5` 按「类别+统一名」关联一致。**严格口径为默认：发现不一致即 FAIL，不静默放行**。若 FAIL，先确认是否为 **UI 组 4:3→16:9 原位替换母版后未回填 `超分清单.tsv`**（特征＝尺寸由清单所记 1600×1200 变为磁盘 1920×1080；回填是 UI 组的义务，见其大纲 S 系列）。**确属回填未同步**才允许 `--allow-stale-cross` 放行（把「尺寸已变」类差异降级为警告；**「尺寸相符却 md5 不符」的真不一致仍 FAIL**），且须在工程记录登记待回填件数；**放行 ≠ 结案**——UI 组回填后须**不带**该开关复跑确认 `ALL_PASS` | fail loud（默认） |

> **2026-09-29 实测**：全量严格模式下 1–7 项全 PASS；第 8 项 FAIL＝「真不一致 0｜清单陈旧 275（271 CG背景 + 4 系统UI）」⇒ `--allow-stale-cross` 下 **ALL_PASS**。**收口门槛**：UI 组回填 `超分清单.tsv` 后须**不带**开关复跑至严格 `ALL_PASS`。

**画质实测结论（本轮交付层 + 主代理独立复验，2026-09-29）**：JPEG 全量 PSNR（**n=1,167**）**min 38.18 / 中位 44.02 / 平均 44.37 dB**（管线自算对照值 44.23，差 ≤0.2 dB 系逐件求值实现细节，两值并列落盘于 `交付说明.md`）；36–40 dB 人工复核清单 **10 件**（`cin086` 38.18 / `cin084` 38.59 / `bg86a` 38.85 / `cin089` 38.89 / `cin082` 38.89 / `bg86` 38.99 / `bg86d` 39.47 / `cin084a` 39.47 / `cin090` 39.90 / `cin091` 39.86）经目视 100% 对照 + 差异×8 套色**无可见差异**（证据 `临时\qs_stand_20260928\jpeg_worst.png`；其中 `cin090`/`cin091` 两件由验收 6b 全量复检补入，初轮抽检未命中）经目视 100% 对照 + 差异×8 套色**无可见差异**（证据 `临时\qs_stand_20260928\jpeg_worst.png`）。PNG 类**逐字节一致**：系统UI **1,569/1,569**、CG背景 RGBA **194/194**（全量），立绘抽 **50/50**。

**`--dedup` 开启时的附加判据**：`交付清单.tsv` 的 `是否重复组` 须标出组内保留者与退场者，且 **1 的期望件数相应下调为「4,415 − 退场件数」，退场件数须与去重组数自洽**。

## 十一、复跑命令

> **路径约定（与实现一致）**：两脚本由自身 `__file__` 反推**主工作区**（`find_main_workspace()` / `GALGAME_MAIN` 环境变量可显式指定），**源（`美术统一_超分\`）只读、产物（`美术统一_交付\`）写主工作区**——因此**在 issue 分支 / worktree 内复跑也是安全的**：读的是主工作区的母版，写的也是主工作区的交付层。脚本不读 `GRETA_DATA_ROOT`、无 `_assert_in_checkout()`（那是 C13 惯例的其他工具，不适用本管线）。

```bash
# 工作目录：checkout 根（例：E:/ZCode Workspace/Galgame/临时/wt-art-slim）
cd "E:/ZCode Workspace/Galgame/临时/wt-art-slim/工程/我们没有翅膀——格雷塔迦露德与柳木原/资源组"
export PYTHONPATH="E:/ZCode Workspace/Galgame/工具/pylibs"

# 阶段一：全量生成派生交付层（美术统一_交付\ + 交付清单.tsv）
python -X utf8 "工具/build_art_delivery.py"

# 阶段二：UI 组 16:9 重制交付后收口（按新母版重建交付层与清单）
python -X utf8 "工具/build_art_delivery.py" --refresh

# 可选杠杆（默认关闭，须显式开启）
python -X utf8 "工具/build_art_delivery.py" --png-recompress   # §八.1，省约 139 MiB，破坏 md5 溯源
python -X utf8 "工具/build_art_delivery.py" --dedup            # §八.2，省 71.7 MiB，删名

# 验收（8 项，含负对照）
python -X utf8 "工具/verify_art_delivery.py"          # 常规 8 项检查
python -X utf8 "工具/verify_art_delivery.py" --no-negative-control  # 跳过内建负对照（仅调试用；常规验收不要加）
```

> **工具落盘位置**：`资源组\工具\build_art_delivery.py`、`资源组\工具\verify_art_delivery.py`（与本方案同批交付；**两者均幂等**——`build --refresh` 在母版未变时全跳过，`verify` 本身只读）。
> **复跑顺序不可颠倒**：`build_art_delivery.py` → `verify_art_delivery.py`；`--refresh` 只在超分集母版已变更（阶段二）后使用。
