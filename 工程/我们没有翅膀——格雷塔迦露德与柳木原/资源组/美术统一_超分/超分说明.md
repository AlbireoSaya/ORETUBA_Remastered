## 三、所用模型与参数

| 项 | 值 |
| --- | --- |
| 工具 | **Upscayl 2.15.0** 的 CLI 后端 `工具\upscayl\app\resources\bin\upscayl-bin.exe`（ncnn + Vulkan） |
| 模型 | **`upscayl-lite-4x`**（Real-ESRGAN 动漫向权重，2.4 MB） |
| 放大倍数 | **2×**（`-s 2`） |
| 推理参数 | 默认 tile / 默认线程；**未开 tta**（`-x`）；输出 PNG |
| 后端 | AMD Radeon RX 5600 XT（Vulkan） |
| 处理脚本 | `.zcode\skills\asset-upscale\upscale_by_bbox.py`（本次新增，已入 skill） |
| 验收脚本 | `.zcode\skills\asset-upscale\verify_bbox_upscale.py`（本次新增，已入 skill） |

**为什么选 2× 而非 4×**：任务书 §4.3 默认 2×，目标画布 1280×720，立绘内容 2× 后约 826×1116 已足够覆盖画布高度；
4× 会让体积与耗时翻倍而无画布层面的收益。

**为什么选 `upscayl-lite-4x`**：实测同一张立绘 + 同一张背景各跑 4 个模型做 100% 像素对照，
4 款 AI 模型均远优于双线性/最近邻，而 `upscayl-lite-4x` 在**赛璐璐线条与平涂区域最干净**、
不引入照片纹理噪点。选型依据详见 `.zcode\skills\asset-upscale\SKILL.md` §四。

**2× 的产出方式**：`-s 2` 由 CLI 直出（模型在原生 4× 上推理后由后端降采样）。
实测与「`-s 4` 再用 LANCZOS 降到 2×」两条路径**画质基本无差**（`-s 2` 在文字/线稿边缘还略锐一点），
而输出像素只有后者的 1/4，故采用直出。

## 四、逐类处理流程

**统一流程（三类一致）**：

```
① 判透明：mode ∈ {RGBA, LA} 或 P 且带 transparency → 视为「带 alpha」
② 定裁切框：
     带 alpha → 用 alpha 通道的 getbbox() 实测内容包围盒
     不透明   → 内容 ≡ 画布，不裁切
③ 裁出内容区 → 交给 upscayl-bin 逐类别目录批量超分（-s 2）
④ 建 (原画布 × 2) 画布（带 alpha 用透明底，不透明用 RGB 底）
⑤ 把超分后的内容贴回，左上角 = (bbox 偏移 × 2)
⑥ 按输入通道语义保存：带 alpha → RGBA；灰度 → L；其余 → RGB
```

**逐类差异**：

| 类别 | 差异 |
| --- | --- |
| `立绘\` | **全部 1,652 件（超分时点；迁移后 1,485 件）为 RGBA**；266 件有透明加边 → 走裁切路径；其余 1,386 件内容 ≡ 画布。**（现行按类别重算：264 件裁切——2 件随 167 件归属迁移挪入 `CG背景\`，见 §二更正块）** |
| `CG背景\` | 绝大多数不透明（RGB 1,152 / L 8 / RGBA 27）；**仅 1 件需裁切**，其余整图超分。**（现行按类别重算：3 件裁切——含迁入的 2 件）** |
| `系统UI\` | 混 RGB 732 / RGBA 715 / L 111 / P 11；**165 件需裁切**；11 个 P 模式文件均**不带 transparency** → 按不透明处理，输出 RGB |

**⚠️ 输出模式不是统一值**（这是刻意的）：**保留输入的通道语义**——
带 alpha 的仍为 RGBA（2,394 件）、灰度仍为 L（119 件）、其余 RGB（1,895 件）。
任务书 §4.4「不得改变透明度（alpha 通道必须保留）」即此意；**没有把 RGBA 压成 RGB，也没有给不透明图加 alpha 通道**。

### 4.1 两处同源缺陷及其修复（如实登记）

**缺陷一 · PNG 产物 58 件错误（已重做）**

首次全量运行后自检发现 **58 件（立绘 50 / CG背景 8）输出错误**。
**根因**：处理脚本内部用**文件名**索引元数据，而三个类别之间存在**同名文件**
（上游 README §六 即载明「立绘∩系统UI = 50、CG背景∩系统UI = 331」，合计 **381 组**），
同名条目互相覆盖。**元数据查错的规模是 381 组，而真正改变了结果的只有 58 件**——
差额来自：未裁切且目标通道一致时命中「直接复制」快路径，结果仍然正确。
**处置**：改为按 `(类别, 文件名)` 复合键索引 → 删除这 58 件输出 → 用修复后的脚本精确重做 →
**重跑全量自检，4,408/4,408 通过**。

**缺陷二 · `超分清单.tsv` 341 行几何列错误（已按磁盘实测重写）**

同一根因还污染了**清单本身**——首版清单也是用文件名键生成的，381 组同名条目中有 **341 行**
（`CG背景` 323 行 + 18 行 ±1 px 舍入）的 `输入画布 / 输入内容bbox / 输出画布 / 输出内容bbox`

> ⚠️ 这些行的 **PNG 本身是对的**（命中快路径），**只有清单声明错**——
> 所以「逐件核对 PNG」的自检**抓不到它**，必须另做「清单声明 vs 磁盘」的核对。

**处置**：按**磁盘实测**重写全部 4,408 行的几何列与 md5（**PNG 未改动**），
并在验收脚本 `verify_bbox_upscale.py` 中**新增「输出清单声明 vs 磁盘」核对项**（【7】），防止再犯。

**本说明与 `超分清单.tsv` 反映的是两处缺陷均修复后的状态**；
