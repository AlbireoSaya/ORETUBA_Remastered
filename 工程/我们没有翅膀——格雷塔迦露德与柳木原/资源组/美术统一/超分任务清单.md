## 四、处理流程（**按序执行，不得跳步**）

### 4.1 分类处理

| 类别 | 处理方式 |
| --- | --- |
| **立绘**（RGBA，透明底） | **必须按内容 bbox 裁切后超分**（见 §4.2） |
| **CG背景** | 多为不透明（`内容bbox == 画布`）→ 可整图超分 |
| **系统UI** | **混两类**：`内容bbox == 画布` 的整图超分；**RGBA 透明底的（如 `tl_*`、`gl_*` 文字按钮）必须按 bbox 裁切**。逐文件用 `内容bbox(w,h)` 与 `尺寸(w,h)` 比较即可判定 |

### 4.2 **关键：透明底图像必须裁切后超分**（立绘与部分 UI）

```
① 按 内容bbox(w,h) 与 bbox偏移(x0,y0) 从原图裁出内容区
② 对内容区做超分（× N）
③ 建一张尺寸为「原画布 × N」的透明画布
④ 把超分后的内容贴回，左上角坐标为「bbox偏移 × N」
⑤ 以原文件名保存
```

**为什么必须这样**：立绘四周是**透明加边**——上游已特意按「内容面积最大」选源、**排除了加边版**。
若对整张画布超分，会**把透明区一起放大**：浪费算力，且透明/半透明边缘放大后会产生**边缘伪影**。
按 bbox 处理后再贴回，**视觉效果与整图超分一致，但省掉透明区的算力与伪影风险**。

> **等价性说明**：若你的模型/流程不方便裁切，**整图 ×N 超分也是可接受的**（结果等价，只是慢、且透明边缘可能有轻微伪影）。
> **但绝不允许只超分内容区就输出紧裁图**——那会丢掉画布与偏移，破坏排版。

### 4.3 放大倍数

- **默认 2×**（推荐）。
- 目标工程画布为 **1280×720**。立绘内容多为 413×558 量级，2× 后约 826×1116，足够覆盖画布高度。
- **4× 亦可接受**（游戏端会自行缩小），代价是体积与耗时翻倍；**不建议超过 4×**。
- **同一次交付内倍数必须统一**（便于编程组整体缩放）；若个别文件走了特殊路径，必须在 `超分清单.tsv` 的 `倍数` 列逐行标明。

### 4.4 不得做的事

- ❌ **不得改动输入目录** `美术统一\` 的任何文件（那是基线，只读）。
- ❌ **不得改名、不得合并、不得拆分、不得删减**——输出文件数必须 == 4,408。
- ❌ **不得改变宽高比**（不得为「填满画布」而拉伸）。
- ❌ **不得改变透明度**（alpha 通道必须保留；不得把 RGBA 压成 RGB 白底）。
- ❌ **不得对 `未识别` / `未判定` 的素材做任何「补画」或「猜内容」**——
  立绘 `未识别` 182 件、CG背景 `未判定` 221 件，它们的用途尚未判读，**只做纯超分，不要脑补**。
  > **事后补注（2026-09-19）**：该 403 件已于 W12 逐件判读完毕（`未识别` / `未判定` 现均为 0 件）；本条纪律在判读前有效，现已无适用对象。
- ❌ **不得输出到工作区外**（一切产物必须落在 `E:\ZCode Workspace\Galgame\` 内）。

## 七、附：上游为何这样交付（背景，理解后更好执行）

六源（本篇 / After Story / 前奏诗 / R 版亚衣线 / PSV 美咲线 / 涅布 明日香篇）的同一张画各有副本，
且**分辨率与画布各不相同**。上游做了三件事：

1. **按归一化名归并**：`ot_asu01a.png` / `otv_st_asu01a.png` 等归为同一个 `asu01a.png`，
   确保**同一逻辑素材只有一个文件**（用户硬要求：不允许同一角色在不同剧情用不同来源的立绘）。
2. **按内容面积选源**（不是按画布）：`otv` 的画布大是因为**透明加边**，实际画面反而比 `ot` 小。
   实测同一张画 `otv` 的内容面积是 `ot` 的 **0.89**（MAD 10–12、alpha-IoU 0.98–0.99 确认同画）。
   改按内容面积后 **236 组改选**，**平均多拿 14.32% 面积**（最大 +75.7%）。
   → **所以你拿到的已经是被排除加边、内容最大的那一版**，请务必按 bbox 处理，别把加边又放大回来。
3. **涅布优先**：`np`（涅布）立绘内容面积是 `ot`（本篇）的 **1.4–2.5 倍**，凡有同画版本一律采用 `np`。

**来源候选 8,022 → 交付 4,408**，消除重复 3,614 个（45.1%）。
