## 三 ★ 关键结论

### 3.1 完整执行模型（浓缩版；详版见 `逆向引擎\执行模型.md` 与引擎规范 §13）

- **Lucifen 是栈式字节码 VM，恰 47 个 opcode**（`0x00..0x2E`）。
  入口 **`VA 0x433650`**；分派表 **`VA 0x433B54`**（全 exe 唯一一张 47 项 indexed `jmp` 表）；**VM 上下文 `ctx` = 脚本管理器 `+4`**。
- **解释器主循环 5 条指令**：
  `0x433675 mov eax,[esi+8]`（pc）→ `0x433678 mov ecx,[eax]`（op）→ `0x43367A lea edi,[eax+4]` → `0x43367D mov [esi+8],edi`（pc++）
  → **`0x433680 jmp dword ptr [ecx*4 + 0x433B54]`**。唯一调用者 `0x4252F9`（在调度器 `sub_4252F0` 内）；
  **帧循环 3 处**（`0x4012EC`/`0x401348`/`0x401AF3`）以 `ecx=[app+0x19C8]`（manager 单例）调用。
- **opcode 语义（关键项）**：`0x04`=**CALL**（`pc = *operand`）、`0x05`=**CALLNATIVE**（`*op2 = op0(op1)`，操作数 = `maps[1]` 的 handler 下标）、
  `0x08`=**PUSH**、`0x0C`=**ADDSP(-k)**（返回后丢弃 k 字节实参，`argc = k/4`）、`0x03`=把 `ctx[0x10]` 写进尾槽。全 47 表见 `执行模型.md` §4.4。
- **★ `[04][V]` 是 op `0x04` 的 `CALL`，`V` = `func_lib.sob` 代码缓冲内的子程序入口**（命令实现体）。
  装载期 `sub_424D30` 把该字重定位为 `V + [mgr+0xD4]`（`[mgr+0xD4]` = func_lib 基址）。
  ⇒ **引擎里没有命令名表、没有「命令名 → 实现」的 switch**——这就是「exe 内搜命令名 0 命中」的成因
  （**注意**：引擎**有**一张 47 路 **opcode** switch；缺的是**命令名**层，别混）。
- **六表在引擎侧**：`maps[0]`→`[mgr+0x58]`（12 B/条，**user_var 变量记录**，`value` = 变量下标）；
  `maps[1]`→`[mgr+0x38]`（4 B/条，**原生 handler 向量下标**，op `0x05` 用它）；`maps[2]`→`[mgr+0x48]`（具名符号，仅 3 个内建）；
  `maps[3]`→`+ [mgr+0xD4]`（**func_lib 代码偏移 / 重定位位图表**）；`maps[4]`→`+ 本模块缓冲`（本模块内串/代码）；
  `maps[5]` 计数须 = 0。**`maps[0]`（变量）与 `maps[1]`（handler）是两套独立编号空间**（上一轮曾混为一谈，已订正）。
- **装载路径**：SOB0 场景（`0x42502B`，`is_lib=0`）、SOB2 库 `func_lib`（`0x4248B2`，`is_lib=1`）、SOB1 变量 `user_var.sob`（`0x424630`，**内联，不走 `sub_424D30`**）。
  `is_lib` 分流在 `0x424EE3`；**只有场景（`is_lib=0`）**才 `ctx.pc = 缓冲`（`0x424EFF`）并压哨兵（`0x424F06`）。
- **静态可达性 = 是（反汇编层 100%）**：① 全 exe 恰 1 张 47 项分派表；② 47 handler 逐个读出；
  ③ 对 **412 个真实 SOB 走查，非法 op 位置 = 0**（对照数据侧 `BASE` 表 = **4172** ⇒ `BASE` 有 6 个 tag 与引擎不符：`00/08/0D/13/14/2E`）；
  ④ 用**引擎自带重定位表**反验：`op 0x05` 操作数 ∈ `maps[1]` **62245/62245 = 100.0000%**、`op 0x04` ∈ `maps[3]∪maps[4]` **113166/113166 = 100.0000%**；
  ⑤ `maps[1]` 的 0/1/2 与调度器 `[0x50382C]` 闭环。
- **跨构建验证**：`OT_PREDE.EXE`（前奏诗）**被 `.settec` 加壳**（`.text` 熵 7.763 vs ORE 6.529）**静态不可用**；
  改用**前奏诗 `otp` 68 文件**数据侧验证（op 0x05 `10111/10111`、op 0x04 `19119/19119`，均 1.0000）。
- **订正**：`maps[0]` → `[mgr+0x58]` 是 **user_var 变量记录**（本作 `ot` 916 条），**不是**「内建符号表」（旧说法已订正）。

### 3.2 软表语义（六表，**订正 §12.1 旧表**）

| 表 | 语义 | 判据 / 去向 |
| --- | --- | --- |
| `maps[0]` | （暂定）**对外/共享符号的引用解析表**：key = 页引用字偏移；value = 被引用对象全局编号（0..915，896 个在用） | 与 `maps[4]` 构成引用站点**精确二分**（`ot` 全库 476,575）；「符号」二字是**命名假设** |

## 四 本会话新增的坑（接坑 101 之后）

102. ★ **「V 是命令标识」只是表象**：真正的机制是 **`[04][V]` = op `0x04` 的 `CALL`，`V` = `func_lib` 代码缓冲内的子程序入口**（装载期重定位为 `V + func_lib 基址`）。别再把「命令身份」当成一张待找的表。
103. ★ **「引擎里没有 switch」这句话本身是错的**：引擎**有**一张 **47 路 opcode 分派 switch**（`0x433680 jmp [ecx*4+0x433B54]`）；缺的是**命令名**层。exe 内搜命令名 0 命中的真因是「**命令名根本不在 exe 里**」（现用名是从 PSV `:Tasktype` 借来的）。
104. ★ **数据侧反推的长度表会错**：`decode_sob0.BASE` 有 **6 个 tag**（`00/08/0D/13/14/2E`）与引擎不符（如 `BASE[0x08]=3`，真值 **1**）；用 BASE 走查产生 **4172** 个非法 op 位置，而引擎真值是 **0**。长度真值**只在 `0x433B54` 各 handler 代码里**。
105. ★ **「V 是每源本地」过强**：正确是「**每 build 组本地**」——`ot`/`otr` 同系列（`otr ⊆ ot`，差 6），`otp` 是另一套。**别把 `V` 号跨 build 搬用**。
106. ★ **func_lib 节点没有长度字段 ⇒ 节点边界不可判**：用窗口读串会**越窗读到邻节点**（实测 9 个「越窗实锤」、12 个「归属未定」）。凡「在某 V 处读到某串」，必须报**与下一个 V 的距离**并做**窗口敏感度测试**（多窗口首串一致才可采信）。
107. ★ **场级共现会「假通过」**：全覆盖型 type（`Tag`/`SceneJumpDialog` 场覆盖 = 1.000）让**任何常见 V 都 P=1.0**；实测口径②下 **51 个 V** 都能「过闸」。必须改用「唯一 event 标签（`D_strict`）」＋「计数签名」，并设**基准率护栏**。
108. ★ **`0x1C8D0` 的「否证」是错判**：它每场恰一次，上一轮据 PSV type 共现否证「章节名」；本轮发现其**唯一实参就是本场标题**（`358/358` 直证）⇒ 改判**采纳**。**基于 type 共现的否证不可靠**。
109. ★ **PSV type 粒度粗** ⇒ 同一 type 被多个 V 认领（`SePlay`←2 个、`SeStop`←2 个、`SpriteBG`←3 个）。这**不是判错**，是对实参细分不足；引「某 type 的唯一 V」前先看是否重复认领。
110. ★ **别把「候选」当「已定名」用**：标签表有**两道闸门**（导出侧 `verdict=='采纳'` ＋ 消费侧 `load_v_labels()` 再过滤）挡候选/未定 ⇒ 候选 15 / 未定 35 **一条都进不来**。
111. ★ **`--fade-source` 默认 off 是保守而非疏漏**：Fade **场级可信**（recall 1.000 / precision 0.950），但**seq 落点只有 0.765–0.918**；**渲染前必须先复核 seq 对齐**，否则会把淡出打到错的时机。
