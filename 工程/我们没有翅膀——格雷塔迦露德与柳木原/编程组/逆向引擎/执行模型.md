## 一 Q1 · 装载全流程（SOB0 / SOB1 / SOB2 三种头）

### 1.1 三种 magic 与三条装载路径

| magic | 用途 | 装载函数 | 引擎侧处理 | 证据 |
| --- | --- | --- | --- | --- |
| **SOB0** | 场景脚本（412 个，含系统脚本） | `sub_424FA0`（按名） | `cmp dword[eax],'SOB0'`；校验通过后 `sub_424D30(is_lib=0)` | `0x42502B cmp [eax],0x30424F53`；`0x4250E1 call 0x424D30` |
| **SOB2** | 共享库 `func_lib.sob` | `sub_424460`（初始化内） | `cmp dword[eax],'SOB2'`；`sub_424D30(is_lib=1)` | `0x4248B2 cmp [eax],0x32424F53`；`0x4248E6 call 0x424D30` |
| **SOB1** | 变量表 `user_var.sob` | `sub_424460`（**内联，不走 sub_424D30**） | 见 §1.3 | `0x424630 cmp [ebx],0x31424F53` |

```

         | u32 ss | u32 se | 代码区 [header_end, header_end+ss) | 串区 [ss, se)
header_end = 8 + table_size + 8
```

### 1.3 SOB1（`user_var.sob`）走哪条路 —— **完全解出**

在 `sub_424460` 内联处理（`0x42460F..0x424897`），**不调用 `sub_424D30`**：

```asm
0x00424630  81 3B 53 4F 42 31   cmp  dword ptr [ebx], 0x31424F53   ; "SOB1"
0x00424656  8B 73 04            mov  esi, [ebx+4]                  ; esi = payload_len
0x00424659  83 C3 04            add  ebx, 4
0x0042465C  83 C3 04            add  ebx, 4                        ; ebx → payload 起点
0x00424663  85 F6               test esi,esi
0x00424667  56                  push esi
0x00424668  E8 ..               call malloc                        ; ① malloc(payload_len)
0x00424678  89 45 74            mov  [ebp+0x74], eax               ;    副本 #1

0x004246CB  03 D8               add  ebx, eax                      ; ebx += payload_len

0x004246D6  ...  8D 7D 54        lea  edi,[ebp+0x54]                ;    向量（begin=+0x58）
   ...      循环 916 次：读 [ebx]（2B 标志 + 4B 偏移 + 4B 字段）→ 追加 12B 记录
```

## 二 Q2 · 重定位 `sub_424D30` 完整语义

签名：`int __thiscall load(this, void* data_after_magic, char* name, int idx, int is_lib)`（`ret 0x10`）。
逐步（本轮补全了上一轮没写透的头部与尾部）：

```asm
; ── 头部：定位六表与 ss/se ────────────────────────────────────────────
0x424D54  mov eax,[esi]      ; table_size        （esi = arg1 = data）
0x424D56  add esi,4
0x424D59  mov ebp,esi        ; ebp = 六表区基址（循环 A..E 用 ebp 前进）
0x424D5B  add esi,eax        ; esi → ss
0x424D5F  mov eax,[esi]      ; ss
0x424D61  mov ecx,[esi+4]    ; se
0x424D67  mov [esp+0x1C],eax ; 暂存 ss（*）
0x424D6B  mov [esp+0x30],ecx ; 暂存 se（*，正好覆盖掉 arg1 的栈槽）
0x424D6F  add esi,4          ; esi → 代码区起点
; ── 分配 12B 模块描述符 + malloc(se) + 整段拷贝 ───────────────────────
0x424D72  call malloc(0xC)   ; edi = 12B 描述符
0x424DC8  mov eax,[esp+0x2C] ; = se（*）
0x424DD0  push eax
0x424DD4  call malloc        ; ebx = 模块缓冲基址（代码+串 合并）
0x424DEB  rep movsd (ecx=se) ; 把 [代码区, se) 整段拷进 ebx
0x424DD1  mov [edi+8],edx    ; 描述符.f8 = arg3 = 模块下标 idx
; ── 六个重定位循环 A..E（见 §1.2）─────────────────────────────────────
; ── is_lib 分流 ───────────────────────────────────────────────────────
0x424EE3  mov al,[esp+0x38]  ; = arg4 = is_lib
0x424EEB  mov [esi+0xD4],ebx ; is_lib=1 → 0xD4 = 本模块（func_lib）基址
0x424EF9  mov [esi+0xD8],ebx ; is_lib=0 → 0xD8 = 本模块（场景）基址
0x424EFF  call 0x4335A0      ; ctx.pc = ebx   ← **把缓冲设为 VM 的 pc**
0x424F06  call 0x4335F0      ; 压入哨兵 0（*sp=0; sp+=4）
; ── 尾部：按 [esi+0x1C]（ctx.hookOn）决定是否构建「模块运行对象」─────
0x424F0B  mov al,[esi+0x1C]; test al,al; je 0x424F83
0x424F52  ... 0x49D6A0/0x49D780 构造一个 `push 0x18`（即 malloc(0x18)）的对象，参数 (&mgr+0xC,&mgr+0x10,&mgr+0x14)
```

**`[this+0xD4]` / `[this+0xD8]` 的确切身份**（本轮）：

| 字段 | 写入点 | 值 | 消费点 |
| --- | --- | --- | --- |
| `[mgr+0xD4]` | `0x424EEB`（唯一非零写；构造函数 `0x422331` 清零） | **func_lib 模块缓冲基址** | `maps[3]` 重定位（`0x424EA1`）；布尔门 `0x425232/0x425293`；**取值器辅助函数 `0x4183B6`**（`mov eax,[ecx+0xD4]; ret`；**不在 handler 注册表内**，M4 已证） |

> 全 `.text` 扫描（`xscan.py --disp 0xD4,0xD8`，215 处命中）确认：**属于本管理器类**的

### 3.4 handler 的调用约定（回答「命令表结构」）

每个 handler 形如（`0x417F50` 为例）：
```asm
0x417F50  mov eax,[esp+4]        ; arg = 指向「实参结构」的指针
0x417F57  mov ecx,[eax]          ; selector = arg[0]
0x417F5F  cmp ecx,0xB ; ja default
0x417F69  jmp dword ptr [ecx*4 + 0x418180]   ; 按 selector 分派（表内联于 .text）
0x417F70  mov al,[eax+4] ; [app+0xd74]=al
0x4183B6  mov eax,[ecx+0xD4]; ret            ; ← getter：返回 func_lib 基址
0x4183A8  mov eax,[ecx+0xD8]; ret            ; ← getter：返回场景缓冲基址
```
⇒ **handler = 一组「按 selector（arg[0]）分派的原生原语」**，参数从 `arg[1..]` 读；
多数 handler 直接操作全局 **app 单例 `[0x503248]`** 与管理器 `[app+0x19C8]`。

> ⚠️ **本形（`0x417F50` 式：首句 `mov eax,[esp+4]` 取参 + selector 分派）约占四成**，
> **不是全部**：789 个 handler 中首句严格为此形者仅 **304（38.5%）**。**逐格分档见 §5.3**（判据写死、
> 脚本 `xhand.py` 可复现）。其余 485 = 首句 `mov edx,[esp+4]`（20）＋ `push`/`sub`/`jmp`/`xor` 序言（301）
> ＋ 不取 `[esp+4]` 的其它 `mov`（164）。
**handler 名（语义名）不在二进制里**——它属于编译器的符号表；要命名须逐个反汇编。
**订正（M4，`ISSUE-20261008-02`）**：**789 个「注册」handler 中纯 getter = 0**（旧述「很多是
`mov eax,[ecx+0xNN]; ret` 型 getter、可自动分类」**不成立**；被当范本的 `0x4183A8`/`0x4183B6`
**不在注册表内**，是 handler 区内的 thiscall 辅助函数）。替代事实：**178 个 leaf 存取器**（22.6%，
多为读全局单例字段）、**147 个含 selector 分派**（表项以 14/7/4 为主）、**档1（首句
`mov eax|ecx,[esp+4]`）= 304**。逐 handler 产物见 §八 项 3 与 `handler命名_说明.md`。

### 4.3 「如何取一个节点 / 如何据 V 找实现 / 如何传参」—— 全解

1. **取节点**：`op = *pc++`（线性字流，无双字对齐、无长度前缀）。
2. **据 V 找实现**：**不存在「V → handler」查表**。`[04][V]` 中的 `V` 已被装载期重定位成
   **func_lib 缓冲内的真实指针**；`op 0x04` 直接 `pc = *operand` 跳过去执行——**V 就是实现体地址**。
3. **传参**：参数由前面的 push 指令（`0x08` 等）压入**操作数栈**；`[0C][k]` 在调用返回后
   `sp -= k` 丢弃参数；`[03][REF]` 把 `ctx+0x10`（= **VM 返回值寄存器 RETVAL**，见 §4.1）写进 REF 槽。

## 五 Q5 · 参数模型（`k` / `[08][arg]` / `[04][0C][03]` / 控制串）

### 5.1 命令节点 `[04][V][0C][k][03][REF]` 的引擎消费（逐字）

以 `s01_02a.sob` cell 6..13 为例（`xdata.py --around`，`[08][title] [04][V=0x1C8D0] [0C][k=4] [03][REF]`）：

| 字 | op | 引擎动作 |
| --- | --- | --- |
| `[08][arg]` | 0x08 PUSH | 把 `arg` 压入操作数栈。**⟦订正（ISSUE-20261008-04 B4 R6，2026-10-08）⟧** 旧述「`arg` 是 maps[0/3/4] 引用字（重定位后为指针）」**过强**：**`op 0x08` = `push(操作数字)`**（handler `0x43372E mov eax,[edi]; push eax`），操作数**可为立即数**——实测 `arg` 为引用字者仅 **83204/321693 = 25.86%**（otp 0.2527） |
| `[04][V]` | **0x04 CALL** | `push(返回地址=下一个字)`，`pc = V`（V 重定位后 = `func_lib_base+V`，即**命令实现体**） |
| `[0C][k]` | 0x0C ADDSP | 返回后 `sp -= k` ⇒ **丢弃 k 字节实参**（`k = 4×实参数`） |
| `[03][REF]` | 0x03 | `*REF = RETVAL`（把 RETVAL 写入尾槽；`ctx+0x10` = VM 返回值寄存器，见 §4.1） |

- **`k` 的含义确认**：`k` 是「实参总字节数」，正好等于前面被 push 的实参字节数；
  `argc = k/4`。`decode_sob0` 的 `node_args`（第 t 个实参 = `cells[node-1-2t]`）与引擎一致。
- **`[08]` 是「压入」而非「节点的一部分」**：一次命令的实参个数 = 前面连续的 `[08]` 项个数。
- **`REF` 是模块内槽**（maps[4] 指向串区的一个空串槽），作**续行地址的落点**。
- **返回值**：原生调用（op 0x05）的返回值写入其第 3 操作数（dest）；命令子程序内部的
  「结果」也通过这些写内存的 op（0x1F/0x20/…）落到变量槽。

### 5.2 控制串（`c` / `l<2` / `!l` / `_` 等）在引擎侧怎么被消费 —— **不是 opcode**

**结论：控制串是普通字符串操作数，引擎不解释它。**
机制：串区里的字符串由 `maps[4]` 引用字给出（重定位后 = `模块基址+偏移` = C 字符串指针）；
脚本把它 `push`（op 0x08/0x09）后交给原生 handler（op 0x05）。**字符串的「语义」全部由 handler 决定**。
⇒ 上一轮 `decode_sob0.py` 的 `CTRL_ROLE` / `CTRL_STRINGS` 是**启发式**（把控制串与 PSV 金标对齐
推断角色），**不是引擎语义**；引擎只看 handler 的 selector 与字节。
这正是「exe 里搜命令名 0 命中」的根因：**命令语义载体是 func_lib 字节码 + exe handler，二者都不以名字相连**。

### 5.3 实参如何变成 handler 的入参（op 0x05 的 `arg`）

`0x05` 的三操作数是 `(fn, arg, dest)`：`fn` = handler 下标（∈ `maps[1]`）、
`dest` = 结果落点（∈ `maps[0]/[3]/[4]`）。

> **⟦订正（ISSUE-20261008-04 B4 R5，2026-10-08）⟧ 删去「`0x05` 的实参是重定位后的引用字」这一定性。**
> 实测 `op 0x05` 的**第 2 操作数（`arg`）63241/63241 全部为非表立即数**；handler
> （`0x4336F4 mov edx,[eax]` → `0x4336F9 push edx`）**按值 `push` 该操作数字、不解引用**。
> ⇒ 旧述「`arg` 是一个指针（重定位后的引用字）⇒ 原生函数的入参是脚本栈上某结构的地址」**应删**。
> 保留的结构事实只有：op `0x05` 的 `dest` 落在 `maps[0]/[3]/[4]`（变量槽或模块内地址），
> 且脚本侧可用 op `0x28`（取栈槽地址）在操作数栈上搭出入参结构。

**handler 首句形态分档**（`789` 个不同 handler；**判据写死、脚本可复现** = `xhand.py`）：
判据 = `xreg.py` 同款枚举去重得 789 个 handler VA；取**从 handler VA 起反汇编的第 1 条指令**（`skipdata=True`）；
分类键 = capstone 5.0.7 的 **(mnemonic, op_str) 全等**（本工作区 capstone 版本 = 5.0.7）。
**不做任何「前 N 句扫描」**——早期文档的「12 句内 `[esp+4]`」三格子档口径不自然、不可逐格复现，**已删除**。

## 十三 `0x2C3C` 的定性：每句台词的「文本行推进门」（ISSUE-20261008-04 B2，2026-10-08）

> **来源**：`子代理工作区\ISSUE-20261008-04\M2\未定V攻坚_说明.md` §2（B2；经一审 `复核_B2.md` 的
> 窗口口径订正后并入）。本节**订正** `SOB0解码\软表解出_说明.md` §五的「带一个内联代码块的命令」
> 表述，并**结项** §六 提到的「57,872 条形态族」。

### 13.1 节点模板与语义

`ot` 全库 `[04][0x2C3C]` 共 **57,859** 站（占 `maps[3]` 项的 **51%**），**全部**是同一条模板：

```
[08][arg]                 ; PUSH arg            arg ∈ {0, 1}
[04][0x2C3C]              ; CALL 0x2C3C
[0C][04]                  ; DELARG 4（丢 1 个实参）
[03][REF]                 ; STVAL：把 RETVAL 写进「下一条指令的操作数槽」（REF 位移恒 +8）
[1E][slot][target]        ; JZ：if (slot == 0) goto target else fallthrough
```

引擎侧读法：`op 0x1E`（JZ，handler `0x433945`）的 `op0` **按地址读**（`cmp [edi],0`），
而 `[03][REF]` 恰好写进同一地址 ⇒ **自改写的条件分支**：
`if (0x2C3C(arg) == 0) 跳到 target（下一句），否则落空 RET（挂起，等玩家推进）`。

⇒ **`0x2C3C` = 每句台词的「文本行推进门」**：返回非 0 = 「本句未结束（等推进）」，返回 0 = 「进入下一句」。
脚本用 `RET` 把控制权交回引擎循环，下一帧再进来 —— 这就是「对话框黑箱」本体。
其实现体（1077 条指令）含循环回边、8 次 `CALLN h9`、`CALLN h668`（音频播放）、内嵌串 `PIC\%s.ELG`
（消息框/立绘部件装载）⇒ 与 **消息窗渲染 + 推进 + 效果音** 一致。

### 13.2 四条不变式（**可失败**；实测值见下）

| 不变式 | 实测 | 若失败会怎样 |
| --- | --- | --- |
| 尾随 op 恒 `0x1E`（JZ） | **57859/57859** | 出现别的 op ⇒ 「门控」假设被推翻 |
| 实参恒 ∈ {0,1} | **57859/57859** | 出现 2/大数 ⇒ 它吃「模式/编号」，不是布尔门 |
| 尾 REF 位移恒 **+8**（写进下一条指令的 `op0` 槽） | **57859/57859** | 位移变化 ⇒ RETVAL 不写「下一条指令的操作数槽」 |
| 自改写分支（`[03]` 写 JZ 的 `op0` 槽 ∧ JZ 按地址读） | 由模板 / `op 0x1E` 语义直证 | 若 JZ 解引用 ⇒ 不是自改写条件分支 |

**窗口口径（如实写）**：与「前邻 `CALLN h462`（文本显示）」的绑定**依赖窗口宽度**——
**10 字窗口**（搜门 `[04]` 前第 4–13 字）命中 **57834/57859**；**放宽到 20 字窗口**即 **57859/57859 = 1.0000**；
最近 h462 距门步数分布 = `{9: 57834, 18: 24, 21: 1}`（10 字窗口漏掉的 25 条在 20 字窗口内**全部补齐**）。
⇒ **「前邻 h462」是该窗口内的实测规律、不是「严格同现」的结构律**（原「`arg=1` ⟺ 前邻无 h462」的说法**作废**）。
「`arg=1` = 同一行块内的**第二个门**」由**裸字节实读**得出（`s01_02c.sob` / `s04_24a.sob`），**与窗口无关**。
