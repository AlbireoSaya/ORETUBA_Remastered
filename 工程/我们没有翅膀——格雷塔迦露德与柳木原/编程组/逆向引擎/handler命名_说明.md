### 1.5 ★ 重要更正：**交接假设「大量 handler 是 `mov eax,[ecx+disp]; ret` 型 getter」不成立**

**789 个注册 handler 中，纯 2 条 getter = 0 个。** 交接里引作范本的 `0x4183A8`（`mov eax,[ecx+0xD8]; ret`）
与 `0x4183B6`（`mov eax,[ecx+0xD4]; ret`）**经注册表枚举验证：二者都不是注册 handler**
（不在 798 个注册调用点配对的 789 个 VA 内），它们是 handler 区内的**普通 thiscall 辅助函数**。
⇒ 「大量 getter」的印象来自把注册集合与「handler 区里的所有函数」混为一谈。**注册 handler 里没有纯 getter**。

替代发现：**178 个 leaf 存取器**（无 call/jmp 止于 ret），其**读法多为「读全局单例字段」而非 `[ecx+disp]`**，如
`h22 = 0x419280`：`mov eax,[0x503248]; mov eax,[eax+0x1954]; ret`（app 字段 getter）。

## 二、② V ↔ handler 的引擎自证关联（机制、判据、边界）

### 2.1 机制（据 `执行模型.md` §13 实装）

命令实现体 = `func_lib` 缓冲内偏移 `V`（op `0x04` CALL 的操作数）。实现体内用 **op `0x05` CALLNATIVE**
调原生 handler，其操作数 site ∈ func_lib 的 `maps[1]`，**value = handler 向量下标**
（装载器循环 B：`code[off]=[mgr+0x38][value]`）。故解析 func_lib → 找 op `0x05` → 取 `maps[1]` value
⇒ handler 下标；把每个 op `0x05` 归到某个 `V` 即得关联。func_lib 内 op `0x04` 的目标（`maps[4]` value
= 本模块偏移，因 func_lib 的 `maps[3]` 计数恒 0）⇒ **内部子程序入口**，可沿调用图传递。

### 2.2 判据（**两条，分开记，不混报**）

| 判据 | 定义 | 覆盖 |
| --- | --- | --- |
| **L1 直接窗口关联** | 从 `V` 线性走查窗口 `[V, V+W)` 内 op `0x05` 的 handler 序；主口径 **W=0x1000**；窗敏感 `W∈{0x200,0x1000,0x4000}` | 全 V 下 op0x05 = **1758**，命中 **147** 个 handler |
| **L2 调用图闭包关联** | 从 `V` 沿 op `0x04` 内部调用闭包（深度≤4）可达入口的 L1 结果 | **166** 个 handler |

**「core」= W=0x200（保守口径）**；**「exp」= W=0x1000（宽松口径）**。命名以 core 为主、exp 仅作提示。
（§2.2 的覆盖统计 1758/147 取 **W=0x1000**；§三 命名表里的 `core_nV` 一律是 **W=0x200**，两者口径不同、不混报。）

### 2.3 ★ 硬边界（不得越界引用）

1. **func_lib 无长度字段 ⇒ 子程序边界不可判**（`.zcode\skills\lucifen-unpack\SKILL.md` §13.8.3）。
   本件的 `[V, V+W)` 是**窗口**不是函数体；窗口会**越进邻接子程序** ⇒ exp 集合不可单独据以定名。
   **实测反例**：`V=0x1C43C`（CharacterOpen）起前 `0x174` B（= nextV−V，nextV=`0x1C5B0`）内
   **不含任何 op `0x05`**；其 op `0x05` 出现在 W≥0x200 处（W=0x1000 时得 22 个 native）
   ⇒ 用「`[V,nextV)` 区间」归属会得到 0 关联。
   **故本件弃用 nextV 分区，改窗口 + 敏感度**。依据（全局量化）：以 `[V,nextV)` 归属 vs `W=0x1000`，
   **80/92 个 V 的 native 集合不同**、**15/92 个 V 在 nextV 窗内得 0 native**（`W=0x1000` 只有 2 个为 0）。
   附注：**全工作区既有产物一律用窗口 `[V,V+W)`**（`SOB0解码\定名_说明.md:89`、`逆向引擎\说明.md:341`），
   **未见任何入档的 `[V,nextV)` 判据** ⇒ 本项是对「一种朴素做法」的否定，**不是**对某条已入档判据的证伪。
   （另附事实：`V=0x1C43C` 处首 op 是 **`0x20`**（原始字节 `20 00 00 00`），op `0x04` 在第 4 条 op（`+0x1C`）；
   语料 92 个 V 中**仅 `0x22704` 以 op `0x04` 开头**。）
2. **API 归属会因共享助手而假通过**：调用图闭包使同一通用 helper 被大量不相干 V 引用
   （如 h9 在 W=0x4000 下关联 61 个 V）。**故 L2 只作弱佐证。**
3. V 号**每 build 组本地**，禁跨源搬用。

### 2.6 ★ 全库最高调用 handler h462 的**关联已定（场景级共现），机制未定**
