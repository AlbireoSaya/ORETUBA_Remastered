## 〇 一句话结论

**T1 假设成立，且置信度「高」**：命令节点里那个「V」**不是** exe 地址，而是一个**指向 `func_lib.sob` 代码缓冲的偏移**。
引擎加载场景脚本时，**装载器 `sub_424D30` 对其 `maps[3]` 表逐项做重定位**：把代码字 `V` 就地改写成
`V + func_lib缓冲基址`，从而变成一个**运行期真实指针**——这就是「分派」的全部机制：
**没有 switch、没有命令名表，命令身份由「指针重定位」承载**。第二条分派层是 `maps[0]` → 引擎内建符号表
（`manager+0x58`，12 字节/条），指向 exe 内的原生实现（**只读，未及反查各内建函数体**）。

> **⟦订正（RV-ENG-02）⟧** 本段两处：① **「没有 switch」不确** —— 解释器是 47 opcode 栈式 VM，
> 分派表 `0x433B54`，主循环 `0x433650`；② **「`maps[0]` → 引擎内建符号表（`manager+0x58`）」不确** ——
> `[mgr+0x58]` 是 **user_var 变量记录向量**，原生函数走 `maps[1]` → `[mgr+0x38]`。见 `执行模型.md` §〇/§一/§三。

> 与既有产物的关系：`SOB0解码\软表解出_说明.md` 已证「六表里没有名字」「`maps[1]`/`maps[3]` 是立即数位」。
> 本件**订正并推进**其中一条：`maps[3]` 的值**不是**冗余副本——它在装载期被当作**偏移**参与重定位（见 §三）。
> 既有产物说 `maps[3][k] == cells[k//4]` 的「恒等式」在**文件层面**成立，但那只说明「磁盘上的值是 V 本身」，
> 装载器随后就用这个 V 去做 `+func_lib_base`。

## 一 T1 · 「V 指向 func_lib 代码区」假设检验

### 1.1 数据侧事实（`t1_evidence_dump.py`，实测输出）

**三个 V 口径必须分开写清（R2 订正）**——不同「形态」的数字不得挂在别人的形态描述下：

| 口径 | 形态定义 | V 数 | 节点/项数 |
| --- | --- | ---: | ---: |
| **① 命名命令节点**（`decode_sob0.py` 定义：带尾 REF→空串） | `[4][V][0C][k][3][REF→空串]` | **75** | **52,984** |
| **② 形态命令节点**（含「内联块」族，不约束 REF 去向） | `[4][V][0C][k][3][REF]` | **82** | **110,888** |
| **③ `maps[3]` 全体**（不要求节点形态） | 全部 `maps[3]` 项 | **93** | **112,621** |

> 本文 §1.2 的「41/93」用**口径 ③**；§1.1 其余量按口径 ③（并注明）。**旧版把 ①/②/③ 混用，本次订正。**

其余实测（口径 ③）：

| 量 | 值 |
| --- | --- |
| `func_lib.sob` | `ss=175052, se=177978`；代码区 `[header_end=102120, header_end+ss=277172)` |
| V 值域 | `[0x2C3C, 0x2A4B4]` = `[11324, 173236]` |
| V 是否 4 对齐 | **93/93 全部 4 对齐** |
| `max(V) < func_lib.se` | **成立**（173236 < 177978） |
| 旧形态判据的假阳性（V ≥ 0x100000，页引用字） | 用 `maps[3]` 背书后 **0 个** |

关键算术：单场场景的缓冲只有 `se` 字节（`s01_02a`：`ss=52324, se=81891`），而 `V` 最大 173236
**远超任何单场缓冲**，却**恰好落在 func_lib 缓冲（177978 B）之内** ⇒ V 不可能是本场偏移。

### 1.2 与 func_lib 内部结构对齐（`t1_v_vs_funclib.py`）

- `func_lib.map4` 的**代码引用目标**（8812 个不同偏移）中，**41/93**（按 `maps[3]` 全体键的 93 个值）**精确命中**某个 V；
- 全部 93 个 V 到「最近的 func_lib 内部代码目标」的距离：`≤4` 55 个、`≤16` 28 个、`≤64` 10 个（**无一 >64**）；
- V 处 func_lib 首字分布：`0xB`×51、`0x20`×30 …… —— V 恒为一段**节点结构的起点**（见 §五 T4），不是随机字节。

### 1.3 结论与置信度

| 候选 | 判定 | 依据 |
| --- | --- | --- |
| **V = func_lib 代码缓冲内偏移** | ✅ **成立（高）** | ① 装载器 `maps[3]` 重定位实测为 `V + [this+0xD4]`，而 `[this+0xD4]` 在 func_lib 装载时被赋值（§三）；② 值域上界 < func_lib.se；③ 4 对齐；④ 与 func_lib 内部引用目标重合 |
| V = exe 地址 | ❌ 排除 | exe `.text` 在 `0x401000..0x4ED000`，V 全 `≤0x2A4B4`，且 `V>>20 ∈ {0,0x18}` |
| V = 场景脚本内偏移 | ❌ 排除 | 多场 V > 本场 `se`（如 `s01_02a` V=0x1C8D0=117456 > 81891） |
| V = 全局字号 / 立即数 | ❌ 排除 | 装载器实测加上基址后成为**指针**，不是数值 |

**反证（如实登记）**：V 只是「func_lib 缓冲偏移」，**不等于「V 就是函数入口」**——`41/93` 精确命中 func_lib 内部
引用目标，其余 52 个只是「离某目标 ≤64 B」，说明 V 指向的是**一段被内联/嵌入的节点**，其精确边界（节点长度字段）
**未解**（见 §六 未决项）。因此“命令实现就在 func_lib 里”成立，但“V 是可直接 call 的函数首地址”**未证**。

## 三 T2 · 装载器与六表在引擎侧怎么用

### 3.1 主初始化 `sub_424460`（VA `0x424460`）

由游戏初始化 `VA 0x4141D9` 以 `ecx=manager` 调用（manager 指针存于 app 对象 `+0x19C8`）。它按顺序：

| 步骤 | 地址 | 反汇编片段 | 解读 |
| --- | --- | --- | --- |
| 读 `SCRIPT\SOB_INIT.DAT` | `0x4244A5` | `push 0x4FC340`(=`"SCRIPT\\SOB_INIT.DAT"`) | 模块登记表 |
| 解析模块表 | `0x4244D9` | `mov si,word[ebx]` = **412**；`lea eax,[edx*8+4]`(=esi*0x28+4) | 412 条，每条 **0x28 B** 记录 |
| 读 `SCRIPT\USER_VAR.SOB` | `0x42460F` | `push 0x4FC32C` | 变量表（SOB1，3 份缓冲 `[this+0x74]/+0x98/+0xBC`） |
| 读 `SCRIPT\FUNC_LIB.SOB` | `0x424898` | `push 0x4FC318` → `cmp [eax],'SOB2'` | 共享库 |
| 注册库 | `0x4248E6` | `push 1; push "FUNC_LIB"; call 0x424D30` | **装载并重定位 func_lib** |

```asm
0x004248D8  6A 01                push 1                     ; arg4 flag = 1
0x004248DA  83 C0 04             add  eax, 4                ; eax = 文件缓冲 + 4（magic 之后）
0x004248DD  57                   push edi                   ; arg3 idx = 0
0x004248DE  68 0C C3 4F 00       push 0x4FC30C              ; arg2 = "FUNC_LIB"
0x004248E3  50                   push eax                   ; arg1 = 数据指针
0x004248E4  8B CD                mov  ecx, ebp              ; this
0x004248E6  E8 45 04 00 00       call 0x424D30              ; <== 模块装载/重定位
```

### 3.2 模块装载/重定位 `sub_424D30`（VA `0x424D30`，`__thiscall`，`ret 0x10`）

签名：`int load(this, void* sob_data_after_magic, char* name, int idx, char is_lib)`。
逐步（**这是 T3 的核心**）：

```asm
0x00424D54  8B 06        mov  eax,[esi]        ; eax = table_size（magic 后第一个 u32）
0x00424D59  8B EE        mov  ebp,esi          ; ebp = 六表区基址

```

⇒ `ebx` = **模块缓冲基址**（代码与串**合并**在一段，串相对缓冲起点偏移 = 原 `ss+…`）。

**六表被顺序读取，各配一个重定位循环**（`maps[0..5]` 与循环 A..E + 末尾零检查一一对应，

```asm
0x00424E9B  8B 4D 00             mov  ecx,[ebp]            ; off = 代码区偏移
0x00424E9E  8B 45 04             mov  eax,[ebp+4]          ; value = V（文件里就是它）
0x00424EA1  8B BE D4 00 00 00    mov  edi,[esi+0xD4]       ; edi = 当前「库基址」
0x00424EAD  03 C7                add  eax,edi              ; V + 库基址
0x00424EB0  89 04 0B             mov  [ebx+ecx],eax        ; 就地改写为指针

0x00424EBF  8B 45 00             mov  eax,[ebp]            ; off
0x00424EC2  8B 4D 04             mov  ecx,[ebp+4]          ; value
0x00424EC8  03 CB                add  ecx,ebx              ; value + 模块缓冲基址
0x00424ECE  89 0C 03             mov  [ebx+eax],ecx
```

**基址 `[this+0xD4]` 何时被赋成 func_lib**（`0x424EE3`，据 arg4 `is_lib` 分流）：

```asm
0x00424EE3  8A 44 24 38          mov  al,byte [esp+0x38]   ; arg4 flag
0x00424EE7  84 C0                test al,al
0x00424EE9  74 08                je   0x424EF3
0x00424EEB  89 9E D4 00 00 00    mov  [esi+0xD4],ebx       ; flag=1(FUNC_LIB): 0xD4 = 库基址
0x00424EF1  EB 18                jmp  0x424F0B
```

**场景里的 V 一律重定位成 func_lib 内地址**。

## 四 T3 · 命令分派机制（回答「V 如何变成派发目标」）

### 4.1 机制（已定位，证据见 §三）

命令节点磁盘形态（`s01_02a`，字节偏移 32）：

```
RAW6 = [0x4, 0x1C8D0, 0xC, 0x4, 0x3, 0x185DF1F]
        ↓ map3                      ↓ map4
   (offset 36 → V=0x1C8D0)    (offset 52 → 本模块串/代码)
```

装载器对 `maps[3]` 的每一项执行 `code[该字偏移] = V + func_lib_base`。因此：

```
磁盘：  [04] [V]           [0C] [k] [03] [REF]
                │
   maps[3] 重定位（+func_lib_base）
                ▼
内存：  [04] [ptr→func_lib+V] [0C] [k] [03] [ptr→本模块]
```

**「V 是脚本内地址而非 exe 地址，引擎如何把它变成派发目标」的答案**：
**靠装载期重定位**——把 func_lib 缓冲基址加到 V 上，得到一个**运行期真实指针**。
引擎的节点解释器（**节点流，非 exe 机器码**）拿到这个指针即可定位命令实现；
**不存在命令名表、不存在 switch 表**（这也解释了「exe 内 35 个命令名 0 命中」）。

### 4.2 第二层分派：`maps[0]` → 引擎内建符号

`maps[0]` 的 value（0..915）经 `[this+0x58]` 的 12 B 记录表重取，指向 exe 内的原生实现/对象。
本次**未反查 `[this+0x58]` 表的填充点**（该表在运行期构建，无静态数组；见 §六 未决项）。

### 4.3 诚实边界

- 已定位：**重定位式分派**（机制 + 反汇编证据 + 数值自洽）。
- **未定位**：读取这些指针并真正「调用」的**解释器循环**。引擎代码区是**序列化节点树**（§五），
  指针被写回节点流后由某个节点遍历器消费；该遍历器**本轮未定位**（已试路径见 §六）。
  > **⟦订正（RV-ENG-02）⟧ 已定位**：解释器 = **47 opcode 栈式 VM**，主循环 `VA 0x433650`
  > （`0x433680 jmp dword ptr [ecx*4 + 0x433B54]`），上下文 = 管理器 `+4`（`sub_4252F0` 以 `ecx=&mgr+4` 调它）。
  > `[04][V]` = op `0x04` **CALL V**（V 是 func_lib 子程序 = 命令实现体）；原生函数走 op `0x05`（`maps[1]` 下标）。
  > 见 `执行模型.md` §四/§4.4（47 opcode 全表）。

## 六 R1 重跑：全 `.text` 覆盖、负结论复核、新证据

### 6.1 覆盖口径修复与实测（`sweep.py`）

`disasm.py:21` 原为 `md.skipdata=False`：capstone 在 `0x418EA1` 撞上一张**数据表**即整体停摆。
实测该点正是 **`0x418Bxx` 处理函数指针表**（表内字节 `xx 8B 41 00` = `0x00418Bxx`）。

```text
skipdata=False -> 32,790 条   （停在 0x418EA1，仅覆盖 0x401000..0x418EA1 ≈ 8.9%）
skipdata=True  -> 361,825 条  （整节 0x401000..0x4ED000，与一审独立复核数一致）
```

- **撤回**：§六 旧文「全 `.text` 反汇编 ×3.4 万指令」——**为假**（实为 8.9% 截断）。
- **撤回**：旧文「字段访问 180 处」「`+0x58/+0x38/+0x48` 命中 90+ 处」——**基于 9% 采样，作废**。
- 修复后字段枚举改用**整节字节模式匹配 + 就地反汇编验证**（`sweep.py` / `fieldscan.py`），
  与反汇编器「在哪停」无关，**无截断**：`[base+0xD4]` 全节 **51 处**、`[base+0xD8]` 全节 **62 处**
  （注意：这是**全 exe 所有类**的 disp 命中，非同一 manager 的字段；`0xD4/0xD8` 只是偏移，多类共用）。

**T2 口径统一（两工具曾「打架」）**：`sweep.py` 与 `fieldscan.py` 现**逐字同源**——
同一 `OPS`、同一 disp32+disp8 规则，`0xD4/0xD8` 两处**都报 51/62**。
二者此前的差异**只在 `OPS` 是否含 `0xFF`**：`0xFF` 是 `call/jmp/inc/dec [m]`（间接控制流），
纳入它会把 `[base+0xD4]` → **54**、`[base+0xD8]` → **65**。现统一**不含 `0xFF`**（只统计
`mov/cmp/add/lea` 这类**数据访问**），故 §二 让读者跑的 `sweep.py`/`fieldscan.py` 与本节数字**同源**。

**T5 工具盲区（已消除并登记）**：旧版两工具**只匹配 disp32**（仅 mod=10），对
`[reg+0x38]/[reg+0x48]/[reg+0x58]` 这类**小偏移（汇编器用 disp8 编码，如 `8B 45 38`）报 0**——
那是**工具盲区，不是「无访问」**。现两工具**同时匹配 disp32（mod=10）与 disp8（mod=01）**：
小偏移恢复出 `[base+0x38]` **266 处**、`[base+0x48]` **303 处**、`[base+0x58]` **422 处**
（含大量 `[esp+disp]` 栈帧访问，故是「全类 + 栈」口径，不等于对象字段）。
`0xD4/0xD8`（>127，只能用 disp32 编码）计数不变。

### 6.2 两处消费点 `0x425232` / `0x425293` 的解读（R1b）

两者同属一个 `__thiscall` 方法 **`sub_4251F0`**（起点 `0x4251F0`，`esi = this`）。该方法**由 `sub_41D700` 调用**
（`0x41D724` 就在 `sub_41D700` 内）；而 `sub_41D700` 的两处调用点 `0x40131A`/`0x401B18` 均以
`mov ecx,[esi+0x19C8]`（**manager 单例**）作 `this`。
该方法是一个**栈/向量清理（reset / erase）**例程，维护 `[this+0x24]`（begin）.. `[this+0x28]`（end）的指针向量：

```asm
0x00425232  8B 86 D4 00 00 00    mov  eax,[esi+0xD4]     ; (1) 读 func_lib 基址
0x00425238  85 C0                test eax,eax
0x0042523A  74 03                je   0x42523f
0x0042523C  83 C5 04             add  ebp,4              ;  非空 → 从第 2 个元素开始释放（跳过元素 0）
0x0042523F  3B 6E 28             cmp  ebp,[esi+0x28]
...
0x00425293  8B 86 D4 00 00 00    mov  eax,[esi+0xD4]     ; (2) 再读一次
0x004252A0  85 C0                test eax,eax
0x004252A2  74 26                je   0x4252ca
0x004252A4..0x4252B9          ... 把 [0x24+4, 0x28) 上移 4 字节（erase-front）
```

**它们把 `[this+0xD4]` 当「func_lib 是否已装载」的布尔门用**（只 `test`，**不解引用**）：
库已装载时，向量的第 0 个槽位被保留/跳过。⇒ **加强** T3：`0xD4` 是一个「只在 func_lib 装载后才有值」的
独立 manager 字段；这两处与 `sub_424D30` 的 `maps[3]` 重定位**共用同一字段**——该字段的
**唯一的非零写值点**是 `0x424EEB`（写 func_lib 基址）；构造/清零点另有 `0x422331`
（manager 构造函数 `mov [esi+0xD4], ebx`，`ebx=0`），故 `0xD4` 才可当「是否已装载」的布尔门。

### 6.3 「同一 manager 单例」补证（一审附加项）

manager 单例 = `[app对象 + 0x19C8]`。四处证据显示 scene 装载与 func_lib 装载用**同一实例**：

| 证据 | 地址 | 反汇编 |
| --- | --- | --- |
| 初始化（内含 func_lib 装载） | `0x4141CE` | `mov ecx,[esi+0x19c8]` → `call 0x424460` |
| 场景装载（同一函数内） | `0x414211` | `mov ecx,[esi+0x19c8]` → `call 0x424fa0` |
| 另一场景装载路径 | `0x40131A` / `0x401B18` | `mov ecx,[esi+0x19c8]` → `call 0x41d700`（→`sub_4251F0`）→`call 0x424fa0` |
| func_lib 装载内部 | `0x4248E4` | `mov ecx,ebp`（`ebp` = `sub_424460` 的 `this`）→`call 0x424d30` |

- `0x4141CE` 与 `0x414211` 之间仅隔 `call 0x40b920`（`0x40B920` 首尾 `push esi`/`pop esi`，**保留 esi**），
  `esi` 始终是同一 app 对象 ⇒ 两次取到的是**同一 `[app+0x19C8]` 值**。
- 结论：**同一 manager 单例**（`0x424460` 装入的 func_lib 基址 `0xD4` 与随后 scene 装载的 `maps[3]` 重定位同源）。
  **（一审该项由「未证」→「已证」。）**

### 6.4 新证据（正向）：内建命令注册表（`registry.py`）

在重跑全节时发现注册序列 `push <handler_VA>; mov ecx,esi; call 0x422730`：

```asm
0x0041565C  68 C0 7D 41 00       push 0x417DC0          ; handler #1（**本轮补入**，见下）
0x00415661  8B CE                mov  ecx, esi
0x00415663  66 C7 05 38 36 50 00 37 00  mov word ptr [0x503638], 0x37   ; 夹在中间的 11 字节
0x0041566C  E8 BF D0 00 00       call 0x422730          ; push→call 恰 16 字节，旧 16B 窗越界漏掉
0x00415671  68 50 7F 41 00       push 0x417F50          ; handler #2
0x00415676  8B CE                mov  ecx, esi
0x00415678  E8 B3 D0 00 00       call 0x422730
```

- **T1 订正**：旧版 `registry.py` 用「push 与 call 间 16 字节固定窗」，漏掉 `0x41565C` 的
  `push 0x417DC0`（其后夹了一条 11 字节的 `mov word[...]`，push→E8 恰 16 字节、越出窗）。
  现改为**从调用点向前搜索最近的 `68 <handler> 8B CE`**（push 后紧跟 `mov ecx,esi`），不再受中间指令长度影响。
- 重跑实测：**798 次注册调用，798 次配对成功，789 个不同原生处理函数**；
  **调用点（`E8`）VA `0x41566C..0x42239A`**、push(handler) VA `0x41565C..0x422393`、
  处理函数 VA 范围 `0x417DC0..0x432680`；`0x422730` 的调用者**全部**落在 `0x41566C..0x42239A`（专用注册器）。
  重复登记：`0x432680`×9、`0x431360`×2（798−9=789）。
  （复审另测得 **788**；与我方 **789** 差 1，属**配对口径差异**，**调用点数一致 798**，不影响任何结论。）
- 处理函数多为 `mov eax,[0x503248]; mov edx,[eax+0x19C8]; ...` 形态（**操作 manager 单例**），
  例如 handler #8 = `0x418F30`（改 `[manager+0x100]` 的 16B 记录数组，即变量/属性写入口）。
- 意义：这正是我上一版说「**未定位**」的**内建符号表来源**的一半——**原生处理函数集合可枚举**。
  ⚠️ **未证**：注册顺序是否就是 `maps[0]` 的编号（0..915）？注册器 `this`（`esi`）与 manager 单例是否同一对象
  （该注册序列所在代码块**不出现** `[esi+0x19C8]`，`0x422730` 操作 `[this+0x34]` 向量，而 `sub_424D30` 的 `maps[0]`
  走 `[this+0x58]` 的 12B 记录表——两者机制不同，需运行期确认对应关系）。**留作未决。**
  > **⟦订正（RV-ENG-02）⟧ 两个 ⚠️ 均已闭合**：
  > ① **注册顺序 ≠ `maps[0]` 编号**，而是 **`maps[1]` 的下标**（`maps[0]` 是变量编号空间）。实测 op `0x05`
  > 的 **63241** 个操作数 **100.0000%** ∈ `maps[1]` 且 `value<801`（= 向量项数 3+798）。
  > （⟦订正（ISSUE-20261008-04 B1/B4）⟧ 旧写「62245」系**截断口径**，**表感知真值 = 63241**。）
  > ② 注册器 `this` **就是** manager 单例：注册块在管理器构造 `0x4154D0` 内（`esi=ecx=this`），
  > 该构造函数由 `init 0x414130` 以 `malloc(0x404)` 的返回 `call`、再 `[app+0x19C8]=eax`。
  > `0x422730` 操作的 `[this+0x34..0x40]` 即向量 `{begin=+0x38,end=+0x3C,cap=+0x40}`（`+0x34` 是前置标志字节），
  > 与 `sub_424D30` 循环 B 读 `[mgr+0x38]` **同源**。见 `执行模型.md` §三。

### 6.5 「解释器主循环未定位」——**仍成立**，卡点具体化

> **⟦订正（RV-ENG-02，ISSUE-20261007-11）⟧ 标题「仍成立」撤回。** 解释器已完整定位：
> 主循环 `0x433650`、分派表 `0x433B54`（47 opcode）、上下文 `mgr+4`；全库 412 文件**非法 op 位置 = 0**，
> op `0x05`/`0x04` 的操作数分别 **100.0000%** 命中 `maps[1]` / `maps[3]∪maps[4]`。
> 本小节下方「卡点」中：**卡点 (a)「handler 索引运行期由符号解析产生、静态不可见」不成立**
> （`maps[1]` 在**文件层**就是下标，静态完全可见）；(b)「遍历器经间接调用进入」**不成立**
> （`0x433680` 是直接跳表分派，唯一调用者 `0x4252F9`）。**不需要实机动态调试**。
> 见 `执行模型.md` §四/§六。以下为历史正文（保留）。

- 修复覆盖后，**仍未找到**消费 SOB 节点流（读 `func_lib_base+V` 指针并调用）的遍历器/主循环。

  ① manager 单例存取点 48 处（`mov r32,[reg+0x19C8]`，簇在 `0x418Fxx/0x4193-94xx`、`0x41ED-41F1xx`、`0x432xxx`）；
  ② 一处含跳转表的代码簇（`0x4181C4..0x4192CF`，正落在旧扫描的截断点之后）；
  ③ 789 个原生 handler（§6.4）。
- **T4 订正（防与 §〇 对撞）**：② 的「20 张跳转表大 switch」**未经逐表复核**（仅按 `FF 24 <modrm>` 模式
  数出该区间有 20 个跳转表，**各表语义未逐一核**，登记为「核不到 / 未逐表复核」）。
  它与 §〇「引擎内无命令分派 **switch**」**不冲突**：§〇 说的是**没有「命令名 → 实现」的 switch/名字表**
  （命令身份靠 `maps[3]` 指针重定位）；而 ② 位于**handler 区内部**（`0x4181C4` 在已注册 handler
  `0x417DC0/0x417F50/0x4181B0` 之间、**本身不是注册 handler**），是 handler 内部对**参数/状态**的
  分支，与「命令分派」不是同一层。**不得把 ② 当作命令分派表引用。**
- **卡点（仍缺什么）**：静态层面无法确定「节点流指针 → handler 调用」的对应，因为
  (a) handler 索引在**运行期**由符号解析产生（`maps[0]` 的 id 在装载时赋值，静态不可见）；
  (b) 节点遍历器若通过**间接调用/虚表**进入，则无直接调用点可回溯。
- **要继续需要**：**实机动态调试**——在 `sub_424D30` 装载后对 scene 缓冲下**内存写/执行断点**，
  或对 `0x422730` 注册表 + `[manager+0x58]` 的 id→handler 关系下**读断点**，跟踪一个已知命令节点（如 `V=0x1C8D0`）的执行路径。
  仅静态反汇编**到此为止**。
