## D. 反证尝试（5 条，**全部失败**）

### D-1 「`0x433B54` 不是唯一分派表」
- 手段：枚举全 .text 全部 indexed jmp（369）+ indexed call（4），按「读到非 .text 或 nop 填充为止」估表长。
- 结果：**仅 1 张 47 项**表；44/52/64/66 项者均为 handler 内部 selector switch（表后为 `0x90909090` 填充，`rv_f.py` 已打印上下文）。
- 判定：**反证不成立**。

### D-2 「那 5 条指令不是主循环（可能是别的循环）」
- 手段：追 `0x433650` 的调用者与上下文来源。唯一调用者 `0x4252F9`；其 ecx = `edi+4`，而 `edi` 来自调度器 `sub_4252F0` 的 ecx；调度器 ecx 由帧循环 `0x4012E6` 赋予 `[app+0x19C8]`；该对象正是 `init 0x414130` 用 `malloc(0x404)`+`0x4154D0` 构造、子 ctor `0x422200` 在 `+4` 处 `call 0x433440`（vtable 0x4EDF34）建的 VM 上下文。
- 且装载器 `0x424EFF/0x424F06` 恰好把场景缓冲写进 `ctx+8`（pc）并压哨兵——正是该循环消费的 pc/sp。
- 判定：**反证不成立**。

### D-3 「op `0x04` 不是 CALL，而是别的」
- 手段：反汇编 handler + 用引擎自带重定位表反查操作数。
- 结果：handler = `push(edi+4); pc=*operand`（经典 call）；**113166/113166 = 100%** 的 op04 操作数是 `maps[3]∪maps[4]` 键，即装载期被改写成 **func_lib / 本模块缓冲内的代码指针**。若 op04 非调用，其操作数不会一致地全是代码指针。
- 判定：**反证不成立**。

### D-4 「op `0x05` 操作数 0 不是 handler 下标」
- 手段：反查 maps[1] 的重定位去向 + 操作数命中率。
- 结果：循环 B（`0x424E4A`）**字节级** = `code[key] = [mgr+0x38][value]`；`[mgr+0x38]` 向量由 798 次 `push handler; call 0x422730` 构建、ctor 另建 3 个 → 共 801 项。op05 操作数 0 命中 maps[1] 键 **100%**（62245/62245），value 全部 <801（max=788）。
- 判定：**反证不成立**（操作数 0 定义上就是 handler 下标）。

### D-5 「maps[1] 的去向不是 `[mgr+0x38]`」
- 手段：逐字节读循环 B。结果：`8B 56 38 / 8B 0C 8A / 89 0C 03` = `[esi+0x38]`，4B/条。
- 判定：**反证不成立**。

### E-1【事实/过度声明】§5.3「**全部** handler 首句均为 `mov eax,[esp+4]` / `mov ecx,[esp+4]`」
- 实测（789 个不同 handler，`rv_g.py`）：首句严格为 `mov eax/ecx,[esp+4]` 的仅 **304/789（38.6%）**（放宽含 edx 为 324）；**485 个（61.4%）不是**——169 以 `push esi` 起、53 以 `mov eax,[0x503248]` 起等。
- 即使把「`push reg` 后 `mov reg,[esp+8]`」也算作「从栈取实参」，只再多 142 个，仍非「全部」。
- 影响：该句作为「handler 调用约定 = 取 [esp+4] 指针、读 [eax]=selector、[eax+4]=参数」的**证据**，方向大体成立（约 466/789 直接或经前言从栈取参），但「**全部……首句均为**」的**字面全称断言为假**，会被后续「逐 handler 命名」工序当既成事实引用。
- 建议：改为「**约 4 成 handler 首句直接为 `mov eax/ecx,[esp+4]`；连同 `push reg` 后 `mov reg,[esp+8]` 者约 6 成从栈取入参**；其余多以全局 `[0x503248]` 直接取参」，并去掉「全部/均为」。

### E-2【事实/过度声明】§4.1「+0x10 cont（**装载时 = pc**）」与 §十二「`0x4251F0` 会话重置（`ctx.cont = ctx.pc`）」
- 实测（`rv_g.py` + 调用链）：
  - `0x4251F0` 的**唯一**调用者是 `0x41D724`；`0x41D700` 的调用者是 `0x401323` 与 `0x401B1E`，两处均先 `mov ecx,[esi+0x19C8]`（**manager**）再 call；`0x41D722 mov ecx,esi`（esi=manager）后 call——即 **`0x4251F0` 的 esi = manager，不是 ctx**。
  - 故 `0x425203 mov edx,[esi+8]` = `mgr+8`，`0x425206 mov [esi+0x10],edx` = `mgr+0x10`。
  - 又 ctx=mgr+4（A.3 双证），故 `mgr+8 = ctx+4 = stack_buf`、`mgr+0x10 = ctx+0xC = sp`。
  - ⇒ 该指令实为 **`ctx.sp = ctx.stack_buf`（重置操作数栈）**，**不是** `ctx.cont = ctx.pc`。
  - 另：ctx ctor `0x433440` 只初始化 +0/+4/+8/+0xC/+0x14/+0x18，**从不初始化 +0x10**；装载器 `0x424D30` 也只经 `0x4335A0` 写 ctx+8（pc），**没有任何装载路径写 ctx+0x10**。⇒「装载时 = pc」无依据。
- 影响：`§4.1` 是核心「VM 上下文」描述，`§十二` 是速查表；两者都会被人当事实用。（op 0x02 读/写 cont、op 0x03 把 cont 写 REF 的**语义本身没错**，错的只是 cont 的初值来源。）
- 建议：`§4.1` 删去「装载时 = pc」，改为「初值未定（ctor 与装载器均不写 +0x10；仅 op 0x02 会写）」；`§十二` 的 `0x4251F0` 改为「会话重置：`ctx.sp = ctx.stack_buf`（mgr+0x10=mgr+8），并清零 `[0x503724]` 深度、处理 `[mgr+0x24..0x28]` 列表」。

### E-3【轻微不精确】§〇 帧循环只列 `0x4012EC/0x401348`，实为 3 处（漏 `0x401AF3`）
- 实测 `callers(0x4252F0)` 三处（§十二 已补列 `0x401AF3`，正文 §〇 未同步）。建议 §〇 与 §十二 统一。

### E-4【轻微不精确】§二 is_lib 段 asm 清单未写明 `0x4335A0/0x4335F0` **仅 is_lib=0（场景）执行**
- 实测 `0x424EEB`（is_lib=1）后紧跟 `0x424EF1 jmp 0x424F0B`，**跳过** `0x424EF3..0x424F06`。清单把两支行并排列出，易被读成「func_lib 装载也设 pc」。建议加一句「is_lib=1 分支直接跳到 0x424F0B，不设 pc/不压哨兵」。
