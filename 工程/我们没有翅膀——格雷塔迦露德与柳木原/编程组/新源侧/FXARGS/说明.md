## 一 方法（口径写死，全部可复跑）

### 1.1 「读位」怎么来 —— 帧口径 `i = (X − d − 8)/4`

引擎事实（`执行模型.md` §4.4 ＋ 本次**直读 handler** 复核）：

| op | 语义 | 本次直读证据 |
| --- | --- | --- |
| `0x23 LD_STK` | `*op1 = *(sp − op0)` | `0x4339FE: mov eax,[esi+0xc]; sub eax,[edi]; mov edx,[eax]; mov [ecx],edx` |
| `0x22 ST_STK` | `*(sp − op1) = op0` | `0x4339A8`（**偏移在 op1**，与 LD_STK 相反） |
| `0x0B FRAME_ALLOC` | `sp += k`（局部量在 `sp−4 … sp−k`） | 模型 §4.4 |
| `0x0C SP_DROP` | `sp −= k`（既丢实参也丢局部量） | 模型 §4.4 |
| `0x04 CALL` | **净栈变化 = 0** | push 返回地址 +4 被 callee 的 `RET`（`0x01`）pop —— 线性清单里看不到 callee 的 RET，**记 +4 会整体错位** |

**换算**：`arg_i` 位于 `sp_entry − 8 − 4i`（arg_0 = 调用点最后 push 的那个，
与 `decode_sob0.node_args` 的 `cells[node−1−2i]` 同序）。在「相对入口累计净栈偏移 `d`」处读 `LD_STK X`
⇒ 命中 `arg_i` 当且仅当 **`X = d + 8 + 4i`**，即 **`i = (X − d − 8) / 4`**。
`d` 由**基本块级抽象解释**沿控制流求出（`_probe_frame_args.py`），合并点上若 `d` 不唯一会同时列出。

- 无 `FRAME_ALLOC` 且读点前无 push 时，本式退化为任务书写的「`node_args[i]` 位于 `+8+4i`」。
- 有 `FRAME_ALLOC k` 时，实参位落在 `X = k + 8 + 4i`（脚本直接算 `i`，不依赖该等价式）。
- **阳性对照（同一脚本内置，`--selftest`）**：M3 已独立验证的 4 条位必须复现 —— 实测 **PASS**（见 §六.2 真输出）。

**分类**：`实参`（0 ≤ i < argc）／`局部`（i < 0，落在 FRAME_ALLOC 出的局部区）／
**`越界`（i ≥ argc —— 任务书要求「读到 argc 之外必须明确写出」）**／`非4字节格`（换算不成立）。
本批 20 个 V **无一例 `越界`**，也**无一例 `非4字节格`**（`效果族参数位_帧读.tsv` 可逐行核）。

### 1.2 argc 从哪来 —— **全库 412 文件**（不是剧情语料）

`解出_{ot,otp,otr}.tsv` 只覆盖**剧情语料**；`cross(0x2A150)` 的 21 个节点**全在系统脚本**
（config1/config2/gallery/history/saveload）⇒ 只用剧情语料会得到「argc 未知」并误判「越界」。

⇒ 每个 V 的 `argc` 与逐位值域都是**全库口径**（与 `Lucifen命令族标签.tsv` 的 `v_nodes` 对得上：
`0x1B888` 524、`0x1B69C` 939、`0x19D58` 7275、`0x2A150` 21 …）。**已据此复核 M3 的 argc 结论，无出入。**

### 1.3 值域统计 —— `evidence` 列的解析纪律

`args=[…]` **不能用非贪婪正则**。本轮实现为**括号感知**解析：从 `args=[` 起 `depth=1`，
遇 depth 回 0 即列表结束，`depth==1` 处的逗号才是顶层分隔，**不 strip**（保留串实参原样）。
**受影响行数（本轮实测，与任务书给的 126 一致）**：

```
串/内容里出现 ']' 的行 = 97 ；含括号且含逗号 = 29 ；含 ']' 或 '(' = 126
```

⇒ 口径 = 「`args=[` 到 ` ctrl=` 的内容**去掉列表闭合 `]`** 后仍含 `]` 或 `(`」的行数 = **126**；
其中 **97 行的串实参内含 `]`**、**103 行的逗号落在括号内**（非贪婪正则与朴素 `split(",")` 都会切错）。
典型样本：`0x12E94` pos12 = `(0,0,1)(400,300,2)`（坐标串，内含 `(`/`)`/`,`；**29 例**即上表「含括号且含逗号」的行数，全部出自 `0x12E94`/`0x12998` 的坐标/比例串位）。

### 1.4 PSV 对拍三口径（**分开报，禁止混报**）

| 口径 | 定义 |
| --- | --- |
| `exact` | 该 seq 上**恰 1 条**该类型带 `time` 的金标行，且 `round(ms×0.06)` **等于**其 `time` |
| `seq` | `round(ms×0.06)` ∈ 该 seq 上该类型行的 `time` 集合 |
| `scene` | `round(ms×0.06)` ∈ 该场该类型行的 `time` 集合（抗 seq 错位，用于 `otr`） |
| `置换基线` | 把本位的 ms 值**整体错位一格**（key 不动）后重对同一批 seq —— zero-information null |
| 换算 | `PSV :Time(帧) = round(PC 毫秒 × 0.06)`（60fps；Fade 已证，本批沿用同一常数、**未引入新常数**） |
| 非退化口径 | 金标 `time = 0` 的行**不计入 exact 分母**（对齐上游 `final_ms.tsv` 口径；本批只影响 `0x19F9C`） |

**且相对置换基线的最大增益 ≥ 0.15**；门槛只压**主源**（样本最大者，本批恒为 `ot`），
另一 build（`otr`）只作**跨 build 复现记录**。`_verify_positions.py` 的 C3/C4 双向强制：
未达门槛的不得标 PSV对拍；标了未证的若重算达标则**校验 FAIL**（逼升档）。

## 三 本轮**新证**的 3 个位

### 3.1 `0x10428` pos4 = 时长(ms)（**新**，M3 未做）

- **对拍**：`PSV SpriteMove :Time` —— `exact 108/113 = 0.956`、`seq 110/116 = 0.948`、`scene 115/118 = 0.975`，
  置换基线 exact 仅 `36/113 = 0.319`。
- **定 type 的对照**：换 type 即塌陷 —— `SpriteBG` exact `2/15 = 0.133`、`Sprite` exact `0/1 = 0.000`
  ⇒ 该位对的是 **`SpriteMove`**，不是泛化的 sprite 时长。
- **对「`bg_anime` vs `SpriteMove`」定位的贡献**：`decode` 的 `TIME_FAMILY["ot"][0x10428] = ("bg_anime", 4)`
  与 PSV 金标 `SpriteMove` 的既存冲突（`定名_说明.md` §6.8 登记）——本轮给出**位级证据**：
  该 V **同时**携带 (a) 位 4 = 时长（对 `SpriteMove.time` 0.956）**(b)** 位 5 = 方向 token 串
  （`r×22 / a0 r×19 / l×16 / d×15 / u×14`，与 `0x10150` pos1 同形），且**过程内 `CALL 0x10150`（bg_move）**
  ⇒ 形态更像「**按方向 token 移动 + 指定时长**」的一体命令；**PSV 侧的 `SpriteMove` 恰好就是这两件事**。
  ⇒ 本轮结论：**PSV 名 `SpriteMove` 在语义上更贴合**；`bg_anime` 只是「背景动画」这一更粗的族标签。

### 3.2 `0x19F9C` pos0 = 时长(ms)（**FadeOut 段**，非退化口径）

- **归 type**：对 `FadeOut` exact `302/310 = 0.974`、对 `FadeIn` exact **0/2 = 0.000**（seq 也 0/405 = 0.000）
  ⇒ 该 V 是 **FadeOut** 侧，不是 FadeIn。
- **非退化口径的必要性（本批唯一受影响的 V）**：金标 `FadeOut` 带 `time` 的 583 行里有 **132 行 `time=0`**（帧 0 ⇒ 瞬时/无时长），使 exact 资格集里多出 **83 个** PC 节点落在 `time=0` 的 seq 上（393−310），
  若把它们留在 exact 分母里，命中率被稀释成 `302/393 = 0.768`（低于 0.90 门槛）；剔出后 **302/310 = 0.974**。
  该处理**与上游 `final_ms.tsv`（p11：`node[p]>0 且 :Time>0` 才算 testable）同口径**，并已登记为待裁决（§七.1）。
- **代码侧旁证（不单独构成证据）**：`EQZ → ST_STK 1000`（默认 1000ms），再接
  `native#251`（通用转场启动器）+ 过程内嵌串 **`cross`** —— 与「该 V 是一次 cross 型转场、时长可缺省」一致。
  ⚠️ 由此**订正** `定名_说明.md`：`0x19F9C` 的过程内嵌串**确属自身**（B1 已判对），且它**就是** `cross`
  （旧窗口法把它当「越窗属邻节点」是判错方向，B1 已翻案；本轮补上「串名 = cross」这一直证）。

### 3.3 `0x1A96C` 的 pos0/pos2 **位歧义已解**（判定性否定 pos0）

`decode 说明` §5.3/§八.3 遗留：「`rule_in` 的 ms 位有歧义（pos0 / pos2 **有时**同为 500）」。
本轮用**置换基线**把它解掉：

| 位 | exact | 置换基线 exact | 增益 | 判定 |
| --- | --- | --- | --- | --- |
| **pos2** | 568/610 = **0.931** | 370/610 = 0.607 | **+0.324** | **ms** |
| pos0 | 314/418 = 0.751 | 312/418 = **0.746** | +0.005 | **不是 ms**（纯值域重叠造成的假命中） |

⇒ **pos0 = ms 被否定**（它的「高分」完全由**与 pos2 共值域**解释，去掉值域自相关后信号为 0）。
**这条同时示范了置换基线的必要性**：只看命中率会把 pos0 误当第二条 ms 位。

## 四 值得下游直接用的结构事实（PC自证，来自反汇编而非值域）

1. **`0x1B040` pos4 = 转场图案选择子（0..6，7 路）**：代码 `LD_STK arg4 → LT 0 / GT 6 → 越界即 RET → TABJMP`，
   7 个分支的 native 名串依次
   **`zoomflip` / `wave` / `mosaic` / `rotaxis` / `rotcenter` / `addsub` / `hblur`**（同过程内嵌串）。
   ⇒ `0x1B040` **不是单一效果**，而是 **InOut_Act 的 7 种图案共用入口**；
   **这订正了**「`0x1B040` = zoomflip」（`定名_说明.md` §1.2/§5.1、M3 §3.x 均只提到 `zoomflip` 这一个串 ——
   它只是 **TABJMP 分支 0** 的名字；B1 用过程归属把串判给本过程是**对的**，但串不是 1 个而是 **7 个**）。
2. **`0x10150` pos1 = 方向 token（串 `l/r/u/d/c`）**：值域 `l×82 / d×65 / r×60 / u×19 / c×18`。
   **订正** `.zcode\skills\lucifen-unpack` §12.4「该 V 只记 `d`/`u`」—— 实测**全 5 种**（M3 §3.4 已提，本轮全库复核一致：249 节点）。
3. **`0x1AD18` pos4 = 素材路径串**（`PIC\EC28.ELG` 543/561）。
   ⚠️ **对不上的原因**：PSV `EyeCatch` 847 行**只有 `image` 列、没有路径列**（列填充画像见 §六.5），
   ⇒ **无可对拍字段**，不是「没解出位」。
4. **常量位（29 个 PC自证 行里的大多数）**：值域去重 = 1，**无信息**（如 `0x10428` pos0..3 恒 0、
   `0x1AEA0` pos0 恒 2、`0x1BD8C` pos1..3 恒 1/1/0）。下游可直接跳过，不再猜。
5. **「值域像 X」一律停在未证**（**纪律**）：`0x1B888` pos1 的 9 个去重值多为**可命名色**（`0xFFFFFF`/`0x6C272D`/`0xDAA520`/`0xFF1493`…）像 RGB、`0xFDF4` pos1 的 `2/1.5/3/2.5/4/10` 像缩放倍率、`0x1B69C` pos3/pos4 ∈[0,50]/[0,80] 众 30 像振幅、
   `0x12E94` pos12 的坐标串像裁剪窗 —— **本批全部只写值域、不写「已解」**（PSV 侧无对应列，或对拍不达门槛）。
