## 2 映射口径与自证

### ① 坐标（`x1920/y1920`，中心 x ＋ 底边定位）

- `x1920 = round(cx×1.5)`、`y1920 = round(cy×1.5)`（1280×720 → 1920×1080，两画布同为 16:9）。
- 构建侧换算**与既有 self 路径同式**（不是新口径）：
  - x：gold `acx = cb.x + gx·cb.w/1920`；self `acx = cb.x + px·cb.w/1280`。因 `gx = cx·1.5`、`1920 = 1280×1.5`，**两式恒等**。
  - y：gold `boty = cb.y + cb.h + dy`，`gy = boty − gh`；self `acy = cb.y + cb.h − gh + 偏移`，`gy = acy`。**基准同为「底边贴内容区下沿」**（`cb.y+cb.h`）。

## 3 槽位上限抬高：只会动到「需要 slot 下标 ≥6」的场

| 侧 | 上限 | 出处 |
| --- | --- | --- |
| `build_story.py` 默认 | `self` → **6**（`STAGE_MAX_SLOTS`）／`gold` → **20**（`STAGE_MAX_SLOTS_GOLD`） | `--stage-max-slots` 可覆盖（dev/证据用） |
| `ui_staging.tjs` | `UIStageMaxSlots = 20` | 槽默认 `visible_default:false` + `asset:void` ⇒ 未用槽不绘制（实机日志 槽6..19 恒 `-`） |

**为什么 20**：★订正（一审，口径重立）——
- **抬 cap 的真正理由是「槽下标空洞」，不是「并发场多」**：CG 件（`CG背景/…`，1,195 行）也吃 `slot_hint` 下标，
  被跳过后**真立绘会落到 slot 6..18**（**17 场**有此现象）⇒ cap=6 会把这 17 场的 **405 条**事件判「越界」丢弃
  （构建日志 `槽位缺失或越界`：cap6 **409** vs cap20 **4**）。
- 金标 `slot_hint` **下标峰值 = 18**（`ot_s04_08a`，19 个立绘占 slot 0..18）⇒ 需 ≥ 19 个槽 ⇒ cap=20。
- ★数字订正：**真并发 >6 的场只有 2 个**（`ot_s04_08a` 峰值 **19** ／ `ot_s04_20a` 峰值 **7**）——
  此前正文/源码注释写的「>6 的场 **18** 个」是**错口径**：18 是「`slot_hint ≥ 6` 的场数」（＝会用到下标 6 的场），
  **不是同屏并发数**（错因：`03_scene_slots.tsv` 的模拟漏了「无名 remove＝清空全部」且把 CG add 算占用；
  该表已按忠实规则重出，见下）。

**「常规场逐场不变」对照（核心证据）**

```

python ... build_story.py --out _build/gold_c20 --staging-source gold --stage-max-slots 20  <31 场>
diff -rq _build/gold_c6/game _build/gold_c20/game
```

- 差异**仅 17 个 `scene_*.tjs`**，且**与「该场会发出的 `chr_add/chr_expr` 需要 slot 下标 ≥6」的集合逐场相等**（独立复算，集合相等 = **True**，见 `_build/C_c20_vs_c6.tsv` 与 §7 的下述命令）。
- **其余 14 个常规场（构建集内）逐文件逐字节相同** ⇒ 抬高上限对常规场**零影响**。
- 差异场清单（17）：`ot_s02_15c ot_s03_03a ot_s03_08b ot_s04_03c ot_s04_08a ot_s04_11b ot_s04_18b ot_s04_20a ot_s04_22a ot_s04_22b ot_s04_23a ot_s04_24a otp_p04_01b otr_s03c_03b otr_s03c_05a otr_s03c_17c otv_M09_01`
  另 `story_assets/` 侧仅多出「只有 cap20 才画得到」的立绘件（`Only in gold_c20` 52 件），非渲染参数变化。
- `gold`（默认）与 `gold --stage-max-slots 20` 产物**逐字节相同**（`diff -r` = 0）⇒ 自动口径落地正确。

**为什么 self 场不跟着抬到 20**（同一对照的另一半）：

```

build_story.py --out _build/self_c20 --stage-max-slots 20 <31 场>   # self, cap 20
```

原因：cap 参与「可见集收窄」（`_order[:max_slots]`）⇒ 抬高会改变保留集与几何，**破坏「self 逐字节等于现状」**。故 self 维持 6（**该分支的语义就是「越界槽永不显示」**）。

## 4 退化场（`scene_degraded=1`）降级策略

- 触阈场 **33**（`map_rate<0.98` 20 场 ∪ `align<0.90` 22 场）；其中**有 ≥1 条 chr 事件者 25 场**，构建集内 **13 场**。
- **默认 `--degraded-mode seq`**（＝沿用金标 `seq`，difflib 比例对位），**理由（已实测自证）**：
  1. 退化的是 `seq` 的**对位精度**，不是事件本身（op/名/坐标取自 PSV 明文）；
  2. 关键风险是「按 `seq` 排序会不会打乱**执行序**」。实测 **25/25 个退化场的 `seq` 在文件序（＝金标执行序）上非降，0 违反**（`_build/04_degraded_seq_mono.tsv`）⇒ 排序是稳定序，**执行序不被打乱**（不会出现「先消失后入场」）；
  3. `seq` 保留了现有对齐信息，属**最小改动**；而 `order` 会按序**均摊**到行区间，等于丢掉仍大致正确的落点信息。
- **备选 `--degraded-mode order`**（按 PSV 序均摊）保留为可切换口径。对照实测：与 `seq` 的差异**只有落点**，**逐 op 计数完全相同**（13 场差异场，`chr_add 2832 / chr_expr 411 / chr_move 102 / chr_remove 240 / chr_z 15` 两侧一致；`_build/C_ord_vs_seq.tsv`）⇒ 两种口径「同一批事件、不同时刻」，可安全回退。
- `otr` 另有一层独立风险：作品专属 skill 载「`otr` 逐行 `seq` 不可用（11/21 场）」，而本表 `seq` 取自 difflib（另一套方法），**未与该方法对拍** ⇒ gold 覆盖到 `otr` 时须复核（登记）。
