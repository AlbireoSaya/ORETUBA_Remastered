## 二、取整口径（U5，由 UI 组裁定，已写进脚本与 `UI清单.md`）

```
几何值（x y w h item_w item_h gap stack_bottom）与字号（font.size, font.shadow_ofs）：
    round_half_up(v × 1.5)              = floor(v × 1.5 + 0.5)      ← .5 一律进位
九宫格边距（nine.{l,t,r,b}，含 item_frame.nine）：
    max(1, round_half_up(v × 1.5))      ← 同上，另加下限 1
```

**为什么不用 Python 内置 `round()`**：它是 banker's rounding（round-half-to-even）。本批数据里 `v` 为奇数时 `v×1.5` 恰为 `.5`，两种舍入会给出**不同方向**的结果——
例：`7×1.5 = 10.5` → half-up 得 **11**、banker's 得 **10**；`5×1.5 = 7.5` → half-up 得 **8**、banker's 也得 **8**。即同批数据下 banker's 一个向下、一个向上，方向取决于前一位的奇偶。**half-up 是唯一可复现、且跨语言（Python / TJS / JS）一致的口径**，故定为交付口径。

对现有数据的影响：本批九宫格边距只有 13 与 5 两个值（`13×1.5=19.5→20`、`5×1.5=7.5→8`），half-up 与 banker's **恰好同解**，故 U5 的选择在本批数据上不产生视觉差异；差异只可能在 M13/M14 重写屏时的新数值上出现，届时按本口径执行。

**唯一被取整影响的几何异常**（见 §六 未决 2）：`fragment.g6_grid` 的 `gap 3 → 5`（half-up；banker's 会给 4），20 列合计 `20×63 + 19×5 = 1355px`，**超出该列表自身声明的 `w=1350` 5px**。

1. **`z` 不 ×1.5**（对照表未列）——`z` 是层序序号，与画布尺度无关；×1.5 会破坏层序的整数性与既有 `order` 映射。理由成立，全屏 `z` 逐一未变。
