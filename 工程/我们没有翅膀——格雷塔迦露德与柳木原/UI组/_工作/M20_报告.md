## 四、③ hover 态：实现方式与证据

### 4.1 实现链路

```
引擎真实鼠标移动
  └─ Window.onMouseMove(x, y, flags)            [startup.tjs · 新增]
       ├─ closing / tourOn → return（巡演不产生真实鼠标移动）
       └─ uiScreenHoverUpdate(x, y)             [ui_screens.tjs · 新增]
            ├─ uiScreenHoverAt(x,y)：扫当前屏 elements，取**最高 z 的、带 state_assets 的 hit**
            └─ 目标变化才返回 true → this.redraw()
                 └─ uiScreenCtx() 里 hoverHit = UIScrHoverHit
                      └─ uiWidgetDrawHit() 命中时画 state_assets.hover，否则 normal   [ui_widget.tjs · 改]
```

### 4.2 坐标换算口径（**沿用现有 onClick 的口径，未自行乘 1.5**）

- 现有代码：`onClick(x,y)` → `handleClick(x,y)` → `uiScreenClick(stageLayer, x, y)`，**直接拿 x,y 与 1920 画布的元素矩形比较**。
- 实测佐证（本次巡演日志）：`[UI] canvas = 1920x1080`、`[UI] client size = 1920x1080`；日志中真实鼠标事件坐标为 `onMouseDown x=974 y=240`、`x=924 y=223`（落在 0..1919 范围内）。⇒ **客户区尺寸 = 画布尺寸，客户区像素即画布坐标**。
- `资源组\04_1920画布与双分辨率方案.md` §6.4 所述「Window 事件坐标需 ×1.5」对应的是**「客户区 1280×720 + setZoom(2,3)」**配置；本工程用 `setInnerSize(1920,1080)` 且**未调用 `setZoom`**，故不适用。**本函数与 onClick 口径完全一致**，并在代码注释里写明「若编程组日后切到该配置，须把 onClick 与本函数**一起**改，两者不得分叉」。

### 4.3 性能与容错

- **只在悬停目标变化时重画**（`uiScreenHoverUpdate` 返回 true 才 `redraw()`），不每帧全屏重画；巡演中直接返回。
- 整段 try/catch；TJS2 坑已规避：无 `lastIndexOf`/`charCodeAt`/`parseInt`，`Timer` 未新增（未引入新计时器），未包装他人函数（无闭包风险）。

### 4.4 **hover 成立性的证据（含「我如何证明它成立」）**

**巡演不产生真实鼠标移动**，故不能靠巡演证明「真人悬停」。我用了**探针法**（任务书明示可用的方式），并**分两层**证明：

**层 1 — 命中判定（hit-test）正确**：在**临时副本**的 `startup.tjs` 里注入探针，直接调用**生产函数** `uiScreenHoverAt()` / `uiScreenHoverUpdate()`（不是复制品），日志原文：

```
14:55:01 [UI][HOVERPROBE] 空白点 960,540 命中 = []（期望空串）
14:55:01 [UI][HOVERPROBE] 菜单1中心 1704,232 命中 = [title.menu_hit_1]（期望 title.menu_hit_1）
14:55:01 [UI][HOVERPROBE] uiScreenHoverUpdate -> changed=1 | hoverHit=[title.menu_hit_1] | 悬停 (无) -> title.menu_hit_1  @ 1704,232
```
⇒ 空白处返回空串、菜单第 1 项中心返回其 id、状态机 `changed=1` 正确翻转。

**层 2 — 渲染路径正确（hover 图真的画出来了）**：探针在标题屏 `redraw()` 后另存一张 `hover_probe_title.png`，与同一屏的常态 `shot_01_title.png` 对比：
- 证据图：`_工作\M20_证据\hover_compare_menu.png`（左常态 / 右 hover，右侧菜单区裁切并排）
- **已 Read 目视确认**：**左图 7 项全银白；右图「开始游戏 START」为金色、其余 6 项仍银白** ⇒ hover 图确实被画、且**按元素精确定位**（不是整屏或整列变色）。
- 量化：菜单区（1500,150)-(1920,1010) 差异像素 **25,880 / 361,200**（7.2%，与「单项变色」的占比一致）。

**诚实边界（不假装验证过真人悬停）**：
1. 我**没有**验证「引擎把真实鼠标移动投递给 `onMouseMove`」这一步——本工程未做 GUI 自动化，无法注入真实鼠标移动。该步依赖引擎事实（`onMouseMove(x,y,flags)` 是 Window 级事件，`visual/WindowIntf.cpp:325-395`；`.zcode\skills\kirikiri-unpack\引擎工作原理.md:248` 有登记）。
2. 但巡演日志里**确实出现了真实鼠标事件**（`onMouseDown x=974 y=240` / `onClick 974,240 ignored（巡演模式）`），说明该环境有真实鼠标落在窗口上；它们被 `tourOn` 分支拦下（按设计），故未触发 hover。
3. 探针走的是 `uiScreenHoverUpdate` / `redraw` / `uiWidgetDrawHit` 的**生产代码路径**，唯一被替换的是「坐标从哪来」——所以证明的是「命中判定 + 状态 + 渲染」全通，**不证明**「引擎→onMouseMove 的投递」。人工验证方法：跑 `krkr\run_loose.bat`，把鼠标移到「开始游戏」上，应变金色。

**注**：探针只存在于**临时副本** `临时\ui_run_m20`（由 `_工作\M20_run_autotour.sh hover` 注入），**仓库内 `startup.tjs` 一字未动**。
